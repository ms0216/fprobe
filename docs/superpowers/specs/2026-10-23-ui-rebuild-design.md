# 画面の作り直し: 考えない画面・足し引きできる画面・強みで厳選した既定 — 仕様の案

状態: **案（利用者と決める項目が §7 に残る）**。2026-10-23 の利用者との相談から。

## 1. なぜ作り直すか

- 専用の画面（API 343 個のうち 215 個に専用の窓）を、使われ方を知らないまま私（Claude）の見立てで選んでいた。
  使われ方の記録（~/.fprobe/activity、10/17〜10/23 の 8,649 件）は開発中の試験がほとんどで、画面からの操作も人の手と
  自動の確かめが混ざって見分けられない。どこから（専用の窓・API パネル）呼んだかも記録に無い。
- 画面の中に計算が 73 件ある（判定・経験則・推定 32 件、決まった計算 41 件。docs/reports/2026-10-23-ui-computations.md）。
  人に見えて AI（API）に見えないものになっている。
- fprobe の価値に直結する「波形のある時刻に CPU がどの行にいたか」が、今は見られない（§4）。

## 2. 原則（利用者と合意、2026-10-23）

1. **画面は考えない層。** API の応答をそのまま描く。画面が持つのは見せ方だけ（16 進・単位・時刻の書き方・拡大縮小・
   目盛り・色・描画の間引き・利用者が選んだ列での並べ替え）。CLAUDE.md の設計原則に記載。
2. **人の操作と AI の操作は一対一**（見えるものも含めて）。意味は次の両方（2026-10-23 に直した。API パネルから
   呼べるだけでは一対一と言わない）:
   - AI が API でできること・見られるものは、人がそれを見ている場所でできる（例: 見えている値は、その窓で書ける）。
   - 人が画面でできること・見られるものは、AI が API でできる（原則 1 から従う）。
3. **どの API の画面も、利用者が足し・外せる。** 作り手が専用の画面を増やし続けない。
4. **既定の画面は、fprobe の価値が最大に出るものを厳選して並べる。** 窓から選ぶのではなく、まず「fprobe の価値が
   最大に出る使い方」を決め（§3.3）、その使い方に要る窓を既定にする。厳選の外の機能も、名前で探して呼べ、足せる
   ことが常に見える。機器に無い機能（ケイパビリティ）の窓は既定で出さない。
5. **日常のデバッグ（書き込み・ブレークポイント・ステップ）は IDE と分担できる。** VS Code 等の IDE から、デーモンの
   GDB サーバ（U04）経由で fprobe を使い、fprobe の画面を並べて解析を見る（利用者と相談した案 A）。IDE と重なる窓でも、
   原則 4 の使い方に要るもの（例: 波形の時刻と CPU の行を結ぶソース・呼び出し履歴・変数の窓）は既定に入れる。

参考にするもの: Lauterbach TRACE32（全操作がコマンド・メニューを利用者が定義）、Home Assistant（機器の機能から既定の
画面を作り、利用者が組み替える）、VS Code（コマンドパレット・窓の出し入れ）、Saleae Logic 2（最小の既定に解読器・測定を
足す）、Grafana（部品 1 つ = 問い合わせ 1 つ）。

## 3. 構成

### 3.1 汎用の窓（API の仕様から作る）

今の API パネルとお気に入りを育てて、どの API でも窓にできる形にする。

- **探して呼ぶ**: 名前・説明で探す（コマンドパレット）。引数の欄は仕様（JSON Schema）から作る（今の apiform）。
- **窓として置く**: 引数を決めた呼び出しを、配置の中の窓にする（今のお気に入りの延長）。読むだけの API は、
  利用者が選んだ間隔で読み直せる（既定は読み直さない）。
- **結果の描き方**: 応答の形から描き分ける（数 → 値、列 → 表、番地・語 → 16 進、時刻の付いた列 → 時間軸へ飛べる表、
  波形 → 波形）。描き分けの規則は「形」だけで決め、中身の意味で判定しない。描き方を API の仕様に注記できるようにする
  （例: この欄は番地、この列は時刻）。
- **AI の呼び出しを開く**: 操作の記録の 1 件から、同じ引数の窓を開ける（AI が見たものを人が同じ形で見る）。

### 3.2 専用の窓

汎用の窓で足りない見せ方（波形・時間軸・ソース・メモリの表・グラフ）だけを専用に作る。専用の窓も API の応答を描く
だけで、計算は持たない。今の専用の窓は、§3.3 の既定に入るものと、汎用の窓で置き換えられるものに分ける。

### 3.3 既定の配置

**決定（利用者の承認 2026-10-24）**: 案 2 を既定（解析の配置 analysis）にする。根拠は docs/reports/2026-10-24-fprobe-value-analysis.md
（価値が出る場面: 条件を置いて捕まえ前後を 1 本の時間軸で見る・FPGA と MCU の切り分け・時間を測る・試して確かめる・止めずに
見る。AI の作業を人が見て引き継ぐことは全部に乗る層）と 2026-10-24-competitor-ui-research.md（中心の窓を固定・時刻の連動は
既定で全部の窓・配置は名前で切り替え）。中央 = 時間軸、右上 = 条件と今の値（System）、右下 = その時刻のコードの位置
（Source・Call Stack・Locals）、下 = Logic Analyzer・Event Log・Data Sampling・Fault・Recordings・Activity。
今までの既定（ソースが中心）は「デバッグの配置」（debug）として表示メニューから選べる。作る順（利用者の承認）:
時刻からコードの位置へ（§4）→ クロストリガの経路をまとめた窓 → 試す窓（故障注入・規則・フック）→ 右クリックのメニュー。

以下は案 2 の前の初めの案の記録:

**決め方**: (1) fprobe の価値が最大に出る使い方を、CLAUDE.md の目的と優先順（1. 解析力: ロジアナとデバッガの一体化・
クロストリガ・共通のタイムスタンプで「なぜ壊れたか」を見つける、2. 日常のデバッガ、3. AI による開発の自動化）から
書き出す。(2) 各使い方を、始めから終わりまで画面でたどったときに要る窓を挙げる。(3) その和を既定にする。使い方の
一覧は利用者と決める。下の表は (1)(2) をまだ通していない私の初めの案で、決め方を通して作り直す。

使い方の候補（私の案）:
- 不具合が起きた瞬間（Fault・ブレークポイント・クロストリガの条件）の前後を、波形・CPU の行・タスク・変数で見る。
- 止めると壊れる不具合（通信・モータ・BLE）を、止めずに変数・波形・タスクで見続け、条件で記録を残す。
- AI が自動で試した結果を、人が同じ時間軸で確かめる。

初めの案の窓:

| 窓 | 理由 |
|---|---|
| 時間軸（MCU の出来事・ロジアナの波形・FPGA の観測・Linux を 1 本に） | 共通のタイムスタンプ = fprobe の中心 |
| 時刻のコードの位置（ソースの行・関数・呼び出し履歴・その時の変数） | §4。波形の時刻と CPU の行を結ぶ |
| クロストリガ（何が起きたら何を止める・取り込む） | 解析力の柱 |
| 止めずに見る（変数・RTOS） | 止めると壊れる不具合を見る |
| Fault と直前の記録 | なぜ壊れたか |
| AI の操作の記録 | AI のしたことを人が見る |
| 止める・走らせる・接続の状態（ツールバー） | 最小限の操作 |

既定に入れない（足せる）: ブレークポイントの管理・ステップの細かい操作・Flash・ペリフェラル・プロファイル・
ヒープ・電源・Linux・FPGA 観測の設定など。どれを既定に入れるかは使われ方の記録（§3.4）で見直す。

### 3.4 使われ方の記録（事実）

操作の記録（activity）に、**どこから**（専用の窓 / 汎用の窓 / API パネル / AI / 台本）と **誰が**（人の手 / 自動）を足す。
一定の期間ごとに一覧で見られるようにする（例: API パネルから何度も呼ばれた操作、開かれない窓）。既定の配置に上げる・
下げるは利用者が決める（fprobe は事実を出すだけ）。

### 3.5 右クリックのメニュー（利用者の指摘、2026-10-23）

今は画面のどこにも右クリックのメニューが無い（デバッガの主な入口が無い）。値の種類（番地・時刻・変数の式・レジスタ・
ソースの行）ごとに、その値を引数に取る API を並べる（例: 番地 → メモリで開く・ウォッチに足す・番地一致のトリガ、
時刻 → 時刻のコードの位置・時間軸へ、行 → ブレークポイント・ここまで実行）。メニューは API の仕様の注記（この欄は
番地・時刻 等）から作り、画面は判断しない。利用者が足した API もメニューに出る。
利用者の決定（2026-10-24）: メニューは**厳選した短い一覧＋「その他の操作」の下に、その値で呼べる全 API**（全部を並べると長く
なり右クリックの速さを失うため）。厳選の項目は、競合・類似の道具の調査（docs/reports/2026-10-24-competitor-ui-research.md）
を踏まえて決める（利用者:「競合類似ツールの仕様をよく研究して、ブラッシュアップ」）。

### 3.6 見えている値はその場で書く（利用者の指摘、2026-10-23）

API には書く操作がそろっている（target.registers.write・target.memory.write・debug.write_expression・watch.write・
target.peripheral.write・fpga_obs.register_write 等）が、画面から書けるのは一部（レジスタ・メモリ・ウォッチ・
ローカル・ペリフェラル・ダッシュボード）で、入口もダブルクリックだけ（印が無い）。データサンプリング・FPGA 観測の
レジスタ・RTOS・システム解析の値は書けない。書く API がある値は、どの窓でも同じ操作（右クリックの「値を変える」と
ダブルクリック）で書けるようにする。走行中・停止中で使う API が違うときは、どちらで書くかを画面に示す（API を選ぶ
規則は API の仕様の注記に置く）。

## 4. 時刻からコードの位置へ（新しい API）

今の事実: PC のサンプル（profile の pcsr の方式。サンプラの記録 stream "sample" に、波形と同じタイムベースで残る）、
止まったときの出来事、RTOS の時間軸（その時刻のタスク）。「時刻 t のときどの行か」を返す API と、時間軸のカーソルに
合わせるソースの窓は無い。

- **API（案）**: `recording.code_at(t)` — 時刻 t について、直前と直後の PC のサンプル（時刻・PC・関数・ファイル・行）と
  t との差、そのときのタスク（RTOS の時間軸があれば）、t の近くで止まった出来事があればその PC（正確）。PC の
  サンプルが無ければ無いと返す。**行を推定しない**（サンプルの間に何を実行したかは分からない、と隙間の幅で示す）。
- 止まった瞬間は PC が正確。ETM のあるターゲットでは直前の命令の履歴（trace.etm.history）も返す。
- PC のサンプルの速さは SWD のクロックで決まる（1 回 約 50 ビット。10 MHz で約 5 µs）。速さの上限はターゲットと線で
  決まるので、使う側が選べる形を保つ。
- 画面: 時間軸のカーソルを動かすと、ソースの窓がその直前・直後の行を示す（隙間の幅も出す）。

## 5. 画面の中の計算 73 件の扱い

docs/reports/2026-10-23-ui-computations.md の全件を、1 件ずつ次のどれかにする（ヒューリスティックの除去と同じ進め方。
台帳を作る）。

- **ホストへ移して API で返す**: 決まった計算（b）。既に同じ API があるもの 7 件は、画面をその API に替える。
- **使う側が明示する引数にする**: 経験則の値（例 c23 の読みの周期、c14 の既定の値、c29 のクロックの範囲）。暗黙の既定にしない。
- **外す / プラグインへ**: 推定（c15・c22・c26・c27・c28 等）は、事実（誰が始めたかを本体が記録する等）で置き換えられる
  ものは置き換え、置き換えられないものは外す。
- **見せ方として残す**: 1 件ずつ確かめ、本当に見せ方だけのもの（例 c32 の真偽の色）。

## 8. しないこと

- 使われ方を知らないまま、作り手の見立てで専用の窓を増やすこと。
- 時刻のコードの位置を推定で埋めること（サンプルの間の行を補う等）。
