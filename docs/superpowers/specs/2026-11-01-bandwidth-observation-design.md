### 1.2 50 MB/s の壁の原因（事実と推測を分ける）

事実:
- 25 MS/s の流れの間、PYNQ の 2 コアとも約 85 % 使用。CPU0 は user 33 %（NEON の読み = 複写の 1 回目）・softirq 49 %（NIC の受信 = ACK）、CPU1 は system 79 %（送信）（10.12 の /proc/stat）。
- PC が空いている時間帯に通った回も溢れた回も、中継の EAGAIN 0・`tcp_ring` の満杯 0（10.13）= そのときの律速は PC でなく PYNQ。
- PC が忙しい時間帯は、PC の受信が詰まり EAGAIN が数万回（10.14）= PC の受信の余裕は 50 MB/s に対して 1〜2 割しかない。
- 素の TCP の送信（複写 1 回・読みなし）だけでも 1 コアで 65〜75 MB/s が上限（10.8、10.12）。
- 中継の起動直後の 3 分間は、jupyter 等の Python が CPU を取り合って溢れた。`Nice=-20` で解決。softirq は nice の対象外（10.15）。

導出:
- 壁は **2 つが近接**している: PYNQ 側（2 コアの TCP 処理と複写、約 50〜54 MB/s）と PC 側（Python の受信、約 56〜66 MB/s）。PYNQ 側だけを上げても、PC 側を上げないと 60 MB/s 前後で止まる。
- ケーブル（117.7 MB/s）・NIC・DDR・PL の書き込みは、どれも 2 倍以上の余裕があり、律速ではない。

推測（未確認）:
- PYNQ の送信の 1 MB あたりの時間のうち、**バイト数に比例する部分（複写・チェックサム）と、パケット数に比例する部分（TCP/IP の処理・割り込み・ACK）の割合は測っていない**。手の選び方はこの割合で決まる（1.4 の B0 で測る）。
- GEM の送信のチェックサムの肩代わり（`tx-checksum`）と分散/集約（`scatter-gather`）が Linux で有効かは確かめていない。無効なら、カーネルが中身を読んでチェックサムを計算しており、ゼロコピーの効果が出ない。
- Zynq-7000 の GEM は TSO（TCP の分割の肩代わり）を持たない、と理解しているが、`ethtool -k eth0` で確かめていない。
- PS の CPU は 650 MHz（**基板の資料による値・未確認**）。-1 の上限 667 MHz（DS187）との差は小さく、クロックを上げる手は無い。

B0 の結果（2026-11-01、la-stream-ps-direct 10.18）で、上の推測は次のとおり確かめた:
- オフロード: `tx-checksumming: on`・`scatter-gather: on`・`tcp-segmentation-offload: off [fixed]`（TSO は無い）・`generic-segmentation-offload: on`（事実）。
- CPU は 650 MHz（`clk_summary` の cpu_6or4x。ps_clk 50 MHz・armpll 1300 MHz）、DDR は 1050 MT/s（ddr3x 525 MHz）（事実）。DDR のバス幅は未確認のまま。
- 送り手の CPU1 の時間のうち、バイト数に比例する複写は約 3 割（`send` − `MSG_ZEROCOPY` = 4.3〜5.3 ms/MB、導出）。中継では、これに CPU0 の NEON の読み（約 9 ms/MB）が加わり、25 MS/s で CPU0 の idle は 0 %（事実）。
- `/dev/mem` の mmap からの `MSG_ZEROCOPY` は `EFAULT`（事実）。1.3.1 の 2 の推測どおり、リングのゼロコピーにはカーネルモジュールが要る。

### 1.3 根本の手と、採る・採らない

| 手 | 効く段 | 見込み | 判断 |
|---|---|---|---|
| **A. PL の Ethernet MAC を直接使う**（PL に UDP/TCP を作る） | PYNQ の CPU を全部外す | PYNQ-Z2 の Ethernet の PHY は PS の MIO につながっている（**基板の資料。リポジトリでは `docs/boards/pynq-z2.md` が eth0 を PS として扱う**）。PL から PHY に届く線が無い。EMIO の GEM も PL の端子に出るだけで PHY が無い | **PYNQ-Z2 では不可**（PHY を PMOD に足す = 追加購入。方針外）。Primer の PL の MAC は 100 Mbit/s（12.5 MB/s）で、今より遅い |
| **B. GEM を Linux から取り上げて自作の駆動で直接送る**（カーネルを通さない） | 同上 | 線の速さ（UDP なら 約 118 MB/s）まで | **採らない**: GEM0 は送信キューが 1 本（**推測**）で、Linux の eth0（SSH・制御）と共用できない。さらに UDP は PC の NIC が 2 万個/秒で破棄する（10.3）ので、PC の設定を変えない方針では 30 MB/s を超えられない |
| **C. UDP に戻す（大きなデータグラム・`sendmmsg`）** | PYNQ の TCP の処理 | PC の NIC の破棄（10.3）で 約 21 MB/s が欠けなしの上限 | **採らない**（同上。TCP は再送と流量の調整で、PC によらず欠けない） |
| **D. ジャンボフレーム（MTU 9000）** | パケット数・ACK 数が約 1/6 | PYNQ のパケット数に比例する部分が減る | **採らない**（PC のメインの回線の MTU 変更とスイッチの対応が要る。10.14） |
| **E. ゼロコピーの送信**（DDR のリングのページを、そのまま TCP に渡す） | 複写 2 回（CPU0 の user 33 % と CPU1 の system の一部） | 1.4 の B0 の割合しだい。バイト数に比例する部分が半分なら PYNQ 側 約 70〜90 MB/s（**推測**） | **採る（B0 の結果が条件）**。1.3.1 |
| **F. PS の負荷の分け方を変える**（スレッド・割り込みの CPU の割り当て） | — | 既に「読み = 割り込みの CPU0、送る = CPU1」に固定（10.9、`main.c:121-135`）。逆の配置は 36 MB/s。2 コアしか無く、E で CPU0 の複写が消えれば、割り当ては見直す | E の後に測り直す |
| **G. PC の受信を Python の外へ**（受信と組み立てを、ネイティブのスレッドに） | PC の 56〜66 MB/s の壁 | 線の速さまで（**推測**。Windows の TCP の受信そのものは 1 GbE を受けられるのが普通。いまの CPU は Python の呼び出しとコピー） | **採る（E と組で）**。Windows の設定は変えない（アプリの中の変更だけ）。1.3.2 |
| **H. 情報を減らす無損失の手**（RLE・la_pack・適応 RLE） | 帯域の全段 | 信号しだい（RLE）・チャンネル数しだい（la_pack） | 実装済み・別の主題（la-stream-pack、la-resolution）。この文書は「生の帯域」を上げる |

#### 1.3.1 E. ゼロコピーの送信（設計の要点）

- いま: DDR のリング（reserved-memory、`/dev/mem` の mmap）→ NEON で `tcp_ring`（利用者空間）へ複写 → `sendmsg` でカーネルがもう一度複写（`main.c:331`）。
- 変える: リングの中身のページを、そのまま TCP の送信に渡す。CPU は中身を読まない。見出し（中継が作るかたまりの見出し 1 拍）だけは小さな別のバッファにあり、`iovec` で中身と並べる。
- 前提（どれも未確認。B0 で確かめる）:
  1. GEM の送信のチェックサムの肩代わりと分散/集約が有効（無ければカーネルが中身を読む = 効かない）。
  2. `/dev/mem` の mmap は `VM_PFNMAP` で、`MSG_ZEROCOPY` の対象にならない（**推測**。Linux の作り）。そのため、リングを「普通のページ」として見せる口が要る: 候補は (a) 小さなカーネルモジュール（reserved-memory の領域を `vm_insert_page` で mmap させ、`MSG_ZEROCOPY` を使う）、(b) 同じモジュールの中で、ページの列を直接ソケットに渡す（`sendmsg` の `MSG_SPLICE_PAGES` 相当。カーネル 6.6 の口は要確認）。(a) は中継の C の変更が小さい。
- 正しさの条件（ここを間違えると中身が壊れる）:
  - **`LA_CONSUMED`・`EV_CONSUMED` を進めるのは、カーネルがそのページを手放した後**（`MSG_ZEROCOPY` の完了通知 = TCP の ACK の後）。いまは `sendmsg` が戻った時点で進めてよい（複写済みだから）が、ゼロコピーでは再送のためにページが使われ続ける。リングに要る余裕は 帯域 × 往復（50 MB/s × 数 ms = 数百 KB）で、リング 32 MB に対して小さい（導出）。
  - キャッシュ: PL は HP（非コヒーレント）で DDR に書き、GEM の DMA は DDR を直接読む。CPU がその行を書いていなければ、送信の DMA の準備（キャッシュの書き戻し）で古い値が DDR に戻ることは無い（**推測**。ARMv7 の DMA の扱い）。中継は中身を読まず・書かない、を守る。
  - 世代（`STREAM_EPOCH`）・書いた位置の公開（AXI の B の後）の規則は今のまま（la-stream-ps-direct 3.2）。
- 失敗のときの扱い: モジュールが無い・チェックサムの肩代わりが無いときは、今の 2 回の複写の道で動く。どちらで送っているかを、中継の起動の記録と、ホストが読める状態に出す（黙って遅い道に落ちない。使う側が分かる）。

#### 1.3.2 G. PC の受信（Windows の設定を変えずに）

- いま: Python のスレッドが `recv_into` で受け、64 KB に満たなければ 1 ms 眠ってまとめて取る（`eth_link.py` `_tcp_rx_task`、10.14）。受けたバイト列をロックの下で組み立てて分ける（10.10 の `_take`・`_dispatch`）。
- 変える候補（どれも PC の OS の設定は変えない）:
  1. 受信と、かたまりの境目の検出を、ネイティブのスレッド（C の拡張）にし、Python には大きな塊（MB 単位）を渡す。Python の 1 秒あたりの呼び出しが数百回になる。
  2. 1 の前に、純 Python のまま 1 回の `recv_into` を 1 MB にし `MSG_WAITALL` を使う版を測る（ネイティブが要るかの判断の材料。効果は**推測**）。
  3. ソケットの受信バッファ（`SO_RCVBUF`、アプリの設定）は今の 8 MB のまま。
- 確かめ方: PYNQ の送信では 75 MB/s を超えて送れないので、**PC の中のループバック**（同じ PC の送り手 → 受け手）で、受け側だけの上限を測る。

### 1.4 確かめ方（B0: 先に測るもの。コードは測定の道具だけ）

1. `ethtool -k eth0`（PYNQ）: `tx-checksumming`・`scatter-gather`・`tcp-segmentation-offload`・`generic-segmentation-offload` の値。
2. 送信の内訳の割合: PYNQ の上で (a) 利用者空間のバッファからの `send`（いまの素の TCP の測り方）、(b) tmpfs のファイルからの `sendfile`（ページキャッシュからのゼロコピー）を、同じ 16 KB の単位・同じ時間で比べる。(b) が (a) より速い分が「バイト数に比例する部分」。(b) も 1 コアを使い切るなら、残りはパケット数に比例する部分で、E の効果は小さい（その場合の手は D か、パケット数を減らす手で、PC の設定の制約に当たる）。
3. `/proc/softirqs` の NET_RX・NET_TX と `/proc/interrupts` の eth0 を、25 MS/s の 10 秒の前後で差を取り、1 MB あたりの割り込み・softirq の回数を出す。
4. PC のループバックで、Python の受信だけの上限（1.3.2 の 2 の版と今の版）。
5. 結果は la-stream-ps-direct の 10 章の続きに記録する。

### 1.5 到達点の見込み

### 1.6 イベントの帯域（垂れ流しに乗るほかの流れ）

- 事実: イベントは 1 件 128 ビット = 16 B（`event_collector.vhd:82-88`）。SWO・UART のバイトは **1 バイトが 1 件**、サンプラの値は **1 語が 1 件**。深いバッファの構成では、イベントのリングも PS 直読みで同じ TCP に乗る（la-stream-ps-direct 2 章）。
- 導出: SWO を 25 Mbit/s で流し続けると、最大 約 3.1 M バイト/秒 = **約 50 MB/s のイベント**になり、それだけで今の壁に当たる（3.3）。サンプラを 1 MHz で読むと 16 MB/s。
- 帯域を上げる手の効果は、ロジアナとイベントの合計に効く。イベントの詰め方は 2.5・3.4。

#### 1.7.4 自作のモジュール (a) の正しさの条件

- ページ: 予約は `no-map` なしで、ページは struct page を持つ `PG_reserved`（1.7.1 の事実）。`vm_insert_page` は無名・slab・型付きのページだけを断り、予約のページは写せる。
  写した領域は `VM_MIXEDMAP`（`VM_PFNMAP`・`VM_IO` でない）なので、`MSG_ZEROCOPY` の `get_user_pages` が通り、ページの参照の数えは 1 から増えて戻るだけで、ページが解放されることは無い（**ソースの作りからの推測。試していない**。予約のページの参照の数えが 1 であることも、memmap の初期化の作りからの推測）。
- キャッシュ: PL は HP（非コヒーレント）で DDR に書き、GEM の DMA は DDR を読む。CPU はリングの中身を読まず・書かない（送信のチェックサムの肩代わりは on、1.4）。
  直線の写像（キャッシュあり）に先読みで入る古い行は**汚れていない**ので、送信の DMA の前の clean は何も書き戻さない（ARMv7 の作り）。
  **危ないのは、カーネルがゼロコピーをやめて中身を写す場合**（完了通知の `SO_EE_CODE_ZEROCOPY_COPIED`）: 写しはキャッシュありの直線の写像を読み、古い中身を送りうる（**推測**。パケットの盗み見（tcpdump 等の AF_PACKET）が `skb_orphan_frags` で写させる、が候補）。
  この通知を数えて、1 回でも出たら黙らずに記録し、ゼロコピーの道を止める（今回の合成の試験では copied は全部 0）。
- PL との競合: **`LA_CONSUMED`・`EV_CONSUMED` は完了通知（その範囲のページを TCP が手放した = ACK 後、再送の可能性が無くなった後）でだけ進める**。完了通知は `sendmsg` の呼び出しの番号の範囲で来るので、呼び出しごとのリングの終わりの位置を順に覚えておく。
  必要な余裕は 帯域 × (往復 + 送信バッファ 4 MB 分) で、100 MB/s なら 約 4〜5 MB（導出）。リングのロジアナの部分（約 30 MB）に対して収まるが、いまより PL が溢れるまでの余裕は減る。`optmem_max` 10240 で完了通知が詰まると `ENOBUFS`（今回の合成は 0 回）。
- 世代（`STREAM_EPOCH`）が変わった時は、古い世代の未完了のページが TCP に残っている。新しい流れが同じ番地を上書きしても、古い流れの TCP は壊れた中身を送るだけで新しい流れに混ざらないが、ホストは古い流れの末尾を捨てる必要がある（いまも世代の切り替えで TCP をつなぎ直すかは**未確認**）。
- 見出しの形: 1.7.2 のとおり、見出し 16 B を 4 KB ごとに挟むと効果が消える。**かたまりを大きくする**（見出しの拍数の欄は 16 ビット = 65535 拍まで表せる。上限はホストの `STREAM_SEG_MAX_BEATS` = 256 の検査、`la.py:358`。PL の窓経由の道の `STREAM_CHUNK` とは別に、PS 直読みの道だけ大きくできる）か、見出しを PL がリングの中に書く（PL の変更）。前者なら 64 KB 以上ごとに 1 つで、合成の `zc` の 98 MB/s に近づく見込み（**推測**。見出し 1 つ/64 KB の並びは測っていない）。
- 失敗のとき: モジュールが無い・写せない・copied が出たら、いまの 3 回の複写の道で動き、どちらの道かを起動の記録とホストが読める状態に出す（1.3.1 のとおり）。
- 2 本の TCP にするなら: ホストが 2 本の流れを、見出しの位置（ロジアナの拍の位置）で 1 本に並べ直す作りが要る（ホストの変更。設計は未）。

#### 1.7.5 結論

- **最も効果がある手は、ゼロコピーの送信（リングのページをそのまま TCP に渡す）で、PYNQ-Z2 のいまのカーネルではモジュールが要る**。モジュールなしで届く上限は 約 55 MB/s（導出、いまの 50 から 1 割）で、
  ゼロコピー 1 本で 約 98 MB/s、2 本で 112〜115 MB/s（ケーブルの 96〜98 %、合成の実測）。ほかの手（割り込みのまとめ・ACK・キャッシュあり・XDP・カーネルの作り直し）は、使えない・正しくできない・得が無い、のどれか（1.7.3）。
- **ただし「モジュールを足せば速くなる」ではない**: いまのかたまり（4 KB ごとに 16 B の見出し）のままゼロコピーにすると、合成の実測で 68〜71 MB/s（普通の `send` と同じ程度）。**かたまりを大きくする変更（ホストの `STREAM_SEG_MAX_BEATS` と中継の PS 直読みの道）が、モジュールと組で要る**。これはモジュールなしでもできる（いまの道でも見出しの拍の分が減るだけで、速さはほぼ変わらない見込み、**推測**）。
- **最も正しい形は、自作の小さなモジュール (a)**（予約の領域を `vm_insert_page` で写すだけの文字デバイス。リングの位置・PL・デバイスツリーを変えない）。理由: 予約のページは struct page を持つので新しいメモリの確保が要らない、カーネルの中に持つのは写像だけでソケットの扱いは中継のまま、完了通知で CONSUMED を進めるのは利用者空間の C で試験できる。
  u-dma-buf は既定の写像が `VM_PFNMAP` で通らず、`quirk-mmap-page` とデバイスツリーの変更が要る（自前の確保になる）ので、(a) より変更が多い。
- **2026-11-02 の追記（1.7.9 の事実）**: 上の「1 本で 約 98 MB/s」は合成の送り手の実測で、ゼロコピーの中継の実際の流れでは、16 ch の RAW で
  66.7 MB/s（33.3 MS/s）を 60 秒持続し、100 MB/s（50 MS/s）は 2.4〜4.5 秒で溢れた（溢れるまでの平均 84.8〜92.0 MB/s）。かたまりは 4096 拍（64 KB）に
  した（`STREAM_SEG_MAX_BEATS` 4096）。モジュールなしの道（新しい中継）は 25 MS/s のまま。2 本の TCP は作っていない。
- 先にやってよいこと（モジュールなし・判断を待たない）: 中継の `stage` を通さない読み（CPU0 で 約 1 ms/MB）と 1 回の `sendmsg` を大きく（CPU1 で 約 1 ms/MB）。どちらもモジュールの有無によらず残る道を速くする。
- 選ぶ前に確かめること（モジュールを読み込む利用者の承認が要るものに印 ※）:
  1. ※ (a) の写像から `MSG_ZEROCOPY` が `EFAULT` にならず、copied が 0 で、98 MB/s 前後が出るか（1.7.4 の推測の確認）。
  2. 見出しを 64 KB 以上ごとにした `iovec` の並びで、合成の `MSG_ZEROCOPY` が 98 MB/s 近くに戻るか（モジュールなしで測れる）。
  3. ゼロコピーの道で、中継の読み取りスレッド（MMIO だけになる）の CPU0 の時間、完了通知の遅れとリングの余裕（PL の溢れまでの時間）。
  4. PC の受信が 100〜115 MB/s を、分割・解読まで含めて受けられるか（10.18 の 4 は 90 MB/s まで。G の要否）。
  5. 2 本の TCP にする価値（+15 % で、ホストの並べ直しが要る）。1 本の 98 MB/s で足りるなら要らない。
  6. 遅らせの設定・`SPIN_NS` の回る作りの見直し（ゼロコピーで CPU の配分が変わるため、1.3 の F）。
  - 2・4 と、上の「先にやってよいこと」の見積もりは、1.7.6 で測った（モジュールなし）。
  - 1 と、3 のうち送り手と softirq の CPU は、1.7.8 で測った（モジュール (a) を作って読み込んだ。中継は変えていない）。
  - 3 の残り（ゼロコピーの道の中継・完了通知の遅れ・リングの余裕）は、1.7.9 で中継に入れて実際の流れで測った。

  Windows のプロセスの sys の時間が大きい（分割ありで 8 秒中 約 3 秒、受信だけで 1.4 秒）。4 MB の `bytes` を作り捨てる度のメモリの確保とゼロ埋めが候補（**推測**。確かめていない）。
- 含めていないもの: 実物の `LaStream` の UDP の CSR の読み（≥ 50 ms ごとに 2 回）、記録（`recording_stream.py` の `add_waveform` と、変化点ごとに Python の generator で `array("Q", ...)` を作る処理 `recording_stream.py:179`）、VCD の書き出し。毎サンプル変化する信号では、記録の generator がさらに律速になるはず（**推測**。測っていない）。
- 判断の材料（G の要否）: 受信・分割はいまの作りで 100〜118 MB/s を受けられた（PC 1 台・この時間帯）。C の拡張が要るのは「変化点の多い信号を解読して記録する」場合で、そこは受信でなく解読と記録の表現の問題。受信のスレッドの上限（溜める量）は別に決める必要がある（→ 1.7.7 で直した）。

##### 3. 中継のモジュールなしの改善（`stage` を通さない・1 回の `sendmsg` を 256 KB に）の見積もり

中継は変えず、同じ形の合成の中継 `b2_relay`（sudo で `/dev/mem` を読むだけ。PL のレジスタは触らない）で比べた:
読み手（CPU0）は `/dev/mem`（`O_SYNC`、0x1E000000 から 8 MB、PL は書いていない）を NEON で読み、見出し 16 B + 4096 B のかたまり 3 つ（12336 B）を 16 KB × 32 のスロットに詰める（中継の `tcp_ring` と同じ）。
`stage` = 4112 B の stage に写してから `memcpy`（いまの中継）、`direct` = スロットに直接写す。送り手（CPU1）は詰まったスロットを最大 `iovmax` 個まとめて普通の `sendmsg`（8 = いまの `TCP_IOV_MAX`、21 = 約 256 KB）。各 10 秒、3 回ずつ。

| 形 | MB/s（3 回） | 1 回の sendmsg の平均 | CPU0 user ms/MB（導出） | CPU0 | CPU1 |
|---|---|---|---|---|---|
| stage・8（いまの中継の形） | 45.3・42.1・44.7 | 25〜27 KB | 約 10.3 | idle 0 %（user 42〜47・softirq 40〜49） | idle 0 %（sys 92〜95） |
| direct・8 | 45.0・42.3・41.8 | 26〜29 KB | 約 10.0 | idle 0 % | idle 0 % |
| stage・21 | 43.3・43.8・41.9 | 26〜28 KB | 約 10.5 | idle 0 % | idle 0 % |
| direct・21 | 40.2・44.1・41.2 | 26〜28 KB | 約 9.8 | idle 0 %（softirq 45〜51） | idle 0 % |

- 事実: **4 つの形の差は、回ごとのばらつき（±2.5 MB/s）の中で、速さは変わらなかった**。`direct` で CPU0 の user は 0.3〜0.7 ms/MB 減るが、CPU0 の空いた分は softirq が埋め（idle は 0 % のまま）、速さにならない。
- 事実: `iovmax` を 21 にしても 1 回の `sendmsg` は 26〜28 KB のまま（スロットが溜まらない = 読み手が先に詰まっている）。10.18 の「64 KB と 256 KB の差」は、送るものが常にある合成の送り手での値で、この道では効かない。
- 事実: 送っている間の NEON の読み（CPU0 の user）は 約 10 ms/MB で、読みだけの試験（1.7.2、4.9 ms/MB）の 2 倍。10.18 の実際の中継の user 9.0〜9.5 ms/MB と合う。送信の DMA・softirq と取り合うため、と見ている（**推測**）。
- 合成の中継は 40〜45 MB/s で、実際の中継（50 MB/s）より低い。PL のレジスタの読み（中継で 約 2〜3 ms/MB）が無い一方、動いている本物の中継が CPU を 1〜2 割使っていた分だけ不利（上の注意）。比べるのは形どうしの差。
- **判断の材料: 1.7.3 の「中継の改善（モジュールなし）で 約 55 MB/s」の見込みは、この合成の試験では確かめられなかった（増えなかった）**。CPU0 は「読み 約 10 + softirq 約 10 ms/MB」で埋まり、CPU1 も `sendmsg` で埋まる。モジュールなしの道は、この 2 つの手では 50 MB/s 前後のまま、と見るのが妥当（導出）。

#### 1.7.7 PC の受信の溜まりすぎの直し（2026-11-01、ホストだけ。実機では未確認）

1.7.6 の 2 の「消費側が遅れても TCP の受信は止まらず、`FrameLink._bytes` に上限なく溜まる（8 秒で 435〜517 MB）」を直した。

**考え方**: TCP には流量制御がある。受け側が受け取りを止めれば、カーネルの受信バッファが埋まり、TCP の窓が閉じて中継の送りが止まる。
中継は送れない間 DDR のリングを読めず（`LA_CONSUMED` が進まない）、リングが溢れれば PL が書き込みを止めて overrun を立てる（今の仕組み。
ホストは `LA_DEEP_STATUS.overrun` を見て止め、それまでの分を出し切る）。遅れを溜める場所は機器の DDR のリングで、溢れは機器が事実として記録する。
PC のメモリに上限なく溜めるのは誤りで、黙って捨てるのも誤り。だから **PC の受け取り済みに上限を設け、上限で受信を止める**。

**作り**（`host/fprobe/frame_link.py`・`eth_link.py`）:
- `EthLink.open_stream_tcp(..., buffer_bytes=...)`: 受け取って未読の量の上限。**キーワードの必須の引数で、既定は持たない**（呼び手が明示する）。
- TCP の受信のスレッドは、`recv_into` の前に空き（上限 − 未読）を求め、空きの分だけ受け取る（`recv_into(buf, min(空き, 1 MB))`）。
  空きが 0 なら、読み手（`read_bytes`）が減らすまで待つ（`FrameLink._wait_stream_room`。close に気づくため 50 ms ごとに起きる）。
  よって未読は上限を超えない。PC のメモリは「上限 + カーネルの受信バッファ（`_RCVBUF` 8 MB）+ 受け取りの作業域 1 MB」までで止まる。
- 捨てる処理は無い。読み始めれば、止めていた分も順に全部届く（試験で確かめた）。
- UDP の道（TCP を開いていないとき）のストリームには上限を設けていない: UDP の受信は制御・DAP と共通で止められず、止めても
  送り手は止まらない（カーネルが捨て、`lost_frames` と通し番号の飛びで分かる）。`capacity_bytes = None` として事実のまま返す。

**上限の値**（`la.STREAM_BUFFER_BYTES` = `2 × LaStream.READ_MAX` = 8 MB。`Session.open_eth(stream_buffer_bytes=None)` が渡す。変えたければ呼び手が明示する）:
- 消費側（`LaStream.chunks`）は 1 回に最大 `READ_MAX`（4 MB）を読む。その 1 回を処理している間に次の 1 回分が溜まれば、
  消費側が平均で付いていける限り受信は止まらない（二重のバッファ）。1.7.6 の 2 で付いていけた場合の溜まりの最大は 5〜9 MB で、
  8 MB を少し超える回は、超えた分だけカーネルの受信バッファ（8 MB）と、その先の DDR のリングが受ける（速さが落ちるだけで欠けない）。
- それより大きくしても、消費側が平均で遅れているときに中継が止まるのが遅れるだけで、溢れるかどうかは変わらない（遅れを溜められる量は
  リングの大きさで決まり、PC に溜めた分はリングの代わりにならない。溜めるほど、止めた後の出し切りが長くなる。1.7.6 では 8 秒の記録に 17 秒）。
- **値は速さだけを左右し、正しさ（欠け・壊れ・記録）を左右しない**。小さすぎれば受信が細切れに止まって速さが落ち、それでも溢れれば
  overrun として記録される。

**API（事実として返す）**: `frame_link.StreamBuffer`（`FrameLink.stream_buffer(reset_peak=False)`・`Device.stream_buffer`）

| 項目 | 意味 |
|---|---|
| `capacity_bytes` | 溜める上限（呼び手が渡した値）。`None` = 上限なし（UDP・シリアル） |
| `used_bytes` | 今の未読の量 |
| `peak_bytes` | 測り始めからの最大（`LaStream` は流れの始めに測り直す） |
| `full_count` | 上限に達して受信を止めた回数 |
| `full_s` | 止めていた時間の合計（秒。止めている最中の分を含む） |

`LaStream.stats().link_buffer`（回数・時間はこの流れの分）を、`probe_la.la_stream`・`RecordingStream.status`・記録の `stream_stop`・
testpoint の `stream` が `link_buffer` として返す（USB の機器では `None`）。リングの使用量・帯域のモニタ（別の担当）と同じく
「容量・今の量・最大」の並びにした（名前は、そちらの決まりに合わせて変えてよい）。

**試験**（`host/tests/test_stream_backpressure.py`、ループバックの UDP と TCP。ハードウェア不要）:
- 読まない消費者: 未読が上限ちょうどで止まり、送り手（止まる `send`）の送れた量が 0.5 秒増えない（TCP の窓が閉じた）。読み始めると 32 MB が全部・順に届く。
- 端から端: PL の役（20 MB/s でリング 1 MB に書き、溢れたら overrun を立てて止める）と中継の役（リングから読んで止まる `sendall`）を、
  本物の `EthLink`・`LinkTransport`・`DeepAnalyzer.stream`・`LaStream.chunks` と 8 MB/s の消費者でつないだ: overrun が立ち、
  届いたサンプルは欠けも壊れも無く、PL が書いた分と同数。未読の最大は上限以下、中継は `sendall` で止まった。
- 上限を外すと（受信を止めない）、未読は 32 MB・8 MB まで増え、端から端の試験は overrun が立たずに落ちる（直す前の振る舞いの再現）。
- 上限の引数を省くと TypeError、0 以下は ValueError。止めて待っている受信のスレッドも close で 2 秒以内に終わる。

**実機での確かめ方**（未実施。PYNQ を使う担当と時間を分ける）:
1. `Session.open_eth("<家の LAN のアドレス>")` で開き、`DeepAnalyzer(s.device).stream(rle=False, rate_hz=...)` を、消費側でわざと遅らせて
   （毎サンプル変化する信号の `transitions()`、または `time.sleep`）10 秒流す。
2. PC のプロセスのメモリ（psutil の RSS）が 上限 8 MB + 受信バッファ 8 MB + 数十 MB 程度で止まり、増え続けないこと。
3. `stats().link_buffer` の `peak_bytes ≤ capacity_bytes`、`full_count ≥ 1`。`stats().overrun = True`（リングが溢れた）。
4. 届いたサンプルに飛びが無い（`StreamFormatError` なし）、止めてから出し切りまでの時間が 1.7.6 の 17 秒より大きく縮むこと。
5. 消費側が付いていける速さ（変化点の少ない信号）では `full_count` が 0 か少なく、速さが 1.7.6 の 2 と同じ（92〜94 MB/s・overrun なし）こと。

| ゼロコピー、見出し / 4 KB | 10.9〜11.1 ms | 約 6.2〜6.6 ms（44〜47 %） | 21〜28 % |
| ゼロコピー、見出し / 4 KB、16 B ずらす | 12.4〜12.6 ms | 約 6.0〜6.6 ms | 29〜44 % |
| 普通の `send`（複写） | 11.7 ms | 約 8.4 ms（52.5 %） | 25 % |

- 事実: 送り手の user は 0.01〜0.08 ms/MB（送るだけで中身に触れない）。送り手の時間は出どころ（`mem`・`ring`）によらない。
- 事実: CPU1 の残り（約 2 割）は動いている中継が使っていた。中継を止めた場合の速さは測っていない（中継は止めない条件にした）。
- **測っていない**（1.7.5 の 3 の残り）: ゼロコピーの道にした中継の読み取りスレッド（MMIO だけになる）の CPU0 の時間、完了通知の遅れ、
  リングの余裕。中継を変えないと測れない。導出の見込み: いまの中継（50 MB/s）は CPU0 で約 17〜19 ms/MB（1.7.2）のうち DDR の読みと複写が
  約 6〜7.5 ms/MB。ゼロコピーではそれが無くなり、CPU0 は softirq 約 4〜5 ms/MB + MMIO・回る作りの約 2〜3 ms/MB（1.7.2 の推測の内訳）になる
  （**推測**）。

**判断の材料**:
- 1.7.4 の推測（予約のページを `vm_insert_pages` で写すと `MSG_ZEROCOPY` が通り、copied が 0、参照の数えが戻る）は、PL が書いていない状態で
  事実になった。速さは利用者空間のメモリからのゼロコピーと同じで、1 本で 87〜93 MB/s（いまの中継の 50 MB/s の約 1.8 倍）。
- ただし 4 KB ごとの見出しのままでは 70 MB/s 前後で、1.7.5 のとおり、かたまりを大きくする変更と組で要る。
- 製品に入れるなら要るもの（1.7.4・1.7.5 から、今回の事実で足したもの）:
  1. **ビルドと据え付け**: この PYNQ のビルドの木では素直に作れない（上の「ビルドの事実」）。`build.sh` の手順を据え付けの道具
     （`fprobe_gw pynq install`）に入れるか、この版のカーネル専用の `.ko` を作って置くか。カーネルを替えたら作り直し。
     起動時の読み込み（`/etc/modules-load.d` 等。起動の設定を変えるので利用者の承認が要る）。
  2. **中継**: リングを `/dev/fprobe_ring` から写して `MSG_ZEROCOPY` で送る道。`LA_CONSUMED`・`EV_CONSUMED` は完了通知でだけ進める
     （呼び出しごとのリングの終わりの位置を順に覚える）。copied・`ENOBUFS` を数え、copied が 1 回でも出たら記録してゼロコピーをやめる。
     モジュールが無い・写せないときは今の複写の道で動き、どちらの道かを記録と状態に出す。
  3. **見出しの置き場所**: 見出しは利用者空間の別のバッファから iovec で渡した（今回の試験の形）。ゼロコピーでは見出しのページも
     完了通知まで NIC が読みうるので、見出しのバッファも完了通知まで書き換えない作り（リングと同じく、使い回しは完了の後）が要る（導出）。
  4. **かたまりを大きく**: PS 直読みの道の見出しを 64 KB（4096 拍）以上ごとに。ホストの `STREAM_SEG_MAX_BEATS`（256）の検査を変える。
     リングの終わりをまたぐかたまりは 2 つに分ける（iovec を 2 つにするか、見出しを分ける）。
  5. **まだ確かめていないこと**: PL が書いている最中のゼロコピーの中身の正しさ（実際のストリームで、ホストの番号と中身の検査を通す）、
     完了通知の遅れとリングの余裕、2 本の TCP の価値（今回はばらつきで言えない）。
- 後始末: `rmmod` した（`lsmod` は `zocl`・`uio_pdrv_genirq` だけ、`/dev/fprobe_ring` は消えた）。試験の置き場所（`/tmp/zcmod`・`/tmp/zcbench`、
  ビルドの木の写し）は名前で消した。中継は `systemctl is-active fprobe-relay` = active のまま（止めていない）。

#### 1.7.9 ゼロコピーの中継（実装と実際の流れの実測。2026-11-02）

利用者の方針（2026-11-02）: ゼロコピーの導入を基本方針として進める。段取り: 起動時の読み込みはしない。手で読み込んだ（`insmod`）ときだけ速い道。

**作り**（`host/pynq/fprobe-relay/`。1.7.8 の「製品に入れるなら要るもの」の 2〜4）:
- 起動のとき `/dev/fprobe_ring` があり、それが写すデバイスツリーのノード（`fprobe_ring`、ただ 1 つ・`reg` 1 組）が深いバッファ
  （`/etc/fprobe/mem`）と同じ番地から始まって含むなら、深いバッファの全体を写す（`relay_ringmap_region_ok`）。無い・合わない・写せないときは
  今の複写の道で、理由を journal に出す。TCP のホストがつないだとき、写せていて `SO_ZEROCOPY` が立てば、そのつながりはゼロコピーの道。
- ゼロコピーの道（`relay.h` の `relay_zc`。OS に依存しない部分を `relay.c` に置き、PC で試験する）は主のスレッド（送る CPU）が受け持つ。
  読み取りスレッドからは、`g_tcp` の受け渡し（5 → 4）で深いバッファの状態（`g_ps`・`g_rd`）を受け取る。読み取りスレッドは PL のフレーム
  （CONTROL・DAP の応答）だけを見る。
- かたまり: 見出しは記述の表（2048 行）の行に置き、中身はリングのページ（`/dev/fprobe_ring` の写し）を指す iovec。かたまりの中身は最大
  4096 拍（64 KB）で、リングの終わりをまたぐものは 2 つに分ける。1 回の `sendmsg(MSG_ZEROCOPY)` に最大 256 KB・iovec 64 個。
  かたまりは「4096 拍溜まった・溜まり始めて 1 ms・書き込みが止まった」のどれかで出す（下の「溜めない版」の実測が理由。1 ms はホストの
  読みの間隔 50 ms・64 KB より十分短い）。複写の道・UDP の道・PL の窓経由の流れのかたまりは今のまま（256 拍）。
- **正しさの条件（1.7.4）の実装**:
  - `STREAM_BEATS` は今の道と同じく渡す前に書く。`LA_CONSUMED`・`EV_CONSUMED` は、流れの前から順に、かたまりの全バイトを運んだ呼び出しの
    完了通知がそろった所までだけ書く（解放してよい位置 = 完了を待つ最も古い呼び出しの始まり）。書く直前に `STREAM_EPOCH` を読み直し、
    新しい流れが始まっていたら古い位置を書かない。
  - 見出しの行は解放の後にだけ使い回す（完了通知まで書き換えない）。
  - 完了通知の copied（`SO_EE_CODE_ZEROCOPY_COPIED`）を数え（呼び出しの数とバイト数）、1 回でも出たら、journal に記録してゼロコピーを
    やめる: まだ送っていない残りは `/dev/mem` の写し（キャッシュなし）から写して普通に送り、出した分の完了を待ち切ってから、そのつながりの
    続きを今の複写の道に渡す。中継を起動し直すまでゼロコピーは使わない（`zc_state = stopped_copied`）。
  - `ENOBUFS`・`EAGAIN` は数え、同じバイトを次に送る。つながりが終わったら、完了を待たずに解放したことにする（複写の道で `tcp_ring` の
    残りを捨てるのと同じ）。
  - UDP のデータグラムで出しかけたかたまりの残り・トリガ取り込みの読み出し（版 3）は、写して普通に送る（順番は今の道と同じ）。
- **使う側が見える事実**: どちらの道かと数えを、journal（つながりの始まりと終わり、copied のとき）と、PC の問い合わせ（UDP の
  `RELAY_CH_STATUS` = 0x41。`EthLink.relay_status()`・`Device.relay_status()`）に出す。`LaStream` は出し切った後の値を
  `StreamStats.relay`（`probe_la.la_stream` の `relay`）に入れる。値: `zc_state`（none・ready・stopped_copied・unusable）・`tcp_path`
  （none・copy・zerocopy・zerocopy_draining）・呼び出し・完了・copied（数とバイト）・ENOBUFS・EAGAIN・完了までの時間（合計・数・最大）・
  完了を待つ呼び出しの数（今・最大）・渡して CONSUMED に返していない拍（ロジアナ・イベントの今・最大）・表や呼び出しの上限に当たった回数。
  判定はしない（数だけ）。
- ホストの検査: `STREAM_SEG_MAX_BEATS` を 256 → 4096 にした（`fprobe_gw/csr/fprobe_map.py`。作る側ごとの上限は、PL と複写の道が
  `STREAM_PL_CHUNK_BEATS` = 256、ゼロコピーの道が `RELAY_ZC_CHUNK_MAX` = 4096）。`SegmentSplitter` は生成物の値を使うので、コードは変えていない。
- 深いバッファの段 B（欠けを記録して続ける。la-deep-fast §12）との統合: 欠けの位置は拍の通し番号と CSR の `gaps`・`gap_last_beat` で
  決まり（`GapPlacer`）、かたまりの境・大きさには依らない。`host/tests/test_la_stream_gaps.py` の流れの試験を、かたまり 1〜256 拍と
  1〜4096 拍の両方で回す。中継は欠けの記録（イベントの種類 19）を、ほかのイベントと同じくイベントのリングから送る（中継は種類を見ない）。

**試験**（PC、ハードウェア不要）: `host/tests/test_pynq_relay_zc.py`（28 件）。PL の模型は CONSUMED が許す所まで新しい拍を書き続け、
ソケットの模型は `MSG_ZEROCOPY` の呼び出しの番地だけを覚えて、中身は完了通知を返す直前に読む（NIC が後で DMA で読むのと同じ順）。
CONSUMED が早すぎれば、読む前に PL が上書きしてホストの検査で落ちる。確かめたこと: 完了の後にだけ CONSUMED が進む、順不同の完了は前から
そろった所まで、リングの終わり（ロジアナ・イベント）で 2 つに分ける、リングを何周もする長い流れ（途中までの送り・遅れた完了・イベント混じり）
で中身と番号がそろう、copied で写す道に切り替え（以後 `MSG_ZEROCOPY` を使わない、写した残りはキャッシュなしの写しから、出した分の完了の後に
複写の道へ渡し、続きが欠けずにつながる）、新しい流れに古い位置を書かない、トリガ取り込みの読み出し、UDP の残り、表の上限、
デバイスツリーの照合、状態の返事の形がホストの解読と同じ。今の試験（`test_pynq_relay.py`・`test_pynq_relay_ps.py`）は変えずに通る。

**実際の流れの実測**（事実。PYNQ-Z2、PL は fw72 = `fprobe_pynq_deep` のまま・書いていない。PC は Windows 11・設定は変えていない）:

  一定 = 0x71C7）。そのため中身の検査は、(1) ホストの見出しの番号の検査（`SegmentSplitter`・`LaStream`）、(2) 全サンプルが一定の値と同じか、

- 事実: copied（パケットの盗み見）で、ゼロコピーをやめて複写の道に戻り、流れは欠けずに続いた。盗み見を使う人がいると、中継を起動し直すまで

- 起動時に読み込むなら要ること（推測と導出）: (1) 中継はモジュールを起動のときだけ探すので、モジュールの読み込みを中継の起動より前にする
  （`/etc/modules-load.d` は `systemd-modules-load.service` で、`fprobe-relay.service` の `After=` に足す。または中継が後から探す作り）。

## 2. 変数のライブ観測（DAP サンプラ）

### 2.1 いまの作り（事実）

- 1 か所ごと: TAR 書き（同じ 1 か所・1 語なら借りた最初だけ）→ DRW 読み × n（ポスト: 語 i の値は i+1 回目の DRW で返り、最後の語は RDBUFF）→ CTRL/STAT（STICKYERR なら最後の語を出さない）（`dap_sampler.vhd:7-11, 415-419, 459-479`）。
- 1 か所 1 語の定常は 3 転送（DRW・RDBUFF・CTRL/STAT）。SWD 10.03 MHz で 14.4 µs = 69 kHz（b17 設計書 §4 の表。導出）。実機の記録は、XIAO で 64 ビットの変数 1 つを毎秒 16,000 巡回・誤り 0（backlog B17。SWD の速さの記録は無い）。
- JTAG: AP の読みは SWD と同じくポストで返し、DP の読み（RDBUFF 以外）は続けて RDBUFF をスキャンする（`jtag_phy.vhd:27-30`）。JTAG の ACK は OK/FAULT が同じ値（`jtag_phy.vhd:31`）で、**FAULT は ACK に出ない**。DRW（40 TCK）+ IR 切り替え + RDBUFF（40）+ CTRL/STAT（2 スキャン 80）+ IR 切り替え ≈ 180 TCK（stop-precision 2 章の 220 TCK から TAR の 40 を除いた値。導出）。20 MHz で 9 µs + FPGA の 1 転送あたり 約 11 sys 周期 → **約 100〜110 kHz**（performance-limits 1 章の「約 110 kHz」。導出で、実測は無い）。
- TCK・SWCLK の上限: JTAG sys/5 = 20 MHz、SWD sys/4 = 25 MHz（performance-limits 1 章）。JTAG を sys/4 にする変更は stop-precision 3.1、sys/2（ODDR）は同 3.8。
- 時刻: サンプラの語の時刻は「値が返った周期」（`event_collector.vhd:133-142` の `smp_time <= time_count`、`dap_sampler.vhd:461, 476` の emit）。読んだ時点（対象のバスの読み）ではない。

### 2.2 1 語を読み続ける速さの理論の下限

| | 1 語あたりの最小 | 理由 | 25 MHz | 50 MHz |
|---|---|---|---|---|
| SWD | **1 転送 = 46 ビット**（要求 8・ターン 1・ACK 3・データ 32・パリティ 1・ターン 1）+ `idle_cycles` | 同じ番地の DRW を続けて読むと、各 DRW の応答が 1 つ前の DRW の値を返す（ポスト）。RDBUFF は流れの終わりに 1 回だけ。**誤りの確認も 1 転送の中に入る**: SW-DP では、AP の読みがバスの誤りになると STICKYERR が立ち、その後の AP の転送の ACK が FAULT になる。だから「次の DRW の ACK が OK」= 1 つ前の値は正しい（ADIv5 の SW-DP の規定。**節番号と、対象ごとの振る舞いは要確認**） | 1.84 µs = **543 kHz** | 0.92 µs = **1.09 MHz** |
| JTAG | **1 スキャン = 40 TCK**（DR 35 ビット + TAP の遷移）。チェーンの BYPASS の装置 1 つにつき +1 | APACC の DRW のスキャンを続けると、各スキャンの Capture-DR が 1 つ前の値を返す。IR の切り替えは要らない。**ただし FAULT は ACK に出ない**ので、誤りの確認は CTRL/STAT を読むしかない（DPACC への IR 切り替え 2 回 + 1 スキャン = 約 60 TCK。導出、チェーンに他の装置が無いとき。2026-11-02 に訂正: 初版の「2 スキャン = 約 100 TCK」は stop-precision §3.6 の前の作り。§3.6 の後は CTRL/STAT をポストの DP の読み 1 スキャンで取る） | 1.6 µs = **625 kHz**（確認なし） | 0.8 µs = **1.25 MHz**（確認なし） |
| JTAG（K 語に 1 回確認） | 40 + 60 / K TCK（導出。2026-11-02 に 40 + 100 / K から訂正）。cocotb で数えた値（2.7。JTAG-DP + BYPASS で DR 41・IR 15 TCK）: K = 1 で 112 TCK / 語、K = 16 で 45.4 TCK / 語 | 2.3、2.7（L1 で実装済み。CSR `sampler.check`） | K = 16 で 43.75 TCK = 約 570 kHz（BYPASS のあるチェーンの 45.4 TCK なら約 550 kHz） | 約 1.14 MHz（同 約 1.10 MHz） |

いまとの比: SWD 25 MHz で 3 転送 → 1 転送（約 3 倍）、JTAG 20 MHz の約 110 kHz → 25 MHz・K = 16 で約 570 kHz（約 5 倍）。どれも導出で、
FPGA の転送の間の空き（下）を含まない。実機（L2）では測っていない。

ほかの下限:
- FPGA の転送の間の空き: いまは 1 転送あたり 約 11 sys 周期（stop-precision 2 章）。次の転送の要求を、前の応答を処理する間に用意しておけば 0〜1 周期にできる（stop-precision 3.6 の先読みと同じ作り替え）。25 MHz の SWD で 11 周期は 1 転送の 6 %。
- 対象の AP の遅れ: 次の転送の要求までに AHB の読みが終わらなければ WAIT（再試行）。SWD 50 MHz で、ACK の後から次の要求の ACK まで 約 0.9 µs あり、100 MHz のバスなら 90 周期（導出）。フラッシュの待ち・周辺のブリッジ・バスの取り合いでは WAIT が出うる。WAIT は今どおり再試行し、回数を数える（判定しない）。
- 線と対象の上限（2026-11-02 に訂正。初版は「Pi 2B は JTAG 20.1 MHz で誤りなし」）: Pi 2B は Primer から 20.1 MHz で 8 組のうち 7 組が食い違い 0、
  1 組は 1024 語の読みの途中で DAP の誤りとして返った（`2026-10-23-jtag-tdo-sample-design.md`:34-35、performance-limits §1）。PYNQ の JA からは、
  継いだ 60 cm のジャンパ線で 4 MHz でも 1 万回に数回化けたが、原因は線（長さと継ぎ目）で、継ぎ目の無い短い線にした後は 4 MHz 1 万回 × 3 回・
  2 万回の 1・4・10 MHz で失敗 0（`docs/boards/pynq-z2.md` の JA の駆動の節）。10 MHz より上の PYNQ → Pi の転送の誤りは測っていない
  （25 MHz は IDCODE のスキャン 10/10 だけ。TAP だけで DAP の転送ではない。stop-precision §6）。SWD の対象（STM32F4・nRF・RP2040）の上限は測っていない。
- 非干渉: 1 MHz の読みは、100 MHz のバスの 1 % の周期を取る（導出）。対象の挙動への影響は performance-limits 2.9 の試験で測る（この文書では作らない）。

### 2.3 誤りの確認の置き方（JTAG）— 情報を捨てず、仮定を入れない

- JTAG では、語ごとに CTRL/STAT を読むと 1 語 180 TCK、K 語に 1 回なら 40 + 100/K（初版の値。stop-precision §3.6 の後は語ごとで 100 TCK、
  K 語に 1 回なら 40 + 60/K。導出、チェーンに他の装置が無いとき。cocotb で数えた値は 2.7 の表）。
- 正しさの規則: **確認が通るまで、その K 語は出さない**（FPGA の中に K 語を溜める）。確認で STICKYERR が立っていたら、前の確認から後の K 語を「誤りの区間」として出す（値は出さず、区間の時刻と語数を事実として出す）。黙って捨てない・正しくない値を出さない。
- 時刻は語ごとに持つ（溜める間も、各語の窓（2.5）はそのまま）。遅れるのは「出す時点」だけ。
- K は**使う側が明示する引数**（既定の暗黙の値にしない。CLAUDE.md）。今の動き（語ごと = K = 1 と同じ）を残す。停止の見張り（halt-watch）は今どおり語ごと（halt-watch §3.4 で巡回ごとの確認を取りやめた理由 = 最悪の遅れが悪くなる、はそのまま当てはまる）。
- STICKYERR が立っている間に MEM-AP が後の AP の読みを実行するか捨てるかは、ADIv5 の規定を**要確認**。どちらでも、上の規則（区間をまるごと誤りとする）は正しい。
- SWD はこの仕組みが要らない（2.2 の FAULT が次の ACK に出る）。

### 2.4 複数の変数を読むときの巡回

| 並び | SWD の最小 | JTAG の最小 | いま（SWD） |
|---|---|---|---|
| 離れた番地 N か所 × 1 語 | 1 か所 **2 転送**（TAR 書き + DRW 読み。前のか所の値は、このか所の DRW で返る。前のか所の誤りは、この TAR 書き（AP の転送）の ACK に FAULT で出る） | 1 か所 **80 TCK**（stop-precision 3.5 と同じ。TAR 書きのスキャンが前の DRW の値を返す）+ 2.3 の確認 | 1 か所 4 転送（TAR・DRW・RDBUFF・CTRL/STAT。halt-watch 設計書 :121、b17 §4） |
| 連続する n 語（1 KB の中） | 1 + n 転送（自動加算。実装済み） | 40 × (1 + n) TCK + 確認 | 1 + n + 2 転送 |

- 例（導出）: 8 か所 × 1 語、SWD 25 MHz: 16 転送 = 29.4 µs/巡回 = 各変数 34 kHz（いまの 10 MHz・32 転送は 6.5 kHz）。
- 巡回は表の順に、全か所を毎回読む（今どおり）。変数ごとに読む頻度を変えたいときは、使う側が表に同じか所を複数回書く（本体は重みを決めない）。
- 巡回の最後のか所の値は、次の巡回の最初の DRW で返る（巡回をまたいだポスト）。巡回の間に線をホストに渡すとき（遅延の戻し）は、渡す前に RDBUFF で回収する（今どおり）。
- 停止の見張り（同じ回路）との関係: stop-precision 3.6 は「巡回を先読みの作りにする」を、見張りの最悪の遅れを悪くしない条件で設計する。この文書の要件（同じ番地の連続読み・SWD の FAULT による確認・JTAG の K 語の確認・読みの窓）は、その作り替えに**流量の型**として入れる（同じファイル `dap_sampler.vhd` なので、3.6 と同じ作業で作る。別々に作らない）。

### 2.5 読んだ値の時刻の正しさ（サンプラの窓）

- 事実: いまの時刻は値が返った周期で、対象のバスで読んだ時点より **1 転送分以上後**（ポストの値は次の転送で返る。最後の語は RDBUFF・CTRL/STAT の後に出す = `dap_sampler.vhd:467-476`）。
- 対象のバスで読んだ時点が入る区間（導出。FPGA が線を駆動しているので、端は FPGA の時刻で正確に分かる）:
  - JTAG: 始まり = 要求のスキャンの Update-DR（AP の転送が始まる）、終わり = 値を返したスキャンの Capture-DR。続けて読むなら幅は数 TCK（Update-DR → Run-Test/Idle → Select-DR → Capture-DR）。WAIT で再試行したら、終わりは OK を返したスキャンの Capture-DR に延びる。
  - SWD: 始まり = 要求の転送の ACK の後（**SW-DP が AP の読みを始める時点は ADIv5 で要確認**。確かめるまでは、安全側に要求の転送の始まりを使う）、終わり = 値を返した転送の ACK の前（間に合わなければ WAIT になるので、OK の ACK の時点で値は揃っている）。
  - 対象の中の DAP のクロックからバスのクロックへの受け渡しの遅れは、この区間の中に入る（区間の端は線の上の出来事なので）。
- 変える: サンプラの語のイベントに、**窓の両端**（または、ある端と幅）を FPGA の時刻で載せる。1 件 16 B に収まらなければ、新しい種類のイベントにする（両端を落とさない）。区間の幅は事実として出し、中央の値などの推定を本体で選ばない（使う側が選ぶ）。
- 時刻の表全体（他の源と並べた遅れ・不確かさの付け方）は `2026-11-01-time-accuracy-design.md` に置く。この節は、その表のサンプラの行の定義になる（食い違えば利用者に確かめる）。
- 確かめ方（実機）: 対象のサイクルカウンタ（Cortex-M の DWT_CYCCNT・Cortex-A の PMCCNTR 等の、対象の時計で一定に進む値）を読み続け、読んだ値と FPGA の時刻の窓の組を集める。直線で当てはめたとき、**直線がすべての窓を通る**ことを確かめる（通らない窓があれば窓の定義が誤り）。値の飛び（WAIT の再試行）も窓の幅に出ることを確かめる。

### 2.6 帯域との関係

- 1 語 16 B のイベント（1.6）で、1 MHz なら 16 MB/s、8 か所 × 34 kHz なら 4.4 MB/s（導出）。深いバッファの構成では TCP の流れに乗るので、1 章の上限の中で足りる。
- 深いバッファの無い構成（`fprobe_pynq`・`fprobe_pynq_cap`）のイベントの道（窓経由。約 10〜15 MB/s）での上限は**要確認**。
- ホストの Python でのイベントの解読の速さ（1 秒に何百万件か）は測っていない。1.3.2 の受信をネイティブにするなら、解読も同じ所で配列（numpy）にする。

### 2.7 L1 の実装（2026-11-02。cocotb まで、L2 の実機はしていない）

time-accuracy の段階 S2（R6: サンプラの窓）と同じ作業で、同じ `dap_sampler.vhd` を作り替えた（time-accuracy §12）。

**直す前の測り**（同じ番地 1 語を間を空けずに読む定常。直す前の RTL = この作業の前のコミットを取り出して cocotb で測った。
チェーンは JTAG-DP + BYPASS で DR 41・IR 15 TCK）:

| | 直す前 | 直した後 K = 1（既定・停止の見張り） | 直した後 K = 16 |
|---|---|---|---|
| SWD | 1 転送 = 46 SWCLK / 語 | 同じ | （K は使わない） |
| JTAG | DR 2 スキャン（DRW・CTRL/STAT）+ IR 2 回 = 112 TCK / 語 | 同じ（112） | DR 17 スキャン + IR 2 回 / 16 語 = 45.4 TCK / 語 |

2.1 の「3 転送・180 TCK」は stop-precision §3.6（先読み）の前の値で、§3.6 の後は上の「直す前」になっていた（SWD はすでに
1 転送。JTAG は語ごとの確認で 2 スキャン + IR 2 回）。L1 で残っていたのは JTAG の K 語の確認と窓の時刻。

**直したこと**:
- CSR `sampler.check`: `words` = K（RW、リセット値 1 = 語ごと）、`max` = K の上限（RO。構成の generic `SAMPLER_CHECK_MAX`、
  PYNQ の構成は 16、ほかは 1）。K は使う側が明示する（ホスト `Sampler.configure(..., check_words=K)`。既定の 1 は今までの動き。
  上限を超える K は断る）。停止の見張り（`halt_watch`）は借りるたびに 1 を書く（stop-precision §3.6 の判断どおり）。
- JTAG: K 回の DRW の読みごとに CTRL/STAT を 1 スキャン読み（その取り込みが直前の語の値）、次のスキャンの取り込み（CTRL/STAT）で
  確かめるまで値を出さない。値は回路の `buf`（CHECK_MAX 語。分散 RAM）に溜め、確認が通ったら番地の順に 1 周期 1 件で出す
  （`event_collector` は 1 周期 1 語。サンプラが線を持つ間は DAP・割り込み書き込みの件が無いので詰まらない）。か所をまたいでも、
  巡回をまたいでも数える。線を渡す前・休む前の回収は、CTRL/STAT（まだなら）と RDBUFF で確かめる。
- STICKYERR（JTAG）・FAULT・WAIT の使い切り・線の不調・切断で出さなかった読みは、種類 18（誤りの区間: 最初の読みの点・
  見つけた転送の点・最初の番号・読みの数・ACK・STICKYERR・線を失った）。黙って捨てない（出した語 + 区間の読みの数 = 受理された
  DRW の読みの数を cocotb で確かめた）。SWD でも K = 1 の JTAG でも、出さなかった読みは同じ件になる（前は数えるだけだった）。
- 窓の時刻（2.5）: 語の時刻 = 読みに行った DRW の点、窓の後端 = 次のサンプラの件の点（time-accuracy §12.1）。2.5 の「両端を
  新しい種類に載せる」案は、128 ビットのまま両端を件の並びに載せる形にした（値を返した転送が次の語の読みなら件は増えない）。

**API・記録の変化**: `Sampler.configure` の `check_words`・`check_words_max()`。イベント 7 の意味・17・18（time-accuracy §12.2）。
CSR `sampler.errors` は今どおり（中止した回数）。

**確かめたこと**（cocotb、`dap_sampler_tb`）: `jtag_k_word_check_reads_one_scan_per_word`（上の表の TCK・スキャンの数、値が全部
番地の順に出る）、`jtag_k_word_check_turns_an_error_into_an_interval_without_values`（K = 3・誤りの番地を含む 2 か所: 誤りの区間に
STICKYERR、正しい値だけが出る、保存則、区間の始めと見つけた点が線上の点、errors = 区間の数）、既存の試験すべて（K = 1 の転送の
並び・停止の見張りの TCK 数は変わらない）。

**残したこと**: L2（実機: Nucleo F401 の DWT_CYCCNT を読み続けて窓の直線、PYNQ の PS の PJTAG での JTAG の K）。SWD の速さの上限
（2.2 の 25 MHz の対象側）。K > 1 で値が出るまでの遅れ（K 語分 + 確認の 2 スキャン）は事実として件の時刻から読めるが、API で
まとめて返してはいない。確認した件を出す間（最大 2 × CHECK_MAX + 1 周期）に次の応答が来ない、は 1 転送の最短（160 周期）から
導いた条件で、RTL の assert で確かめる（CHECK_MAX ≤ 64）。

## 3. SWO

### 3.1 いまの作り（事実）

- 受信は sys（100 MHz）で、1 ビットの周期数 `divisor` ≥ 4 → **最高 25 Mbit/s**（UART = NRZ と Manchester の両方。`swo_receiver.vhd:14-20`、`swo_manchester_rx.vhd:13-15`）。
- NRZ（UART 8N1）: 開始ビットの後は数えるだけなので、送り手との速さのずれが 10 ビットで溜まる。divisor = 4 で −1〜+5 %（`swo_receiver.vhd:15-17`）。分周は整数（`dap_cmd_swo.vhd:156`）。
- Manchester: ビットごとに同期し直す。入力の 2 段の同期化で時刻が ±1 周期ずれ、T = 4 が最小。**実用の上限は divisor = 5〜6（20〜16.7 Mbit/s）**（`swo_receiver.vhd:18-19`）。
- 出口: SWO のバイトは 2 か所に出る。(1) SWO のチャンネル（`frame_mux` の CH 2 → PYNQ では窓 → 中継の UDP のまとめ送り）。(2) イベント（1 バイト 16 B、`event_collector.vhd:93-96, 150-158`。SWO は USB の口が溢れても記録には残す）。

### 3.2 受信の理論の上限

| 律速 | NRZ | Manchester | 根拠 |
|---|---|---|---|
| 取り込みのクロック f（ビットあたり最低 4 回） | f / 4 | f / 4（余裕なし）、実用 f / 5〜6 | 3.1 の回路の条件 |
| f = sys 100 MHz（いま） | 25 Mbit/s | 25（実用 16.7〜20） | 事実 |
| f = 300 MHz（`fprobe_pynq_cap` の `cap_clk` と同じ領域） | 75 | 75（実用 50〜60） | 導出。**受信回路だけの上限**で、目標ではない（下の注） |
| f = 端子の過サンプリング（ISERDES。la-resolution の取り込みの領域） | 端子の上限まで（受信の論理は律速でなくなる） | 同 | la-resolution に従う |
| 端子・線（PYNQ の 3.3 V シングルエンド） | 最小のパルス = 1 ビット。13.3 ns まで確実なら **約 75 Mbit/s** | 最小のパルス = 半ビット。13.3 ns まで確実なら **約 37 Mbit/s** | la-stream-ps-direct 10.17（FPGA の出力 → ジャンパ線 → FPGA の入力のループバックで、13.3 ns 以上は幅が一致、10 ns は ±1 サンプル）。**対象の SWO の出力の駆動とは別の測定**なので、目安 |
| 対象 | TRACECLKIN / (ACPR + 1)。STM32F401 は HCLK 84 MHz（Manchester は 1 ビットに 2 回の変化なので、端子の上限が先に来る） | 同 | 対象の参考資料。**実測なし** |

- NRZ の分周のずれ: 速い領域にすると divisor の刻みが細かくなる。さらに、整数でなく小数の分周（位相の累算器）にすれば、送り手の速さにちょうど合わせられる（ホストが指定した速さで決まる。推定ではない）。
- Manchester の速い側の上限は、受信の回路より**端子（約 37 Mbit/s の目安）**で決まる見込み（**推測**。対象の駆動で変わる）。
- **目標と回路の上限の書き分け**（2026-11-02。performance-limits §7 の (10)・§2.8 に合わせた）: 目標は端子の目安で、NRZ 約 75 Mbit/s、
  Manchester 約 37 Mbit/s。上の表の「300 MHz で Manchester 実用 50〜60」は受信回路だけを見た上限（導出）で、端子の目安 37 を超えるので、
  300 MHz の領域に移しても Manchester は端子で先に止まる見込み（推測）。NRZ は回路の上限と端子の目安がどちらも 75 で一致する。
  どちらの数字も実機の SWO（対象の出力）では測っていない（端子の目安はループバックの実測からの目安、回路の上限は導出）。

### 3.3 下流の上限（受信より先に当たる）

- 事実: SWO の 1 バイトが 16 B のイベント 1 件（1.6）。
- 導出: 25 Mbit/s の NRZ（10 ビット/バイト）で 2.5 M バイト/秒 = 40 MB/s のイベント、Manchester で最大 約 3.1 M バイト/秒 = 50 MB/s。**いまの最高速度で流し続けると、イベントだけで垂れ流しの壁（50 MB/s）に当たる**。75 Mbit/s なら 120〜150 MB/s で、1 章の到達点（117.7 MB/s が理論の上限）を超える。
- SWO のチャンネル（CMSIS-DAP の SWO と同じバイト列）は、PYNQ では窓（約 10〜15 MB/s）を通る（la-stream-ps-direct 1 章・10.4）。75 Mbit/s の NRZ は 7.5 MB/s で、窓には収まる（導出）。PC の UDP の破棄（10.3）はパケット数で効くので、まとめ送りの大きさで決まる（要確認）。

### 3.4 変えること

1. **SWO のバイトを詰めたイベント（無損失）**: 1 件に最大 4 バイトと、各バイトの時刻（先頭のバイトの 48 ビットの時刻 + 2〜4 バイト目の差、各 12 ビット・sys 周期）。差が 12 ビットに収まらなければ、そこで次の件にする（時刻を丸めない・捨てない）。1 バイト 16 B → 4 B（連続して受けたとき）。新しい種類のイベントにし、古い種類 5 は残す（ホストの解読は両方を読む）。UART のバイト（種類 3・4）も同じ形にできる。
2. **受信を速い領域に移す**: Manchester・NRZ の受信器を、la-resolution が決める取り込みの速い領域（いまある `cap_clk` 300 MHz の領域、または ISERDES の領域）に置き、バイトを sys に受け渡す。ボード非依存のコアは「受信器のクロック」を抽象の口で受け、ケイパビリティで最高速度を申告する（Primer 等は sys のまま）。
3. **NRZ の小数の分周**（3.2）。応答の「実際のボーレート」は今どおり返す（`dap_cmd_swo.vhd:156`）。
- 順番: 1（帯域。受信を速くしても下流で詰まるので先）→ 2 → 3。

### 3.5 詰めたイベントの形（3.4 の 1。段階 S1、2026-11-01 実装）

**形**（128 ビットのまま。time-accuracy §6 の判断 2）: 種類 13 = UART 受信、14 = UART 送信、15 = SWO（古い種類 3・4・5 を詰めた形。
古い種類はそのまま残る）。

| ビット | 中身 |
|---|---|
| [47:0] | 先頭のバイトの時刻 |
| [79:48] | バイト。i 番目（0〜3）が [48+8i+7 : 48+8i] |
| [115:80] | 2〜4 バイト目の、前のバイトからの時刻の差（各 12 ビット・時刻の刻み）。i 番目のバイトの差が [80+12(i−1)+11 : 80+12(i−1)] |
| [117:116] | バイトの数 − 1 |
| [119:118] | 0 |
| [127:120] | 種類 |

使わないバイト・差の欄は 0。回路: `rtl/core/event_byte_pack.vhd`（源ごとに 1 つ）を `event_collector`（generic `BYTE_PACK`、`fprobe_core` の
`EVENT_BYTE_PACK`）が 3 つ持つ。出す優先順は古い形のバイトと同じ位置（DAP・割り込み・サンプラの後、補助の前）。

**各バイトの時刻の意味は古い形と同じ**（1 段レジスタで受けた周期。time-accuracy §2.1 の 11・12・13 のいまの意味）。よって時刻の意味の
申告は増やさない。R3・R4 で時刻の意味を変えるときは、古い形・詰めた形の両方に同じ TIMING の申告が効く（そのとき差は源の時刻の差に
なるので、`event_byte_pack` の差の数え方も変える。下の「差の数え方」）。

**申告**: ケイパビリティ FEATURES の bit14 `EVENT_BYTE_PACK`（ホスト `Capabilities.event_byte_pack`）。PYNQ の 3 構成で有効、Primer・
Nano 9K 等は無効（古い形のまま）。ホストの解読（`fprobe.events.decode_events`）は種類の番号で両方を読み、詰めた件はバイトごとの古い形
（種類 3・4・5）の件に戻すので、解読より後（`resolve`・記録・VCD・画面・MCP）は変わらない。古い形のデバイスも今どおり動く。
記録の番号（書いた数・`events_read` の `first`・`next`）は 16 バイトの記録の件数で数える（`EventLog.read` が返した記録の件数を
`records` に残す。詰めた記録は 1〜4 件のイベントになるので、返したイベントの数で番号を進めると食い違う）。

**件を切る条件**（どれも「そうしないと詰められない」という事実。経験則の閾値は無い）:

1. 4 バイト溜まった（欄が尽きた）。その次の周期に出口へ移す。
2. 最後のバイトから 2^12 = 4096 周期たった。この周期以後に来るバイトの差は 12 ビット（最大 4095）に収まらず、もう誰も入れない。
   「新しいバイトの差が収まらない」も、その周期にはこの条件が成り立っているので同じ条件になる。差がちょうど 4095 のバイトは同じ件に入る
   （試験 `a_gap_of_4095_joins_and_4096_starts_a_new_record`）。

**溜める上限**（上の条件から決まる。別の閾値は置かない）: 4 バイト。時間は先頭のバイトから最大 3 × 4095 + 4096 = 16381 周期
（100 MHz で 163.8 µs）と、出口（1 周期 1 件）を待つ間。続けて流れる区間（バイトの間隔 < 4096 周期）では 3 バイト分の間隔 + 1 周期。
「時間軸の上で、送らないと後ろのイベントの順が崩れる」は条件にしない: イベントの流れはいまも源をまたいで時刻順ではなく（バイト・サンプラ・
観測は保持して DAP の後に出し、観測の時刻はエンジンが付けたもの）、記録（`recording`）は時刻で並べ、ポストされた読みの対応付けは DAP の
線の種類だけの順を使う。これを条件にすると、DAP の転送のたびに件を切ることになり詰められない。同じ源の中のバイトの順は保つ。
「時刻 T までの出来事を全部読んだ」とみなしたい使い手は、上の 163.8 µs（+ 出口の待ち）だけ後まで読む必要がある。

**欠けの数え方**: 切るべき件が出口の空きを待つ間に来たバイトは捨てて `events.lost` に数える（古い形の「保持が出る前に次が来た」と同じ）。
記録を止めた（`events.control` = 0）周期に溜めていたバイトも記録に残らないので数える（古い形の保持の 1 件は、止めたときに数えずに捨てる。
今と同じで変えていない）。

**差の数え方**: `time_count` は毎周期ちょうど 1 増える（`timebase` の約束。同じ `rst` で戻る）ので、48 ビットの引き算の代わりに、最後の
バイトからの周期数（4096 で止まる 13 ビットのカウンタ）で数える（sys を上げたときの遅い経路を作らない）。試験の基準モデルは時刻の差そのもの
で比べる。

**帯域の見込み**（導出。実機は未測定）: 続けて流れる区間（バイトの間隔 < 4096 周期 = 毎秒 24.4 k バイト以上）では 1 件 4 バイト = 4 B/バイト。

| SWO | 古い形（16 B/バイト） | 詰めた形（4 B/バイト） |
|---|---|---|
| 25 Mbit/s NRZ（2.5 M バイト/秒） | 40 MB/s | **10 MB/s** |
| 25 Mbit/s Manchester（最大 3.125 M バイト/秒） | 50 MB/s | **12.5 MB/s** |
| 75 Mbit/s NRZ（3.4 の 2 の後） | 120 MB/s | 30 MB/s |
| 間隔 ≥ 4096 周期（< 24.4 k バイト/秒） | < 0.39 MB/s | 同じ（1 件 1 バイト） |

UART（種類 13・14）も同じ。3 つの源が同時に最高速度でも、イベントは 1 周期 1 件（16 B × 100 MHz）の出口の中に十分収まる。

**確かめたこと**（cocotb・ホスト）: `event_byte_pack_tb`（基準モデルと毎周期一致、出口が詰まる・記録を止める場合の欠けの数、
解読で全バイト・全時刻が元のまま、4095 / 4096 の境、1 バイトだけなら 4096 周期後に出る、4 バイトなら待たずに出る）、
`event_collector_pack_tb`（全部の源のランダムな入力で、DAP・割り込みの件は今と同じ周期・同じ語、バイトと時刻は元のまま、保存則）、
`swo_events_tb`（端子 → `swo_receiver` → `event_collector` → 解読。25 Mbit/s の NRZ・Manchester で、古い形と詰めた形の解読が
同じバイト・同じ時刻、36 バイトの連続が 9 件）、`fprobe_core_tb`（構成 `event_byte_pack` で記録の種類 14）、
ホスト `test_events_packed.py`。

## 5. 設計原則との関係

- ヒューリスティックを入れない: 帯域の手はどれも中身を変えない（無損失）。サンプラの K と窓の両端、SWO の時刻の差は事実として出し、推定（窓の中央・誤りの推定）を本体で選ばない。K は使う側が明示する引数。
- 情報を捨てない: 間引きは採らない。誤りの区間・溢れは黙らず記録する（今の overrun・lost と同じ扱い）。
- 移植性: ゼロコピーは PS（Linux）の中継の中だけ、PL は変えない。SWO の速い領域はボードの層の抽象の口とケイパビリティで申告し、Primer は sys のまま同じ PC のソフトで動く。
- 画面は考えない層: 窓・誤りの区間・実際の速さはすべて API が返し、画面は描くだけ。
