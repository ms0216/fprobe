# 画面（UI）のフレームワークの評価

- 日付: 2026-10-18
- 問い: 今の方式（ブラウザの Svelte + TypeScript をデーモンが配る）でよいのか、egui 等のほうがよいのか。
- 方法: 候補ごとに同じデータ・同じ間引き・同じ絵の小さな試作を作り、同じ視点の列（900 フレーム）で測った。
  試作と測り方は `prototypes/ui-bench/`（README）、生の結果は `prototypes/ui-bench/results/`。
- 入力: 画面の要件 G01〜G11（`docs/reports/2026-10-18-gap-analysis.md` §3）、UI/UX の調査
  （`docs/reports/2026-10-17-debug-ui-ux-survey.md` 第 3 部）、今の画面 `host/ui/`、API `host/api/fprobe_api.json`（247 メソッド）。

## 1. 結論

**今の方式（ブラウザ + Svelte/TS、デーモンが配る）を続ける。ただし共通タイムライン（G01）の描画と間引きの置き場所は変える。**

1. 共通タイムラインの密な段（波形・出来事）は **WebGL2** で描く（間引いた画素の状態を毎フレーム小さなテクスチャで送り、
   シェーダで描く）。文字・カーソル・印は Canvas 2D（または DOM）の重ね。Canvas 2D だけでは縮小した視点で 60 fps を割る。
2. **間引きは画面側（ブラウザの Web Worker）で毎フレーム**行い、デーモンは「見えている範囲の生の変化点・出来事」と
   「縮小用の事前計算の要約（段の索引）」を**バイナリのタイル**で返す。今の `la.view` / `recording.waveform` /
   `recording.density` のように 1 フレームごとにデーモンへ頼む方式は、測ると 1 回 34〜366 ms で、対話の速さに届かない。
3. egui は描画が最速（ネイティブ）。それでもブラウザを採る理由は、時間軸以外のビューの多く（ソース・逆アセンブル・
   メモリ・変数の木・ログ/端末・解読表）が文字の多い画面で、ブラウザには成熟した部品（Monaco・xterm.js・仮想化した表）
   と標準の操作（選択とコピー・検索）があるから（egui では自作になる）。差は小さく、§6.1 の条件で見直す。PySide6・Dear PyGui は遠隔で見られない（LAN・タブレット・
   AI と同じ画面）ため、要件を満たせない。Tauri・Electron は「同じ Web の画面の包み」として後から足せる（今は要らない）。

## 2. 測定

### 2.1 条件

- データ: 16 ch・合計 9,885,374 変化点（1 秒、10 ns のタイムベース。バースト入り）、出来事 8 段 × 12.5 万 = 999,377 件。
- 視点: 拡大（1 s → 10 µs）300 + 移動（1 ms の窓）300 + 縮小（1 ms → 1 s）300 フレーム（前に慣らし 60）。
- 絵: 1600 × 800、描く幅 1500 画素。波形 16 段（線・縁・変化の塊）、出来事 8 段（疎なら区間とラベル、密なら画素ごとの
  件数の棒）、名前・軸・ラベル。
- 間引き: チャンネルごとの変化点の表を画素の境界で引く（今の `la.Waveform.view` と同じ定義）。JS・Rust・numpy の
  3 つの実装の結果は突き合わせの和で一致した（`check` の 4 視点）。
- 作業 = 間引き + 描画の命令。フレーム間隔 = 垂直同期を外した実力（`vsync` 付きは画面 100 Hz での実際）。
  プロセスの最大 = 子プロセス（ブラウザ・WebView2）を含む作業セットの合計の最大。
- PC: Ryzen 5 2600、16 GB、Radeon RX 580、Windows 11、Edge 155 / Chrome 155、表示 100 Hz。

読み方:

- **60 fps（16.7 ms）を p95 で保てたもの**: WebGL2（ブラウザ・Tauri）、egui（ネイティブ・WASM）、PySide6・Dear PyGui
  （ぎりぎり）。**Canvas 2D は保てない**（縮小した視点で p95 20〜25 ms。Path2D に数万の矩形を積むと GPU のラスタで
  最大 286 ms 止まる）。重い部分は縮小した視点（画素ごとに数千の変化点、出来事の段が全部「密」）。
- 1 回目の測定では PySide6 が p95 18.0 / p99 20.3、Dear PyGui が p95 17.7 / p99 21.0 で 60 fps を割った（実行ごとの揺れ）。
  Python は 1 本のスレッドで間引き・塗り・UI のイベントを回すため、PySide6 は作業だけで p50 8.5 ms を使い、ほかの
  ビュー（ソース・メモリ・端末）を同時に更新する余裕が小さい。
- egui ネイティブは全候補で最速（p99 9.7 ms、メモリ 249 MB）。WebGL2 との差は p99 で約 2 倍だが、どちらも 60 fps に
  収まる。ブラウザのメモリはデータ（約 95 MB の float64）よりブラウザ本体の分が大きい。
- Tauri（WebView2）は Edge と同じ（同じ描画エンジン）。メモリは Edge より 100 MB ほど小さい。

### 2.3 間引きだけの時間（描画なし、1 フレーム 16 ch × 1500 画素 + 出来事 8 段）

| 実装 | 波形 p50 / p95 / p99 | 出来事の段 p50 / p95 |
|---|---|---|
| Rust（ネイティブ） | 0.21 / 3.8 / 5.3 | 0.01 / 0.96 |
| JS（Node 24 / V8。ブラウザも同じエンジン） | 2.2 / 9.8 / 11.9 | 0.08 / 2.2 |
| numpy | 2.3 / 6.7 / 8.3 | 0.36 / 1.6 |

最初の JS は 1 画素ごとに配列全体を二分探索して p50 4.4 ms だった。前の画素の位置から指数探索に変えて半分になった
（3 実装とも同じ改良を入れた）。間引きは 1 フレームの予算の大きな部分を使うので、ブラウザでは描画のスレッドから
Web Worker に分ける。

### 2.4 間引きをデーモンでする場合（今の API の方式）

| 方式 | 1 回の時間 | 返事の大きさ |
|---|---|---|
| 今の `la.Waveform.view`（純 Python・bisect、16 ch × 1500 画素） | p50 34 ms / max 48 ms | 16 × 1500 文字 |
| 今の `Recording.density`（画素ごとの SQLite の COUNT）1 段 | p50 47 ms / max 68 ms | 1500 個の数 |
| 同 8 段 | p50 366 ms / max 524 ms | — |
| numpy で間引き + JSON-RPC over WebSocket（ループバック、JSON） | p50 10.9 / p95 48.3 / max 104 ms | p50 59 KB / max 599 KB |
| 同（バイナリのメッセージ） | p50 7.2 / p95 17.1 / max 49.5 ms | p50 42 KB / max 294 KB |

（`server/current_api.py` は本体のコードを読み取りで呼んだ。100 万件を記録に入れるのに 7.3 秒。）

- 今の画面の波形（`host/ui/src/lib/waveform.ts`）は、表示を動かすたびに `la.view` を頼み、返るまで次を待つ。捕捉が
  8192 サンプル程度なら速いが、記録の大きさ（1000 万変化点・100 万件）では 1 回 34〜366 ms で、拡大・移動が
  3〜30 fps に落ちる。
- numpy にしてバイナリで返しても、ループバックで p95 17 ms。LAN の往復と帯域（1 フレーム 40〜300 KB）が加わると
  毎フレーム頼む方式では 60 fps にならない。**毎フレームの間引きは画面側**に置き、デーモンは間引きの材料（タイル）を返す。

## 4. 推奨の構成

```
デーモン（Python, host/fprobe/api/daemon.py）                 画面（ブラウザ, host/ui）
 ├ 記録（recording.py / recording_long.py）                    ├ 状態の層（Svelte の store。lib/*.ts は Svelte に依らない）
 │   生データ: チャンネルごとの変化点・出来事（SQLite）        │   ui 状態 = デーモンの「画面の状態」の写し
 │   要約: 段ごとの件数・波形の要約（事前計算の索引）          ├ データの層（Web Worker）
 ├ タイルの API（新設、バイナリ）                              │   タイルのキャッシュ（範囲 × 細かさ）
 │   timeline.tiles(t0, t1, streams, level)                     │   毎フレームの間引き（core と同じアルゴリズム）
 │     → 細かい: 範囲の生の変化点・出来事                        ├ 描画の層
 │     → 粗い:   要約の段（画素より細かい粒度）                  │   WebGL2: 波形・出来事の段・密度（テクスチャ + シェーダ）
 ├ 画面の状態の API（新設）                                     │   Canvas 2D / DOM: 文字・カーソル 3 種・印・ラベル
 │   ui.state.get/set + 通知 ui.state                           └ パネル（ドッキング）: ソース・メモリ・端末・RTOS・解読表…
 │   （視点・カーソル・開いている段・選択。人・AI・別の窓が共有）
 └ MCP（mcp_server.py）: 同じ ui.state を AI に公開
```

- **描画の層**: G01 の段は 1 枚の WebGL2 のキャンバスにまとめる（段ごとに要素を作らない）。間引いた結果（段 × 画素の
  状態・件数）をテクスチャで送り、シェーダで線・塊・棒を描く。測定で毎フレームの GPU の作業は一定で、データの量に
  依らない。文字（名前・時刻・ラベル）は 2D の重ね。表・木・端末・ソースは DOM（Svelte）のまま。
- **間引きの置き場所**:
  - 毎フレームの間引き = 画面（Web Worker）。キャッシュしたタイルから引くので、拡大・移動の間はデーモンを待たない。
  - タイルの用意 = デーモン。見えている範囲の生データが一定（例 200 万変化点）以下なら生の変化点、超えるなら要約の段
    （`recording_long` の事前計算の索引を一般化。粗い段を画素より細かい粒度で返す）。範囲の前後に余白を付けて先読み。
  - 遠隔（LAN・タブレット）でも、往復は視点が大きく動いたときのタイルの取得だけになる。
  - 1 つのデータを描画と AI が同じ定義で使えるよう、間引きの定義（§2.1）は Python（`la.Waveform`）と TS で同じに保ち、
    試験で突き合わせる（試作の `check` と同じ方法）。
- **状態の層と API**: 視点（t0・t1）、カーソル 3 種（選択・マウス・基準点）、開いている段、選んだ出来事を
  **デーモンが持つ「画面の状態」**とし、画面はその写しを持つ。AI（MCP）・人・別の窓・別の PC が同じ状態を読み書きし、
  通知で揃う（UI/UX の調査 C-9・C-10）。URL にも視点とカーソルを載せ、リンクで同じ視点を開ける（C-2）。
  調停（`arbiter.py`）は「状態を変える操作」が対象で、画面の状態は誰でも変えられ、誰が変えたかを操作の記録に残す。
- **ドッキング・複数の窓**: パネルの配置はドッキングのライブラリ（候補 dockview。フレームワークに依らない TS）。
  別の窓に出したパネルは、デーモンの画面の状態で同期する（同じ PC でも別の PC でも同じ仕組み）。
- **配布**: `npm run build` の出力をデーモンの wheel に同梱し、利用者は Node を入れない。窓のアプリとして配る必要が
  出たら Tauri で包む（画面のコードは変えない。WebView2 で Edge と同じ性能を確認）。

## 5. 移行の段取り

1. **タイルの API**（デーモン）: `timeline.tiles` をバイナリ（WebSocket のバイナリのメッセージ、または同じポートの
   HTTP）で返す。生の変化点・出来事と要約の段。API の仕様（`fprobe_api.json`）に足し、Python の試験で生データと
   要約が一致することを確かめる。今の `la.view` / `recording.waveform` / `recording.density` は AI と互換のために残す。
2. **間引きの TS 版**（`host/ui/src/lib/`、Svelte に依らない）: 試作の `web/core.js` を TS にし、vitest で Python の
   `la.Waveform.view` と同じ結果になることを試験する（試験用のデータを Python で作って突き合わせる）。Web Worker で動かす。
3. **WebGL2 の時間軸の部品**: 試作の `webglRenderer` を元に、段の種類（波形・区間・点・数値のグラフ・密度）を
   シェーダの描き分けで足す。今の `WaveformView.svelte` をこの部品に置き換える（捕捉の表示も同じ部品で）。
   WebGL2 が使えないとき（古い端末）は Canvas 2D（fillRect 版）に落とし、遅いことを表示する。
4. **画面の状態の API**: `ui.state.get/set` と通知、MCP に同じ道具。視点・カーソル・段の構成を載せる。URL との対応。
5. **G01 の段を足す**: DAP・UART/SWO/RTT・RTOS・割り込み・変数・電圧・印・AI と人の操作（API は既にある）。
   カーソル 3 種、縮図（ミニマップ）、キーボードで次/前の出来事。
6. **ドッキング**と他のビュー（G02〜G11）を、時刻でつなぐ規則（1 回クリック = 選ぶ、ダブルクリック = タイムラインへ）
   で足していく。
7. （必要になったら）Tauri で包む。Linux の WebKitGTK の性能をそのとき測る。

1〜3 で今の画面の作り直しは要らない（波形のビューの差し替えだけ）。

1〜3 は実装した（2026-10-18。`docs/superpowers/specs/2026-10-18-timeline-tiles-design.md`。本体の部品で
WebGL2 + Worker が垂直同期なし p99 13.1 ms・最大 15.6 ms、垂直同期ありで 16.7 ms を超えたフレーム 0）。

4 も実装した（2026-10-18）: デーモンの `ui.state.get` / `ui.state.set`（kind read。一時停止中も変えられ、誰が変えたかは
操作の記録に残る）と通知 `ui.state`（origin = 変えた窓の印）、MCP の `ui_state_get` / `ui_state_set`。画面は
`lib/screen.ts`（ScreenSync）で視点・カーソル 3 種・開いている段・選んだ出来事・呼び出し履歴のフレームを送り・当て、
URL のハッシュ（`#v=capture:t0-t1&sel=…&ref=…&rows=…&ev=stream@t&f=…`）にも載せる。

## 6. 捨てた案と理由

- **egui / eframe**: 性能は最良（ネイティブ p99 9.7 ms、メモリ 249 MB）で、同じコードが WASM でも動いた（p99 18.7 ms）。
  採らない理由は、文字の多いビュー（ソース・逆アセンブル・メモリ・変数の木・ログ/端末・解読表）が画面の大半で、
  ブラウザには成熟した部品（Monaco・xterm.js・仮想化した表）と標準の操作（文字の選択とコピー・Ctrl+F の検索）が
  あること。egui ではこれらの多くを自作する。性能の差は時間軸の 1 つのビューにしか効かず、WebGL2 でも 60 fps に収まる。
  - 2026-10-18 の見直し（利用者の指摘）: 当初挙げた「Rust の導入・作り直し」「日本語入力」「AI が DOM を読めない」は
    理由にならない。画面は別のプロセスで API を叩くだけなので言語は設計思想に反さず、作り直しは 1637 行。日本語入力は
    組み込みの開発ではほぼ使わず、弱いのは WASM 版だけ（ネイティブは IME 対応）。AI は MCP と `ui.state` で画面の
    状態を読むので、画面を読み取る必要は無い。遠隔もネイティブ版をネットワーク越しにつなげばよく、差はタブレットだけ。

### 6.1 egui に見直す条件

- 実際の記録（ロジアナ 128 MB・長時間の記録）で、WebGL2 の時間軸が 60 fps を p95 で割るとき。
- そのときは、時間軸だけをネイティブ（egui）にして他のビューはブラウザのまま、という分け方も比べる。
- 見直し後の点（重み: 描画 30・保守 15・文字のビュー 10・ドッキング 10・配布 10・遠隔 10・大きなデータの余裕 10・
  既存の資産 5）: ブラウザ 425、egui 390。
- **PySide6（Qt）+ pyqtgraph / numpy**: Python だけで書け、ドッキングは最も成熟。しかし遠隔で見られない（LAN・
  タブレット・AI と同じ画面）。60 fps は p95 でぎりぎり（測定ごとに 16〜18 ms）で、1 本のスレッドに余裕がない。
  依存が大きい（入れたもので 656 MB。この PC では長いパスのため作業ディレクトリの venv に入らなかった）。
  pyqtgraph も同じ QPainter の上なので、numpy で塗る今回の形（ImageItem と同じ道）より速くはならない。
- **Dear PyGui**: 軽い（6 MB）が、遠隔不可、部品が少ない（表・木・豊かな文字）、p95 16〜18 ms。
- **Canvas 2D だけ**: 縮小した視点で p95 20〜25 ms（fillRect）、Path2D では最大 286 ms の止まり。文字と重ねにだけ使う。
- **間引きを毎フレームデーモンで**: 今の実装で 34〜366 ms、numpy + バイナリでもループバックで p95 17 ms（§2.4）。
- **Electron**: 画面は Chrome と同じ性能だが、1 つごとに Chromium を同梱して重い。包む必要が出たら Tauri と比べて選ぶ
  （Linux で描画を揃えたいなら Electron が有利）。今は包まない。
- **Slint・Flutter**（測っていない）: 新しい言語（Slint の DSL / Dart）を入れ、Web 版はキャンバス描画で egui と同じ
  弱点がある。今の資産を生かせず、性能で WebGL2 を上回る理由も見当たらない。
- **WebGPU**: WebGL2 で足りた（GPU の作業はデータ量に依らない形）。対応の広さで WebGL2 を選ぶ。

## 7. 確かめられなかった点

- **macOS・Linux** での測定（Linux の WebKitGTK 上の Tauri、Safari、Firefox）。今回は Windows 11 の Edge / Chrome /
  WebView2 だけ。
- **タブレット**（iPad・Android）の性能と、タッチでの拡大・移動。egui の WASM のタッチ・IME も試していない。
- **LAN 越し**の往復（ネットワークの設定を変えず、別の PC も使わなかった）。タイルの取得の時間は「ループバックの値 +
  往復 + 大きさ / 帯域」の見積もりにとどまる。
- **より大きな記録**（1 億変化点以上・数時間）。1 フレームの間引きは O(画素 × log N) で増え方は小さいが、画面に
  全データを持てないため、タイルの方式（§4）は試作していない（部品の時間だけ測った）。
- **ドッキングのライブラリ**（dockview・egui_dock・ImGui のドッキング）と複数の窓の試作。評価は文献と経験による。
- **高い DPI**（倍率 1.5〜2）。全候補を倍率 1 で測った。WebGL2 は画素の数に比例してシェーダの作業が増える。
- Web Worker に間引きを移したときの効果（試作は描画と同じスレッドで間引いた。作業の時間は間引きを含む）。
- 実行ごとの揺れ: 同じ試作で p95・p99 が 1〜3 ms 動いた（PySide6・Dear PyGui は 1 回目に 60 fps を割り、2 回目に
  収まった）。各 1〜2 回の測定で、統計的な比較はしていない。
- egui の WASM は wasm-opt をかけていない（9.1 MB）。
