# PYNQ-Z2: 記録のストリームを PS の DDR から直接 PC へ流す（設計）

2026-10-29。状態: 案（利用者の確認待ち）。上位の検討: `2026-10-29-performance-limits-study.md` §2.1（連続記録の長さ = PC への帯域。最優先）。

## 1. 目的と、なぜ

- 連続して記録できる長さは、PC へ流せる帯域で決まる。PYNQ は今 約 2 MB/s（生の 16 ch で約 1 MS/s）で、全項目の中でいちばん細い。
  2 MB/s を超えると、制御の往復が 0.4〜1.4 秒に延びる（`docs/boards/pynq-z2.md`）。
- 今の流れは遠回り: PL がロジアナ・イベントを PS の DDR のリング（0x1E000000、32 MB。Linux の外）に書く → PL がそれを読み戻す →
  1 バイトずつ frame_mux → zynq_frame_link の 1 KB のバッファ → 中継が AXI-Lite で 32 ビットずつ読む（1 語 0.15 µs）→ 512 B の UDP。
  **データはすでに PS 側のメモリにある。** 中継がリングを直接読めば、読み戻しと 1 語ずつの受け渡しが要らなくなる。
- 目標: 帯域の上限は、1 GbE と Cortex-A9 のネットワークの処理（実測して決める。見込み 40〜100 MB/s）。今の 20〜50 倍。

## 2. 範囲

やる:
- PL: リングの「書いた位置」を PS に見せ、PS が「読み終えた位置」を返す口（ストリームを PS が読む方式）。DDR への書き込みの効率化。
- PS の中継: リングを直接読み、TCP で PC へ流す。制御・DAP・UART は今の UDP のまま、別の経路にする（ストリームが制御を詰まらせない）。
  PL からの割り込みで起こす（今の空回りと 1 ms の poll をやめる）。
- PC: ストリームの TCP の受け取り。取りこぼしと位置の連続を、事実として記録する。

やらない:
- Primer の経路（USB のストリームの EP はすでに約 25〜40 MB/s）。本体の口は共通にし、Primer は今のまま。
- ロジアナの取り込みの並列化（検討書 §2.2。別の設計書）。

## 3. 設計

### 3.1 PL: リングの位置を PS とやりとりする

- 深いバッファ（`la_deep_buffer`）は、リングに書いた拍の数（64 ビット、増えるだけ）を出す。PS（中継）は読み終えた拍の数を書く。
  書き手は、未読がリングの大きさを超えそうなら止まり、**止めた事実（あふれた拍の数・時刻）を数える**（今の「未読がリング − 256 拍を超えたら
  止める」の読み手を、PL の読み戻しから PS に替える）。
- 方式は CSR で選ぶ: 今の方式（PL が読み戻して frame_mux へ）と、PS が直接読む方式。ケイパビリティで「PS が読む方式がある」を申告する
  （Primer には無い）。本体の口は「書いた位置・読み終えた位置」だけで、ボードに依らない。
- ロジアナとイベントは今どおり 1 つのリングを分け合う（ロジアナ 15/16・イベント 1/16）。それぞれに位置を持つ。

### 3.2 PL: DDR への書き込みの効率（`axi_mem_port`）

- 今は 128 ビットの拍ごとに 1 回のバースト（16 B）を出し、3 サイクルに 1 回しか受け付けない。PS が読む方式では PL の読み戻しが無いので、
  書き込みが読みで止まることも無くなる。
- 長いバースト（最大 16 拍 × 8 B = 128 B）、AW と W の重ね合わせ、未完了の数を増やす。HP0 の上限は 64 ビット × 100 MHz = 800 MB/s。
  ロジアナの最悪（RLE で 400 MB/s、100 MS/s）を受けられる余裕を持たせる。

### 3.3 PS: 中継（`host/pynq/fprobe-relay`）

- リングを mmap で読む（Linux の外の領域。キャッシュしない普通のメモリとして読む: PL の書き込みとキャッシュの食い違いが起きない。
  まとめ読みが効く）。
- ストリームは TCP（別のポート）で送る。理由: 取りこぼしの再送をカーネルに任せられる（UDP で自前の再送を作らない）。送れた分だけ
  「読み終えた位置」を PL に返すので、PC が遅ければ PL の書き手が止まり、その事実が数えられる（黙って捨てない）。
- 制御・DAP・UART は今の UDP と zynq_frame_link のまま。ストリームと経路が別なので、ストリームが流れていても制御は詰まらない。
- PL からの割り込み（PS の IRQ_F2P、Linux の UIO）で起こす。割り込みのたびに、送るフレームとリングの位置を見る。

### 3.4 PC（`host/fprobe`）

- `eth_link` に、ストリームの TCP の受け取りを足す。受け取った拍の位置（64 ビット）が連続していることを確かめ、飛びやあふれは
  PL の数とともに事実として記録する。デコードは今のストリームの形式（R1 の見出し付きの塊）のまま。
- 受け取りが PC の処理より速い場合に備え、大きなバッファへの `recv_into` で受ける（Python の速さが律速なら、そのことを測って記録する）。

## 4. 測ること（実機）

- 持続の帯域（PL → DDR → 中継 → PC）と、それぞれの段の上限（中継の DDR の読み・TCP の送り・PC の受け取り）。
- ストリームを流しながらの制御の往復（今は 2 MB/s で 0.4〜1.4 秒。目標は流していないときと同じ 約 0.3 ms）。
- あふれの数（PC が遅いとき、正しく数えられること）。

## 5. 試験

- cocotb: `axi_mem_port` の長いバースト・重ね合わせ（AXI のスレーブのモデルで、順番・データ・応答の誤り）。`la_deep_buffer` の位置の
  受け渡し（読み終えた位置で書き手が止まる、あふれを数える）。
- 中継: C の単体試験（偽のメモリと偽の PL の窓で、位置の受け渡しと TCP への書き出し）。
- ホスト: TCP の受け取りの単体試験（位置の連続・飛びの記録）。
- 実機（HIL）: 上の §4。

## 6. 設計原則との関係

- 本体（PL のコア）は「書いた位置・読み終えた位置」の汎用の口だけ。PS の中継は PYNQ の層（`host/pynq`）。Primer は今のまま。
- 取りこぼしとあふれは数えて返す。黙って捨てない。
- ケイパビリティで方式を申告し、PC はそれを見て選ぶ。
