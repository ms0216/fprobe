# 性能を限界まで上げる検討（2026-10-29）

状態: 方針は利用者が承認（2026-10-29）。各項目は、作る前に個別の設計書を書く。対象は全機能の構成（PYNQ-Z2、Zynq-7020 -1）。Primer は面積に余裕が無いので扱わない。

## 0. 評価の軸

目的は「デバッグ対象の挙動を、時系列で正確かつ詳細に解析できること」。人の単発の操作の応答性は重視しない。この目的に要る条件は 5 つ:

| 条件 | 中身 |
|---|---|
| 網羅性（何が見えるか） | 端子・CPU の命令の流れ・変数・OS の出来事・内部トレース |
| 時刻の正しさ | 全情報源を 1 本の時間軸に。情報源ごとの遅れの補正と、残る不確かさの報告。対象側の時計との対応付け |
| 細かさ | サンプリングの周期、時刻の分解能、チャネル数、入力のしきい値 |
| 連続性と長さ | 取りこぼしなく、どれだけ長く連続して取れるか。取りこぼしたら必ず記録する |
| 非干渉性 | 観測が対象を乱さないこと。乱した量を測って記録する |

方法は 2 通りある: 周波数を上げる（律速の経路に FF を入れて詰める）と、並列にする（1 サイクルに複数を扱う・別の速いクロックの領域に分ける・処理を重ねる）。
**本当の限界は周波数ではなく帯域**（端子・内蔵メモリ・DDR・PC への経路）で決まる。並列化はクロックの上限（BUFG 約 464 MHz・Block RAM 約 388 MHz）を越える手段。

## 2. 項目ごとの限界と方法（優先度の順）

### 2.1 連続記録の長さ = PC への帯域（最優先: 今いちばん細い）

- 限界: PYNQ の 1 GbE で 117.7 MB/s（MTU 1500・MSS 1448 の中身。帯域の設計書 `2026-11-01-bandwidth-observation-design.md` :34・:124 の導出。2026-11-02 に「約 110 MB/s」から直した。PC 側の USB の LAN だと 30〜100 MB/s）。
- 方法（並列化・ゼロコピー）:
  1. PL の DMA が、ストリームを PS の DDR のリングに直接書く（AXI HP。今の `axi_mem_port` を、長いバースト・多数の未完了・HP の複数ポートに広げる）。
  2. 中継は、そのリングを mmap で読んでそのまま送る（ゼロコピー）。大きな UDP（ジャンボフレーム）と `sendmmsg` でまとめて送る。
  3. PL からの割り込み（UIO）で起こす（いまは 1 語ずつの空回りと 1 ms の poll）。
  4. 制御を別の経路・優先にする（ストリームが流れていても制御が詰まらない）。
- 見込み: 約 2 MB/s → 数十〜約 100 MB/s（25〜50 倍）。生の 16 ch で 25〜50 MS/s を連続で流せる。RLE ならさらに長い。

### 2.2 ロジアナの細かさ（サンプリング・チャネル数）

- 限界: 端子 1 本あたり HR バンクで 950 Mb/s（ISERDES の DDR 受信、-1。§0.1。2026-11-02 に -2・-3 の値「約 1.25 Gb/s」から直した。§0.1 の下の訂正と同じ）→ 950 MS/s。内蔵の記録は Block RAM の帯域（幅 × 周波数）、DDR は 2.1 の帯域。
- 方法（並列化）:
  1. 取り込みの領域を分ける: ISERDES（DDR）で端子を 4〜8 倍で取り込み、sys の 1 サイクルに 4〜8 サンプルを渡す。
  2. トリガ・エンコーダ（RLE）・フィルタを、1 サイクルに複数サンプルを扱う幅に広げる。
  3. 入力の制約（IOB の FF、入力遅延の制約、チャネル間のずれの測定）を入れる。
  4. チャネル数を増やす（PMOD JB・RPi ヘッダ等、空き端子の数による）。入力のしきい値は基板の仕様に縛られる（3.3 V の CMOS）。
- 見込み: 100 MS/s → 400 MS/s〜1 GS/s（内蔵の記録）。連続記録は 2.1 の帯域で決まるので、RLE が前提。

### 2.3 時刻の正しさと分解能

- 方法:
  1. 情報源ごとの遅れ（取り込みの段数、RLE、DAP の転送のどの時点か、SWO の受信）を表にして補正し、残る不確かさを各イベントに付ける（事実として）。
  2. タイムベースを速い領域に置く（2.2 の取り込みの領域と同じクロック）、または ISERDES の位置で細かい時刻を付ける（部品の上限で約 1.05 ns = 950 Mb/s。la-resolution :48、time-accuracy :83。2026-11-02 に「約 1.25 ns」から直した。いまの `fprobe_pynq_fast` は 800 MS/s = 1.25 ns）。
  3. 必要な入力だけ、キャリーチェーンの TDC（10〜20 ps 級、較正が要る）で 1 ns を下回る時刻。
  4. 対象側の時計との対応付け: SWO / ITM・トレース・ftrace の時刻と、プローブの時間軸を、同期の印と回帰で結ぶ（ボード間の `timesync` と同じ考え方）。
  5. ボード間の同期の実機の数値を測る（いまは記録が無い）。

### 2.4 CPU の命令の流れ（新しい機能）

- PYNQ の ARM（Cortex-A9）は、PTM のトレースを TPIU 経由で PL に出せる（EMIO）。fprobe がそれを取り込み、DDR のリングに記録し、ホストで復号する。CPU の挙動を時系列で最も詳しく表す。
- Pi 2B はトレースの外部出力が無い。チップ内の記録（ETB）を止めた後に読めるかは未確認。
- 規模が大きい（取り込み・記録・PTM の復号）。帯域は 2.1 に依存する。

### 2.5 停止の同時性

- CTI のある SoC: すでに ns 級。
- CTI の無い SoC: FPGA の停止の見張り（実装済み・実機未測定）。さらに縮めるには 2.6（TCK を上げる・余分なサイクルを除く）。

### 2.6 デバッグの口（JTAG / SWD）

- 方法:
  1. JTAG の 1 ビットごとの余分なサイクルを除く（sys/5 → sys/4、20 → 25 MHz）。
  2. 出力を IOB で登録し、クロックを ODDR で出す・PHY を 2 倍の領域で動かす（sys/2 = 50 MHz まで。上限は対象と線）。
  3. 周波数の段を細かくする、または「実際の値」を必ず返して記録する（今日、要求値を書いてしまった）。
  4. 1 パケットに複数のコマンド（DAP_ExecuteCommands）、FPGA の中で次の転送を先に準備する。
- 見込み: 対象しだい（Pi 2B: Primer から 20.1 MHz で 8 組のうち 1 組が DAP の誤り（jtag-tdo-sample :34-35）、PYNQ から 25 MHz で IDCODE のスキャン 10/10（stop-precision §6。TAP だけ）、PYNQ のジャンパ線では 4 MHz でも 1 万回に数回化ける（`docs/boards/pynq-z2.md`））。PC との往復が律速のもの（人の操作）には効かない。

### 2.7 変数のライブ観測

- 方法: TCK を上げる（2.6）。流量を優先する使い方では、誤りの確認を巡回に 1 回にまとめる設定（停止の見張りでは遅れるので使わないが、流量には効く）。JTAG の DP 読みの 2 回目のスキャンを減らす。
- 見込み（2026-11-02 に直した。前は「JTAG 25〜50 MHz で約 150〜280 kHz」で、根拠の式が書かれていなかった）: 同じ番地の 1 語を読み続けるとき、
  誤りの確認を K 語に 1 回にすると 1 語 40 + 100/K TCK、K = 16 で 46.3 TCK = JTAG 25 MHz で約 540 kHz、50 MHz で約 1.08 MHz
  （帯域の設計書 §2.2 :559・§2.3、作業 L1。K は使う側が明示する引数で、S2 で実装済み・統合待ち）。FPGA の転送の間の空き（1 転送 約 11 sys 周期）は含まない導出。
  K = 1（語ごとに確認。いまの既定の動き）は 1 語 約 100 TCK（DRW 40 + IR 2 回 + CTRL/STAT 1 スキャン、stop-precision §3.6 の作り。導出）= 25 MHz で約 250 kHz。
  注: 帯域の設計書の確認の 100 TCK は stop-precision §3.6 の前の作り（CTRL/STAT が 2 スキャン）の値。§3.6 の後（1 スキャン）なら確認は 60 TCK で、
  K = 16 で 43.75 TCK = 25 MHz で約 570 kHz（導出）。帯域の設計書の直しは §7 の「統合の後に直す」。

### 2.8 SWO

- 方法: 取り込みを速い領域・ISERDES の過サンプリングに置く（Manchester の再同期が細かくなる）。
- 見込み（2026-11-02 に「25 → 50 Mbit/s 以上」から直した）: 目標は端子の上限の目安で、NRZ（UART）約 75 Mbit/s、Manchester 約 37 Mbit/s
  （最小のパルスが NRZ は 1 ビット・Manchester は半ビットで、13.3 ns まで確実に見えるループバックの実測から。帯域の設計書 §3.2 :624。
  対象の SWO の出力とは別の測定なので目安）。帯域の設計書の中では、Manchester の受信回路の上限（300 MHz で実用 50〜60、:622）が
  端子の目安 37 を超えており、:628 は端子で決まると書く。この文書は端子の値を目標にする。帯域の設計書の直しは別の担当の統合の後（§7）。帯域は 2.1 に依存する。

### 2.9 非干渉性

- DAP で読み続けたときに対象の挙動がどれだけ変わるか（バスの取り合い）を測る試験を作り、観測のたびに「読んだ回数・時間」を記録に残す。

### 2.10 sys のクロックを上げる

- 律速の経路に FF を入れて詰める。結果はビルド中（§3）。2.2・2.3 で取り込みとタイムベースを別の速い領域に分ければ、sys そのものを上げる必要は小さくなる（上げれば DAP の段・SWO・UART が細かくなる）。

- 注意（2026-10-29）: PYNQ の sys のクロックは 2 か所に書かれている（`fprobe_gw/boards/pynq_z2.py` の `sync_pll` = ケイパビリティの
  申告、`rtl/boards/pynq_z2/pynq_z2_pkg.vhd` の `MMCM_*`・`SYS_CLK_HZ` = 実際の MMCM）。一致は試験
  `tests/test_boards_pynq_z2.py::test_vhdl_package_matches_board_definition` が確かめる（ビルドは確かめない。試しのビルドで片方だけ変えて気づいた）。
  周波数を変えるときは両方を変え、この試験を通す。

## 6. 設計原則との関係（CLAUDE.md。2026-10-29 に確かめた）

- 解析力が最優先（CLAUDE.md の優先順位 1）: この検討の軸と同じ。
- ロジアナを sys で取る判断（M7 の設計書 §3）は「DDR3 と一緒に高速化を検討する」前提の判断で、見直しはその予定どおり。
- ヒューリスティックを入れない: 遅れの補正・TDC の較正は測った値（較正の結果）として持ち、不確かさを一緒に返す。取りこぼしは事実として返す。
  流量を優先する設定などは、使う側が明示する引数にする（暗黙の既定にしない）。
- 移植性: ISERDES・IDELAY・キャリーチェーン・PS の DMA は Xilinx / Zynq 固有。ボードの層のラッパーに置き、本体は「1 サイクルに N サンプル」
  等の抽象の口だけを持つ。ケイパビリティで N・サンプリング周波数を申告し、Primer 等は N = 1 のまま同じ PC のソフトで動く。
  DMA はベンダーの IP を使わず、`axi_mem_port` を広げて自作する。
- 特定のターゲットのための機能を足さない: CPU の命令の流れは、ARM の標準のトレースポート（TRACECLK + TRACEDATA）を取り込む汎用の機能に
  する。PYNQ の PS のトレースを PL に引き込む経路は、ボードの配線として扱う（PJTAG の素通しと同じ）。
- 標準のプロトコル: 1 パケットに複数のコマンドは CMSIS-DAP の DAP_ExecuteCommands。
- 食い違い: CLAUDE.md の「主ターゲット・中心は Tang Primer 20K」は古い。全機能の基準は PYNQ-Z2（`docs/guide/getting-started.md` と、
  利用者の 2026-10-29 の指示）。CLAUDE.md は利用者の了承を得て直した（2026-10-29）。
