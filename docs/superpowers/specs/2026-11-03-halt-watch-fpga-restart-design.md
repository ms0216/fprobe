# 停止の見張り: 再開を FPGA が行い、見落としの窓をなくす（設計）

2026-11-03。状態: 実装済み（模擬で確認。実機は未確認: Pi 2B で主担当が確かめる。§8）。
前の設計: `2026-10-29-halt-watch-design.md`（§3.5・§3.6 の方式を、この文書の回路を持つデバイスでは置き換える）。

## 1. 何が問題か（事実）

今の見張り（§3.6 の方式）は、ホストが全コアの DBGDRCR に再開の要求を書き、FPGA のサンプラが各コアの DBGDSCR を読み続け、
値の一致が「前の標本が止まっていない → 今の標本が止まっている」に**移った**瞬間に発火する。

- 再開の要求が書かれてから、サンプラがそのコアの「走っている値」を初めて読むまでの間に、そのコアが止まると、FPGA から見ると
  「止まっている → 止まっている」で、移った瞬間が無い。値の一致は発火しない（原理的な窓）。
- 実機（fw82）で 20 回中 2 回、この窓に入った（ブレークポイントがすぐ当たった）。回路の印 `unmatched` とホストの DSCR の読みで
  事実として見分け、ホストの方式（5〜7 ms）に落ちた。窓そのものは残っている。
- 窓ができる理由: FPGA は、ホストの書いた再開の要求が**いつ**届いたかを知らない。止まっている標本が、再開の前のもの（まだ止まった
  まま）か、再開の後に止まったものかを、値だけでは区別できない（どちらも DBGDSCR.HALTED = 1、RESTARTED = 1）。

## 2. 方針

**再開の要求を FPGA が書き、その書き込みの後に読んだ標本だけを比べる。** さらに「止まった」の条件に DBGDSCR.RESTARTED を入れる。

Arm の定義（ARMv7 の DBGDSCR、bit1 RESTARTED。ARM DDI 0406C C11.11.20）: RESTARTED は、コアが再開の要求（DBGDRCR.RRQ）を
受けたときに 0 になり、デバッグ状態を出たときに 1 になる。次の再開の要求まで 1 のまま。よって、再開の要求の**後に**読んだ DBGDSCR で:

| HALTED | RESTARTED | 意味（定義から） |
|---|---|---|
| 1 | 0 | 要求を受けたが、まだデバッグ状態を出ていない |
| 0 | 1 | 再開して走っている |
| 1 | 1 | **再開した後に、また止まった** |

（0, 0 はこの手順では起こらない。）再開の要求の**前**に読んだ値は 1, 1（前回の再開から止まったまま）のことがあり、3 行目と区別
できない。FPGA が要求を書き、その後に読んだ標本だけを比べれば、「HALTED = 1 かつ RESTARTED = 1」はそれだけで「再開の後に止まった」
という事実になる。前の標本が走っていた必要は無い（推定ではなく、定義と読みの順の事実）。

読みの順の根拠: 再開の要求の書き込みと DBGDSCR の読みは、同じ DAP・同じ AP の転送で、AP は転送を順に行う（ADIv5）。割り込み書き込みは
要求の DRW の後に CTRL/STAT を読んで誤りを確かめてから線を返し、サンプラはその後に始めたか所の読みしか標本にしない（§3.2）。よって、
門（§3.1）が開いた後の標本は、どれも全コアの再開の要求の後にターゲットのバスで行われた読み。

これで窓は無くなる: 再開の後のどの停止も、止まっている間ずっと（HALTED, RESTARTED）= (1, 1) のまま残るので、サンプラがそのコアを
次に読んだ標本で必ず発火する（once で先に別のコアが発火していれば、その発火で全コアに停止要求が書かれる）。

## 3. 回路

既存の部品をつなぐだけで、専用の部品は作らない（前の設計 §2 と同じ考え）。足すのは 3 つ。どれも停止の見張りに限らない汎用の機能。

### 3.1 値の一致の門と「最初の標本」（`sampler_match`）

CSR `sampler_match.control` に 2 ビットを足す。どちらも既定 0（今までと同じ）。

- **`after_start`**: 1 のとき、`start`（下）を受けるまで標本を比べない（数えず、状態も変えない）。`start` の後の周期の標本から比べる。
  `start` を受けたことは `control.started`（RO）。有効の 0→1 で消える。
- **`first_sample`**: 1 のとき、有効にした後（`after_start` なら門が開いた後）の**その番号の最初の標本**が条件に入っていれば発火する。
  0 なら今までどおり、最初の標本では発火しない（その前を見ていないので「入った」かは分からない）。どちらにするかは使う側が明示して
  選ぶ（暗黙の既定で「最初の標本は入った」とみなさない）。
- `start` は 1 周期のパルス（`start_time` = 門を開けた事実の時刻、§3.2）。`fprobe_core` が割り込み書き込みの「始動の列」の成功で出す。
- 最初の標本で発火したとき: `fire.first` = 1、`prev` = `start_time`（門が無ければ 0）。`prev` は「その番号が条件に入っていなかったと
  分かっている最後の時刻」で、今までの「直前の不一致の標本の時刻」と同じ役。停止の見張りでは、`start_time` = 始動の列の最初の語の
  DRW の線上の点（どのコアも、自分の再開の要求の DRW より後に止まる）。
- `once`・`unmatched`・番号ごとの状態は今までどおり（門の前の標本は印にも入らない）。

### 3.2 割り込み書き込みの「始動の列」（`swd_injector`）

- 今の要求（クロストリガ）は語 0〜`extra` を書く。これに、**ホストの要求で表の語 `first`〜`last` を書く**要求を足す（CSR
  `inject.start`。`go` を 1 にする）。書き方（CSW・TAR・DRW、最後に CTRL/STAT、控えに戻す）・失敗の扱い・語の時刻は今の要求と同じ。
- 待ち: 要求は `pending` として残り、割り込み書き込みが空いたときに始める。クロストリガの要求と同じ周期に来たら、クロストリガを先に
  する（止めるのが優先）。実行中にクロストリガの要求が来たら、今と同じく捨てる（見張りでは、門が開くのは始動の列が終わった後なので、
  始動の列の最中に発火は来ない）。
- 結果（CSR `inject.start_status`）: `pending`（要求してから終わるまで）、`result`（0 成功 / 1 SWD の異常 / 2 未接続）、`written_words`、
  `count`（終わった始動の列の数）。時刻（`start_first_time`・`start_last_time`）: 最初と最後の語の DRW の線上の点（受理されたもの）。
- 今の `xtrig.inject_time`・`inject.first_time` は、**クロストリガの要求**の語の時刻にする（始動の列では変えない。見張りの発火の後の
  停止要求の時刻を、再開の時刻で上書きしないため）。`xtrig.inject_status`（busy・result・ack・count）と `inject.status.written_words` は
  今どおり「最後の要求」（どちらの種類でも）。
- 表は 8 語（語 0 + 表の 7 語。`WORDS`）。見張りでは停止要求に語 0〜n−1、再開の要求に表の n〜2n−1 を使う: **4 コアまで**。

### 3.3 つなぎ（`fprobe_core`）

- 始動の列が終わり、`result` = 0（成功）のとき、`sampler_match.start` を 1 周期出す（`start_time` = 始動の列の最初の語の時刻）。
  失敗なら出さない（門は閉じたまま: 見張りは発火しない。ホストが結果を読んで扱う）。
- ケイパビリティ FEATURES bit18 `WATCH_START`: この経路（3.1〜3.3）がある。値の一致と割り込み書き込みの両方がある構成で申告する。

## 4. ホスト

`fprobe.halt_watch.HaltWatch`:
- `configure(..., restart_writes=[(DBGDRCR_n, RRQ | CSE), ...])`: デバイスが `WATCH_START` を申告していれば、表の後ろに再開の要求を
  入れ、`inject.start` の first・last を設定する（`restarts` が真になる）。申告が無ければ今までどおり（`restart_writes` は使わない）。
- `arm_and_restart()`（`restarts` のときだけ）: 値の一致を 0→1（once・`after_start`・`first_sample`）→ サンプラを動かす → 始動の列を要求。
  `restart_status()`: 始動の列の結果。
- `poll`・`status` に `fire_first` を足す。

`ArmACores.resume`（全コアを再開し、見張りがあるとき）:
- `restarts` なら: レジスタを戻す（ホスト）→ 時刻を記録 → `arm_and_restart` → 始動の列が終わるのを待つ（失敗・時間切れなら見張りを外し、
  受理された語の数を事実として例外にする）→ ホストが全コアの DSCR を読み、RESTARTED でデバッグ状態を出たのを確かめる（今と同じ
  `_confirm_restarted`）。以後 `wait_event` は FPGA の状態だけを読む（JTAG を使わない。再開の後のどの停止も発火するので、§3.6 の
  見逃しの確定は要らない）。
- 申告が無いデバイス（古い回路）は、§3.6 の方式のまま。

停止の報告（`StopReport`）: method は今と同じ "sequential"、bound は呼び出し側が渡した値（測っていなければ None）。basis に事実を書く:
FPGA が全コアの再開の要求を書いたこと（語の数）、止まったのを見つけたコアの DBGDSCR が HALTED = RESTARTED = 1 だったこと、
それがそのコアの再開の後の最初の読みだったか（`fire.first`）。`last_wait["fpga"]` に `restarted_by_fpga`・`fire_first`・
`t_restart_first`・`t_restart_last` を足す。

## 5. 時間（見積もりではなく、変わる点だけ）

- 再開の要求の書き込みは FPGA の割り込み書き込み 1 回（4 語）: ホストの 1 回の往復（前の作り）と同じく、全コアの要求は
  1 コア 2 転送（TAR・DRW）ずつ続けて書かれる。
- 門は始動の列が終わった周期に開き、サンプラはその後すぐ次のか所を読む。ホストの往復を待たない。
- ホストの往復: 再開は CSR の書き 3 回 + 結果の読み 1 回以上 + DSCR の確かめ 1 回（前の作り: 見張りの arm 2 回 + 再開と DSCR の 1 回）。
  どの往復の間もコアの停止は窓に入らない（再開はその前に FPGA が済ませ、見張りも始まっている）。

## 6. 安全

- 始動の列は、ホストが `go` を書いたときだけ動く。クロストリガの経路とは別（源ではない）。
- ホストは、コアを個別に止める・ステップする前に見張りを外す（今と同じ）。外した後に `go` を書かない。
- 始動の列が失敗したら門は開かない（見張りは発火しない）。ホストは受理された語の数を報告し、受理されなかった語のコアは再開されて
  いない（parked）として扱う。

## 7. 試験

- `sampler_match`（cocotb）: 門の前の標本は比べない・`started`・`first_sample` で最初の標本が発火・`fire.first` と `prev = start_time`・
  `first_sample` = 0 なら最初の標本で発火しない（今まで）・once・門の後の不一致 → 一致の普通の発火。乱数の試験のモデルに門を足す。
- `swd_injector`（cocotb、dap_harness）: 始動の列が表の first〜last を書く・クロストリガの要求と同時なら後になる・結果と時刻。
- 端から端（`fprobe_core`、SWD のモデルに 4 コア（JTAG のモデルでの同じ試験は未。書き方は割り込み書き込みの既存の JTAG の試験と同じ経路）。DBGDRCR に RRQ が書かれたら RESTARTED を 0 にし、デバッグ状態を出す
  （HALTED = 0・RESTARTED = 1）。「すぐ止まるコア」は再開と同時に HALTED = 1・RESTARTED = 1 になる）:
  - 旧い作り（ホストが再開を書く・門なし）: すぐ止まるコアでは発火しない（窓。`unmatched` も 0）。
  - 新しい作り（FPGA が再開を書く・門・RESTARTED を条件に）: 同じコアで発火し、全コアに停止要求が書かれる。
  - 再開が遅いコア（数回の読みで HALTED = 1・RESTARTED = 0）では発火しない。
- ホスト: 申告の有無で道が切り替わる、`restarts` のとき `wait_event` が JTAG を使わない、始動の列の失敗の扱い、報告の事実。

## 8. 実機で確かめること（主担当）

- PYNQ-Z2（この回路の `fprobe_pynq_deep`）→ Pi 2B、25 MHz。`host/tests/linux_halt/hw/test_hw.py` の一式（HaltSkew を含む）と、
  ブレークポイントをすぐ当てる試し（再開の直後に止まる）を数十回。FPGA の方式に落ちず（`last_wait["by"] == "fpga"`）、報告の basis に
  `fire.first` の有無が出ること。
- 前の作り（fw82）で 1 回あった 358.8 ms（記録なし）は、この変更とは別に、記録を取って調べる。

## 9. 決めていないこと・確かめていないこと

- Arm の定義（RESTARTED の意味）は ARMv7 の文書の記述で、Cortex-A7 の実機でそのとおりかはこの回路で初めて当てにする（前の作りの
  `_confirm_restarted` も同じ定義を使っている）。
- 表は 8 語で、見張りは 4 コアまで。5 コア以上は `WORDS` と CSR の幅を広げる別の変更。
