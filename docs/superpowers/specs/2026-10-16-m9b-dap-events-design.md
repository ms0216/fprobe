# M9 第 2 段: DAP トランザクションのイベント記録 設計

- 日付: 2026-10-16
- 親: `2026-10-15-fprobe-architecture-design.md` §4.2（TransactionMonitor）・§4.5（EventFabric）、
  `2026-10-16-m8-ddr3-design.md` §5（深いバッファ）、`docs/reference/prior-art-fpga-probes.md`（Glasgow の analyzer）

## 1. ゴールと完了条件

| 完了条件 | 測り方 |
|---|---|
| SWD / JTAG の線上の全転送（要求・ACK・番地・データ）を、ロジアナと同じタイムベースの時刻付きで外部メモリに記録できる | シミュレーション + HIL（pyOCD の読み書きが記録に全部現れる） |
| ロジアナの深いバッファと同時に動かせ、ホストが同じ時間軸で突き合わせられる | HIL: トリガの時刻とイベントの時刻の差が SWD の 1 転送以内 |
| 記録できなかったイベントがあれば申告する（黙って捨てない） | シミュレーション |

## 2. 構成

```
dap_processor → swd_injector → debug_port
      └─ dap_monitor（既存: SELECT・CSW・TAR を追い、DRW の番地を求める）
            └→ イベント（128 ビット）→ 小さな FIFO ─┐
la_encoder → 拍 ─────────────────────────────┴→ 合流（ロジアナ優先）→ 非同期 FIFO（既存）→ la_mem_writer
                                                          ロジアナの拍 → リング A（容量の 15/16）
                                                          イベント     → リング B（容量の 1/16 = 8 MB = 52 万件）
```

- **イベント（128 ビット = 1 拍）**: [47:0] 時刻（タイムベース、転送の完了時）、[79:48] 番地（DRW は TAR から求めた
  メモリの番地、それ以外はレジスタの番地 A[3:2]）、[111:80] データ（書き込み値 / 線上の読み値。AP の読みは
  ポストされた値のまま）、[114:112] ACK、[118:115] 要求（APnDP, RnW, A[3:2]）、[119] パリティ異常、
  [127:120] 種類（1 = ホストの転送、2 = クロストリガの割り込み書き込み、以後追加）。
  線上の生の記録とし、ポストされた読みの対応付けはホストが行う（プロトコルアナライザと同じ考え方）。
- **合流**: ロジアナの拍は止められない（符号器は詰まると捨てる）ので優先する。イベントは 1 件の保持レジスタで待つ
  （イベントは SWD 転送ごと = 最速でも約 280 周期おき、ロジアナの拍は RAW で 8 周期に 1 回なので 1 件で足りる）。
  空く前に来たイベントは捨てて数える（events の LOST）。
- **リング**: la_mem_writer を 2 つのリングに拡張する。リング A（ロジアナ）はトリガ後 post_beats で止まる（既存の意味）。
  リング B（イベント）は記録を有効にしている間ずっと書き、書いた総数を出す。読み出し（mem_reader）は領域の先頭と大きさを
  受け取り、その中で折り返す。
- **CSR**: `events` ブロック（有効化、書いた総数、失った数、リング B の位置）。ケイパビリティに記録の容量。
- **ホスト**: `fprobe.events`（読み出し・復号・ポストされた読みの対応付け・ロジアナの時間軸への変換）、MCP の道具。

## 3. 判断

| 判断 | 理由 | 誤っていた場合のコスト |
|---|---|---|
| 新しい非同期 FIFO を作らず、ロジアナの経路を共用する | BSRAM が 94% 使用済み。ロジアナの拍は 8 サンプルに 1 回なので隙間は十分 | 低 |
| ロジアナのリングを 15/16 に減らす（RAW で 0.63 秒、要求の 32 M サンプルは満たす） | イベント用に 8 MB を確保 | 低 |
| 記録は線上の生の転送（意味づけはホスト） | ハードウェアを単純に保つ。ポストの解釈は DAP.c と同じ規則でホストが再現できる | 低 |
| 時刻は 48 ビット（100 MHz で 32 日） | 1 拍に収める | 低 |
| 待ち行列は 1 件（当初 2 段のスキッド） | CLS 93% で配置が混み ULPI のタイミングが崩れた。1 件で約 120 FF 減。取りこぼしは LOST で見える | 低 |
| DDR3 のあるボードでは内蔵 BSRAM のロジアナを外す（`LA_INTERNAL => false`、LA_DEPTH = 0） | 深いバッファが同じ前段を共用し、深さ・読み出しで上回る。BSRAM 94% → 83%。ホストの `LogicAnalyzer` は自動で深いバッファを使う | 低 |

## 追記: UART・SWO のバイト（時刻相関、2026-10-16）

成功基準「全イベント（波形・DAP 操作・UART・SWO・トリガ）が同一タイムベースで記録される」のため、UART の送受信バイトと
SWO のバイトもイベントとして同じリングに記録する。

- 種類: 3 = UART 受信（ターゲット → PC）、4 = UART 送信（PC → ターゲット）、5 = SWO。データの下位 8 ビットがバイト。
- 時刻: ブリッジ / SWO 受信器との受け渡しの周期（UART 受信・SWO は線上の受信完了の数周期後、UART 送信は PC から
  受け取った時点 = 線上に出る前）。
- 源ごとに 1 件保持し、DAP・割り込みのイベントが無い周期に出す。UART は 3 Mbaud でも 1 バイト約 330 周期おきなので
  1 件で足りる。保持が出ないうちに次のバイトが来たら捨てて数える（`events.lost` に足す）。
- ホスト: `fprobe.events.KIND_UART_RX / KIND_UART_TX / KIND_SWO`。`resolve` はバイトをそのまま返し、ポストされた
  読みの対応付けには関わらせない。
