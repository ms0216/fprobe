# JTAG の TDO の取り込みの点（R16）

2026-10-23。利用者の承認済みの 12 時間の作業の一覧の 2 番。決め事は私（Claude）の判断で、利用者は帰ってから確かめる。

## 1. 分かった事実（Pi 2B、Primer の DVP の端子、ジャンパ線。RTCK の線を足した配線）

- TAP は TCK の立ち下がりで TDO を変え、次の立ち下がりまで保つ。前の jtag_phy は TDO を Low 相の終わり（立ち上がりの直前）で
  取っていた。立ち下がりから半周期しか待たない。
- 実測（sys 100 MHz、まとめ読み 1024 語 × 5 回）。**R16 を入れる前の fprobe_jtag の回路で測った**（Pi の JTAG は
  標準の構成 fprobe には無く、道具が fprobe_jtag に切り替える。段 1 の回路は fprobe だけ作っていた。後で分かった）:
  - 要求 10 MHz（実際 9.1 MHz）・12.5 MHz（実際 11.1 MHz）: 食い違い 0。速い読み 273〜288 kB/s（11.1 MHz）。
  - 要求 16.7 MHz（実際 14.3 MHz）・25 MHz（実際 20 MHz）: チェーンの IDCODE が 0x974008EF。正しい値 0x4BA00477 を
    1 ビットずらした値（`0x4BA00477 << 1 | 1`）。値が化けたのではなく、TDO が取り込みの点より後に届いている。
  - 前の回路の取り込みは Low 相の終わり（din は 1 周期前のピン）= 立ち下がりから (half_period − 1) 周期。よって遅れは
    14.3 MHz（half_period 3）の 20 ns より長く、11.1 MHz（half_period 4）の 30 ns 以下。中身（Pi の GPIO の出力の遅れ・
    配線）は分けて測っていない。
  - 段 1 の取り込み（次の立ち下がりの直前 = 2 × half_period 周期）なら、20 MHz（half_period 2）でも 40 ns 待てる。
- R16 を入れた fprobe_jtag での測り直し（2026-10-23 昼。Pi 2B、まとめ読み 1024 語 × 5 回の食い違いの語数）:

  | 要求（実際の TCK） | 遅れ 0 | 遅れ 1 | 遅れ 2 | 遅れ 3 | 速い読み |
  |---|---|---|---|---|---|
  | 10 MHz（9.1） | 0 | | | | 253〜283 kB/s |
  | 12.5 MHz（11.1） | 0 | | | | 273〜299 kB/s |
  | 16.7 MHz（14.3） | 1689 | 248 | 302 | 0 | 307〜323 kB/s |
  | 25 MHz（20.1） | 0 | | 0 | | 320〜348 kB/s |

  - jtag.sample_delay_scan（IDCODE を 50 回）: 14.3・20.1 MHz とも遅れ 0〜3 で 50/50、4〜7 で 0/50（取り込みが次の
    ビットへ行き過ぎる）。14.3 MHz の読みの食い違いは IDCODE の読みでは出ない（中身は分けていない）。
  - 前の上限（10 MHz、275 kB/s）から、20 MHz で 320〜348 kB/s。HIL の試験は 10 MHz のまま（20 MHz は 5 回の事実だけ）。
  - 最終の回路（R24 の作り直しの後、2026-10-23 13 時台）: 20 MHz は 2 回とも食い違い 0（316〜359 kB/s）。14.3 MHz は遅れ 3 でも
    DP の誤りの印（STICKYERR）が立った。その直後（13:45）に Pi が起動し直していた（ジャーナルの起動の記録）。この確かめの
    台本は割り込みの行き先のコア 1 を止めていた（試験の決まりはコア 3）。起動し直した原因（化けた命令の実行か、コア 1 を
    止めたことか）は分けていない。14.3 MHz はそれ以後試していない。
  - 20 MHz の繰り返し（同じ日の 14 時台、Pi の起動し直しの後）: 遅れ 0 と 1 を交互に 4 回ずつ、各 5 回のまとめ読み。
    8 組のうち 7 組は食い違い 0（277〜355 kB/s）。遅れ 0 の 1 組は、1024 語の読みの途中で DAP の誤りとして返った
    （黙って化けたのではない）。試験の既定の速さは 10 MHz のまま。
- 遅れが 1 周期近くになると、取り込みの点を「次の立ち下がりの後」まで遅らせる必要がある（次のビットの Low 相の途中で、
  前のビットの値を取る）。

## 2. 作るもの

- jtag_phy: 基準の取り込みを次の立ち下がりの直前（次のビットの TCK を下げる周期。din はその 1 周期前のピン）に移し、
  そこから `sample_delay` 周期（sys、0〜7）遅らせる。遅らせた取り込みは
  （ビット番号・どこに入れるか）の遅延線で運び、次のビットの出力と重なってもよい。TDI を出すシフトレジスタと、TDO を
  入れるレジスタは分ける（遅れた取り込みが TDI を乱さない）。命令の終わりは、遅延線が空になってから。
- CSR `debug.sample_delay` に欄 `jtag`（bit 8〜10、既定 0 = 次の立ち下がりの直前）。FPGA の観測のエンジン（obs_jtag_engine）も
  jtag_phy を使うが、遅れて届く対象がまだ無いので遅れは 0 に固定する（段 1 の High 相の終わりは効く。要るときに CSR を足す）。
- ホスト: `jtag.sample_delay_set(cycles)` と、速さと遅れの組ごとにチェーンの IDCODE を読んで、期待値（呼び手が明示して
  渡す）と一致したかを並べる `jtag.sample_delay_scan(frequency_hz, expected_idcode, reads)`。どれを使うかは決めない
  （事実を返し、選ぶのは使う側。CLAUDE.md のヒューリスティックの原則）。

## 3. 試験

- cocotb: モデルの TDO の遅れを 1 周期より長くし、sample_delay を足すと IDCODE と DP の読み書きが正しいこと、足りないと
  1 ビットずれること、TDI がずれないこと。
- 実機: Pi 2B で 14.3 MHz・20 MHz の scan の結果と、選んだ遅れでのまとめ読みの食い違い。
