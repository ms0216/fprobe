# 深いバッファのストリームを、PS が DDR から直接読む（PYNQ-Z2）

2026-10-30。状態: 設計（未実装）。関連: `2026-10-30-la-capture-clock-design.md` の 10.3、`2026-10-16-m8c-la-streaming-design.md`、
`2026-10-19-r1-unified-stream-design.md`、`2026-10-19-pynq-z2-port-design.md` §5.1。

## 1. 目的と、なぜ

PYNQ-Z2 の深いバッファ（`fprobe_pynq_deep`）の垂れ流しは、PC が取りこぼしなしで受けられる速さが約 10.4 MB/s
（RAW 16 ch で約 5.2 MS/s）で頭打ちになっている。律速は、中継（PS）が PL の窓を 32 ビットずつ読む処理で、
1 フレーム（約 510 バイト）あたり約 34 µs（実測。中継の中で時間を数えた）。

データは、もともと PS の DDR にある。ストリームは「ロジアナ（と DAP のイベント）が DDR のリングに書く → PL の `mem_reader` が
DDR から読み戻す → バイト列にして窓から PS へ」という回り道をしている。PS が DDR のリングを直接読めば、窓の読みが要らない。

実測（PYNQ、読み取りのみ。深いバッファの領域 0x1E000000 から 4 MB を `/dev/mem` で読む。カーネルドライバなし。O_SYNC の有無で差なし）:

| 読み方 | 速さ |
|---|---|
| 32 ビット | 33.8 MB/s |
| 64 ビット | 69.9 MB/s |
| NEON 128 ビット | 138.9 MB/s |
| `memcpy` | 68 MB/s（当初 207 MB/s と書いたのは誤り。10.2 の訂正を参照）。NEON で 64 バイトずつなら 125 MB/s |
| （参考）今の窓の読み | 約 15 MB/s（510 バイト ÷ 34 µs） |

読みが壁でなくなると、次の壁は送信（`sendto` 1 パケット約 27〜29 µs。実測）と、PC の受信（ループバックで毎秒 80,000 フレーム =
約 41 MB/s まで欠け 0。デコードは含まない。実測）と、リンク 1 Gbps（約 125 MB/s）。見込みは 40〜70 MB/s（RAW 16 ch で約 20〜35 MS/s）。
これは**計算と部分の実測からの見込み**で、通しの実測は実装後。

## 2. 範囲

- やる: `fprobe_pynq_deep`（`mem_bytes > 0` かつ `la_stream_events`）のストリームを、PS の直接読みで流せるようにする。
  ロジアナのリングとイベントのリングの両方。
- やらない: Primer（外部 DDR3 は PS がない）。内蔵 BRAM のロジアナ（`fprobe_pynq`・`fprobe_pynq_cap`）。トリガ付きの 1 回取り込み
  （深いバッファのトリガ取り込みの読み出し。今のまま）。300 MS/s の垂れ流し（深いバッファの符号器が sys で 1 サンプル/周期）。
- アンチゴール: 直接読みのモードを入れたせいで、今のストリーム（窓経由）が壊れること。モードを入れないときは、回路も線上の形式も今と同じ。

## 3. 方式

### 3.1 モード
`la_deep.control.ps_read`（新しい 1 ビット、RW）。1 のときだけ直接読み。ストリームの開始（run の 0→1）の時点で取り込む（`stream` と同じ扱い）。

> **2026-11-03: 位置の約束（世代・窓のレジスタ・中継の読み書き）は [2026-11-03-ps-stream-position-design.md](2026-11-03-ps-stream-position-design.md)
> （窓の版 4）で置き換えた。** 以下の 3.2〜3.4 の世代・STREAM_STATUS・ps_clear の記述は版 3 までのもの。

### 3.2 PL（la_deep_buffer）
- 直接読みのとき、チャンクを `mem_reader` に読ませる状態機械（T_IDLE→T_SUM→T_HDR→T_GO）は動かさない。見出しも作らない。
  `mem_reader` の読み出しは `read`（トリガ取り込みの読み出し）だけが使う。
- 読み終えた位置は、PS が窓のレジスタに書く（3.3）。それを mem クロックに渡し、`r_total`（ロジアナ）と `ev_rpos`（イベント）として使う。
  未読（`w_total − r_total`・`ev_wpos − ev_rpos`）の判定と、リングに迫ったときの書き込み停止・overrun は、今のまま同じ式で動く。
- 書いた位置（`w_total`・`ev_wpos`）と、書き込みが動いているか（`w_running`）、overrun は、窓から読めるようにする。
- **公開する位置は、書き込みの応答（AXI の B）が返った拍までに絞る**。`axi_mem_port` は、PL が読む場合に「書きの B がすべて返ってから
  読みを出す（AXI は書きと読みの順を保証しないため）」としている。PS が読む場合も同じ保証が要るので、`axi_mem_port` が応答待ちの書きの数
  （`wr_pending`）を出し、`la_deep_buffer` は公開する位置から、その数だけ引く（ロジアナもイベントも、どちらの書きか分からないので同じ数を
  引く。安全側）。引いた分は次の公開で見える。公開される位置は、前の値より小さくなることがあり、中継は「未読が範囲外」として未読なしに扱う。
- **世代（`ps_epoch`）は、書き位置・イベントの最初の位置と同じ受け渡し（1 つの保持レジスタ）で公開する**。`ps_read` の流れを始めるたびに
  mem 側が 1 進める。中継は、世代を読んで → 位置を読んで → 世代をもう一度読み、変わっていたら捨てる。新しい世代が見えたとき、位置は
  新しい流れのもの（前の流れの古い総数を見て、古いリングの拍を新しい流れとして読む事故を防ぐ）。
- PS が返す読み終えた位置が、書いた総数より先なら採らない（前の流れの古い値）。窓の `ps_clear`（流れの開始の 1 周期）は、PS の読み終えた
  位置を 0 に戻す。
- 止め方は今と同じ（run の 1→0 で書き込みを止め、未読を出し切って終わる）。「出し切った」は、PS が書いた総数まで読み終えたこと。
  `status.reading` は、直接読みでは「PS がまだ読み終えていない未読がある」とする（ホストの `_discard_stream` と同じ意味を保つ）。

### 3.3 窓（zynq_frame_link）に足すレジスタ（PS から読み書き。AXI-lite 1 回 約 150 ns）
読み出し専用: `STREAM_MODE`（ps_read の値）、`LA_WRITTEN`（w_total）、`EV_WRITTEN`（ev_wpos の総数）、`STREAM_STATUS`（writer 動作中・overrun）。
`STREAM_EPOCH`（世代。上記の `ps_epoch`）。書き込み: `LA_CONSUMED`（PS が読み終えたロジアナの拍の総数）、`EV_CONSUMED`（読み終えた
イベントの数。どちらも流れの開始からの総数で、流れの開始で 0 に戻る。イベントのリングの位置は `EV_START + EV_CONSUMED`）。
窓のレジスタの表は `relay.h` と、PL の模型（`host/tests/test_pynq_relay.py`）と同じに揃える。窓の版（`RELAY_LINK_VERSION`）を上げる。
中継は CSR に触れない（CONTROL チャンネルは PC とコアの間）ので、PS と PL のやり取りは窓にだけ置く。

### 3.4 中継（fprobe-relay）
`STREAM_MODE = 1` のとき、窓の `LA_WRITTEN`・`EV_WRITTEN` を見て、未読があれば、PL のチャンクと同じ形（見出し 1 拍 + 中身。種類・拍数・位置は
`fprobe_map.STREAM_SEG_*`）の STREAM チャンネルのバイト列を DDR から NEON の読みで作り、まとめ送りの 1 つの UDP にする。
読み終えたら `LA_CONSUMED`・`EV_CONSUMED` を書く。DDR の領域（`MEM_BASE`・`LA_SIZE`）は、中継が既に知っている。
中身のフレームの長さは、まとめ送りの 2 バイトの長さの範囲で自由（今の 512 バイトの制約を受けない）。
送信は、読み取りのスレッドを使わずに済むので、2 つのスレッドで送れる。
CONTROL・DAP は今と同じ道（窓）。

### 3.5 ホスト
- `DeepAnalyzer.stream` が、ケイパビリティ（新: `la_stream_ps`）があり、まとめ送りが有効なら `ps_read` を 1 にする。無ければ今のまま。
- バイト列とチャンクの解釈（`LaStream`）は変えない（中継が PL と同じ形のバイト列を作るので）。`StreamFormatError` の検査も、そのまま働く。

## 4. 試験

- ゲートウェア（cocotb。`tests/test_la_deep_buffer.py` の形）: ①`ps_read = 0` のとき、これまでの出力と完全に同じ（既存の試験が全部通る）。
  ②`ps_read = 1` のとき、`mem_reader` にチャンクを読ませない。③`LA_CONSUMED` を進めないと、未読がリングに迫った時点で書き込みが止まり overrun が立つ。
  ④進めれば書き続ける。⑤イベントも同様（`EV_CONSUMED`）。⑥止めた後、PS が総数まで読み終えると `reading` が落ちる。
- 窓（`zynq_frame_link`）: 新しいレジスタの読み書きと、PL の信号との対応。
- 中継（`host/tests/test_pynq_relay.py` の模型を DDR 付きに）: PL の FSM が作る見出し・並びと、中継が作るバイト列が同じ。リングの折り返し。
- 実機（PYNQ）: 窓経由のストリームと直接読みのストリームを同じ条件で流し、バイト列が（見出しを除いて）一致する。速さ・欠け・overrun。

## 5. 未確認・リスク

- NEON の 139 MB/s は DDR の読みだけの値。見出しの組み立て・UDP への詰め込みを含めた通しの速さは未測定。
- 送信を 2 コアで進めても、見込み（約 70 MB/s）まで伸びる保証はない。伸びなくても、読みは壁でなくなるので今より速いはず。
- PS の DDR の読みと PL の HP0 の書きが同じ DDR を取り合う。実測した書き込み（200 MB/s）と同時に読んだときの、互いの遅れは未測定。
- 窓のレジスタの版を上げるので、PL と中継を揃えて入れ替える必要がある（PL だけ・中継だけの入れ替えは中継が起動を拒む = 安全側）。
- 全件のゲートウェアテストは約 44 分。Vivado のタイミング（sys 100 MHz）を、`fprobe_pynq_deep` と、`la_deep_buffer` を使うほかの構成で確かめる。

## 10. 実装の記録と実測（2026-10-31、PYNQ-Z2、`fprobe_pynq_deep`、RAW 16 ch）

### 10.1 実装した形（設計からの変更点）
- 3 章の設計どおりに入れたうえで、実機の通しの試験で見つけた不具合を直した（どれも先にテストで再現した）:
  1. 窓の `STREAM_MODE` を、CSR の `ps_read` ではなく「PS が読む流れが生きている」印（`ps_active`: 開始から PS が全部読み終えるまで）にした。
     ホストは止めるとき制御レジスタに 0 を書く（`ps_read` も 0 になる）ので、CSR の値だと、未読が残ったまま中継が読むのをやめた。
  2. ホストは CSR の `stream_beats` で「必ず届く量」を知る（`LaStream._available`）。PS が読む流れでは PL がこれを知らない（かたまりの見出しを中継が作る）ので、
     中継が出すと決めた拍の総数（見出しを含む）を窓の `STREAM_BEATS` に書き、PL がそれを `stream_beats` として見せる。かたまりのデータグラムを渡す前に書く。
  3. ホストの `FrameLink` は条件変数が 1 つで、ストリームのデータグラムが 1 つ届くたびに、CSR の応答を待つスレッドを毎回起こしていた
     （毎秒 1 万以上で GIL を奪い合い、受信が詰まって制御が時間切れ）。チャンネルごとの条件変数にした（10 → 20 MB/s）。
  4. `LaStream.chunks` は、止めた後に機器が読み出し中のまま出し切らないとき、永久に待っていた。`timeout_ms` 進まなければ TimeoutError にした。
  5. 窓の世代（`STREAM_EPOCH`）は、書き位置・イベントの最初の位置と同じ受け渡しで公開する（3.2 のとおり）。
- 追加した設計: ストリームを **TCP** でも送る（`open_stream_tcp`、中継の 63921）。理由は 10.3。ホストがつないでいる間、中継は PS 直読みのバイト列を TCP だけで送る
  （制御・DAP は UDP のまま）。つなぐのは `Session.open_eth` が、ケイパビリティ `la_stream_ps` を見て自動で行う（`stream_tcp=False` で UDP のまま）。
- DDR の読みは、ARM では NEON で 64 バイトずつ（`copy_from_device`）。

### 10.2 読みの速さ（実測、PYNQ、読み取りのみ。深いバッファの領域 0x1E000000 から 8 MB）
| 読み方 | 速さ |
|---|---|
| 32 ビットずつ / 64 ビットずつ / NEON 128 ビットずつ | 33.8 / 69.9 / 138.9 MB/s |
| glibc の `memcpy`（256 B〜64 KB のどの大きさでも） | **68 MB/s** |
| NEON で 64 バイトずつ（4 本の 128 ビット読み） | **125 MB/s** |
| （参考）窓の語ごとの読み | 約 15 MB/s |

訂正: 設計 1 章の表の「`memcpy` 207 MB/s」は、コンパイラが最適化でコピーを省いた誤りで、正しくは 68 MB/s。NEON の値は検算した。

### 10.3 UDP の限界と TCP（実測）
- PYNQ → PC の UDP（1395 バイト）は、毎秒 15,000 個（20.9 MB/s）までは欠け 0、毎秒 20,000 個（27.9 MB/s）で 1〜1.7% が消えた。
  バーストでも滑らかでも同じ。PC の `netstat -e` の受信の「破棄パケット」が、消えた数とほぼ同じだけ増えた（1,120 / 約 1,240）。PC の UDP の受信エラーは 0、
  PYNQ の送信側（qdisc の落ち、`SndbufErrors`、NIC の送信エラー）は 0。つまり、**この PC の NIC が受信を破棄している**（NIC の受信バッファの設定は管理者の権限が要るので、変えていない）。
- そのため UDP のストリームは、8 MS/s（16 MB/s）でも、30 秒の運転で欠けて止まる回があった（欠けは黙って見逃さず、通し番号の飛びで StreamFormatError にする）。
- 素の TCP（PYNQ → PC、再送つき）は、16 KB ずつ送って 68 MB/s、1395 バイトずつだと 28.7 MB/s（呼び出しの回数で決まる）。
  TCP は欠けを再送し、流量も調整するので、中継は 12 KB 前後ずつ送る。

### 10.4 通しの実測（TCP、各 5 秒。「受信」は PC が受け取った速さ）
| 要求 | 受信 | 欠け | overrun | 備考 |
|---|---|---|---|---|
| 10 MS/s（20 MB/s） | 20.2 MB/s | 0 | なし | 10 秒でも同じ（実機のテスト） |
| 12.5 MS/s（25 MB/s） | 25.1 MB/s | 0 | なし | UDP では欠けて止まっていたレート |
| 16.7 MS/s（33.4 MB/s） | 33.4 MB/s | 0 | なし | **60 秒で 2,014 MB を、途切れず受信**（60.03 / 60.05 秒） |
| 20 MS/s（40 MB/s） | 35.2 MB/s | 0 | なし | 5.02 秒分を 5.73 秒で受信（遅れ分は PL の DDR のリングが溜める） |
| 25 MS/s（50 MB/s） | 39.7 MB/s | 0 | あり（3.1 秒後） | リングが溢れて、PL が止まる。欠けや破損は出ない |
- **持続できる速さは約 35 MB/s（RAW 16 ch で約 17.5 MS/s）**。今までの窓経由は約 10.4 MB/s（RAW 約 5.2 MS/s）、UDP の PS 直読みは、この PC で欠けなしに続けられるのが約 10 MS/s まで。
- 中継の内訳（20 MS/s、3 秒ごと）: 読み 12.2 KB で 143 µs（約 85 MB/s。稼働は約 41%）、送信は 3 秒のうち約 88% を使う。**今の壁は、ARM の 1 コアが TCP で送る速さ**
  （素の TCP の測定でも 1 コアで 68 MB/s）。これ以上は、送信を複数の接続・コアに分ける必要がある（未着手）。
- ストリーム中の制御（CSR の読み）の往復（TCP）: 8 MS/s で中央値 1.6 ms（最大 8 ms）、17 MS/s で中央値 4.6 ms（最大 14 ms）。アイドルは 0.2〜0.3 ms。
- 開始と停止を 10 回繰り返して、すべて成功（5 MS/s、1 秒ずつ。欠け 0、不正フレーム 0）。
- 3 つの経路（UDP の PS 直読み、窓経由、TCP）を、同じ PYNQ で続けて使えることを確かめた（実機のテスト `gateware/tests/hil/test_pynq_ps_stream_hw.py`、3 件通過）。

### 10.5 入れ替えの順番
窓の版 2 の PL に、版 1 しか受けない中継を組み合わせると、中継は起動を断る（安全側で、止まる）。**先に中継を入れ替え（版 1 と 2 を受ける）、その後に PL を書く。**
中継の元のバイナリは `fprobe-relay.old` などに退避しておき、戻せるようにする。

### 10.6 未確認・残ること
- AXI の書きの応答（B）が返った拍までを公開する（5.）が、B が返った時点で、PS の CPU の読みに最新の値が見えることは、AXI と DDR コントローラの仕様に基づく想定で、
  PS からの読みで直接は確かめていない（実機の通しの試験では、見出しの通し番号と中身に飛びも壊れもなかった。60 秒・2,014 MB）。
- 送信が複数の接続・コアに分かれていない。上は約 35 MB/s。
- 結果は、この PC（NIC）での値。UDP の限界は PC の NIC に依存する。TCP は、欠けを再送して流量を合わせるので、PC によらず欠けは出ないが、持続できる速さは PC と回線に依存する。
- ケイパビリティ `la_stream_ps` があっても、中継が TCP に対応していない古い版だと `Session.open_eth` は ConnectionError で断る（黙って UDP に落とさない）。

### 10.7 トリガ取り込みの読み出しも PS 直読みにした（2026-10-31、窓の版 3）
- 範囲: **書き込みが止まったロジアナの取り込み**の読み出し（`DeepAnalyzer.read` / `capture`）だけ。イベントのリングは、書き込み中のことがあり、応答の来ていない最新の書きを PS が読む恐れがあるので、今まで通り窓経由。
- 流れ: ホストが CSR の `la_deep.command.read_ps`（新しい 1 ビット）を打つ（`read` の代わり）。PL は `mem_reader` を動かさず、要求（領域・先頭・拍数）を世代つきで窓の
  `RD_EPOCH` / `RD_REGION` / `RD_FIRST` / `RD_COUNT` に出し、`reading` を 1 にする。中継が DDR から読んで、枠の無いバイト列として TCP で送り（読み出しのバイト列は、リングの拍のまま）、
  最後まで送ったら `RD_ACK` に世代を返す。PL の `reading` はそこで下がる。要求の時点の値を持つので、要求の後に CSR が変わっても影響しない。
- ホストは、デバイスに `la_stream_ps` があり、TCP のストリームが開いているときだけ `read_ps` を使う（`Device.stream_tcp_open`）。TCP が無いときは今まで通りの窓経由（UDP で 31 MB を一気に送ると、欠けても気づけないため）。
- 形の悪い要求（先頭がリングの外・リングより多い・0 拍）は、データを出さずに返事だけする（PL が待ち続けない）。新しい要求が来たら、読みかけを捨てる。

### 10.8 壁の調べと RLE のストリーム（2026-10-31、実測。変更は時間の内訳のカウンタだけ）
- **素の TCP 送信（PYNQ → PC）**: 1 回の `send` が 1400 B で 29 MB/s、16 KB で 約 70 MB/s、64 KB で 約 75 MB/s。繰り返しても 68〜70 MB/s で安定（8 回）。経路と PC の NIC は、ばらつきの原因ではない。
- **中継の中の内訳**（22 MS/s、中継 `main.c` のカウンタ。TCP が閉じたときに stderr へ）: `send` の中が全体の約 83 %、1 MB あたり約 22 ms（素の TCP は約 14 ms）。DDR の読み出しは 1 MB あたり約 22 ms（単独で測った約 8 ms の約 3 倍）。読み取りと送信の 2 スレッドが互いに遅くし合う。
- **効果が確認できず、入れなかったもの**: リング満杯のとき眠る・NIC の割り込みの CPU（`eth0` は CPU0 のみ）を避けたスレッドの固定。どちらも約 34〜39 MB/s で、変更前の約 40 MB/s と同じ。
- **DDR の読みが遅い理由（推測。未確認）**: 起動パラメータが `mem=479M` で、リング（0x1E000000）は Linux の管理外。`/dev/mem` はこの領域を、最も遅い種類のキャッシュ無しで割り当てるはず。直すには、リングを Linux の reserved-memory に置いて書き込み結合にする構成で、起動パラメータの変更と PYNQ の再起動が要る。効果は未測定。
- **ホスト（Python）の受信**: ホストと同じ作りの受け側だけで、63〜66 MB/s（CPU は 1 コア近く）。実経路（18 MS/s、33.6 MB/s）で、TCP の受信スレッドが user 0.81 s・kernel 3.03 s、主スレッド（CSR の往復・分割）が user 1.47 s・kernel 1.20 s（8 秒）。CPU 1 コアの限界（約 60〜70 MB/s）が、ARM の壁（約 40 MB/s）のすぐ上にあり、実行ごとのばらつきの一因。受信にタイムアウトを付けない・付けるの違いは、1 MB あたりの CPU に出なかった。

- **RLE のストリーム**（`stream(rle=True)`、実機、入力は変化なし）: 50・100 MS/s を各 5 秒、欠け 0・overrun なし、受信は 0.01 MB/s（0.1 MB 未満）。200・300 MS/s の指定は、この回路ではサンプルクロック（100 MS/s）で頭打ち。RLE の費用はサンプル数でなく変化点の数に比例する（1 変化点 4 バイト）ので、35 MB/s なら毎秒約 870 万回の変化まで続けられる計算（算出。変化のある入力では未測定）。

### 10.9 リングを reserved-memory に置く・スレッドの固定（2026-10-31、実測。中継 commit 0d46362、`host/pynq/fit-reserve/`）

### 10.10 ホストの受信の CPU を約 4 割減らした（2026-10-31、実測。`eth_link.py` の `_tcp_rx_task`）

### 10.11 中継の壁（約 48 MB/s）の内訳（2026-10-31、実測。コードは変えていない）
- 20 MS/s・10 秒（PYNQ-Z2）: 読みスレッドの読み出しは 1 MB あたり 約 20 ms、主スレッドの send も 1 MB あたり 約 20 ms。**2 つが同じ長さで、両方を縮めないと壁は動かない**。
- 読みの時間と、そのスレッドの CPU 時間は同じ（8325 ms と 8296 ms）。**割り込みや他のスレッドに取られて待たされているのではなく、実際に動いている時間**（10.9 の「読み出し 235 MB/s なのに 19 ms/MB」の問いへの、一部の答え）。
- 読みの内訳（推定を含む）: 1 つのかたまり（256 拍 = 4 KB）ごとに PL のレジスタ（MMIO）を約 9〜10 回触り、1 MB で約 2,400 回。回数は実測。時間は、計測自体（clock_gettime が 1 回約 2 µs。この ARM ではシステムコール）で歪み、読み 1 回あたり計測込み 約 3.3 µs（上限）で、1 MB の読み 20 ms のうち 4〜8 ms。残りは NEON の読みで、PL が書いている間は 約 70〜90 MB/s（PL が止まっているときは 235 MB/s）。**DDR の取り合いは実際にある**。
- かたまりを大きくしてレジスタの回数を減らす手は使えない: ホストの `SegmentSplitter` が `STREAM_SEG_MAX_BEATS`（0x100 = 256 拍）を超える見出しを壊れたものとして止める（試して確かめた。元に戻した）。
- 未着手の案（効果は未測定）: (1) 1 回のレジスタの読みで複数のかたまりを写し、CONSUMED・STREAM_BEATS の書きもまとめる（読み側で 約 3 ms/MB の見込み。送信側が同じ 20 ms/MB のままなので、単独では壁は動かない）。(2) 送信側は、1 MB あたり 約 700 セグメント（MSS 1448）の TCP の処理が主と見ているが未確認。PC・PYNQ の MTU を上げる（ジャンボフレーム）と減らせる見込み。PC の NIC の設定変更が要る。

### 10.12 中継: 送信をまとめる・読みのレジスタをまとめる（2026-10-31、実測。`main.c` の `tcp_drain`、`relay.c` の `ps_snapshot`/`ps_take`/`ps_publish`）
- **持続できる速度が上がった**（RAW 16 ch、PYNQ-Z2・Windows、同じ条件の A/B）: 25 MS/s（50 MB/s。23〜25 の指定はここに丸められる）の 40 秒は、変更前が 3 回とも 12〜21 秒で溢れ、変更後は 4 回とも 40 秒（2 GB）欠けなし（49.6〜50.2 MB/s）。ただし**持続はぎりぎり**: 60 秒は 5 回中 1 回だけ通り（3 GB）、ほかは 7.8・14.7・15.6・24.7 秒で overrun（原因は未確認。50 MB/s は測れた最大 約 50 MB/s と同じで、少しの遅れで溢れる）。確実なのは 20 MS/s（40 MB/s）の 60 秒（3/3 欠けなし、2,415 MB）。
- 原因の見立てを直した: 10.9・10.11 の「読みが 1 MB あたり 約 20 ms」は、読みそのものでなく、**CPU0（NIC の割り込みと同じ）の softirq に取られた時間が、読みスレッドの時間に数えられていた**。ストリーム中（24 MS/s・10 秒）の /proc/stat は CPU0 が user 33 %・**softirq 49 %**・idle 15 %、CPU1（送信）が system 79 %・idle 15 %。user の時間から読みの実際の速さは 約 6.5 ms/MB（約 150 MB/s）。10.11 の「読みの時間 = CPU 時間だから待たされていない」は、この設定（割り込みの時間が走っていたスレッドに数えられる）では成り立たない。MMIO の時間の見積もり（4〜8 ms/MB）も、計測が重く（clock_gettime が約 2 µs のシステムコール）上限でしかなかった。レジスタをまとめて 1 MB あたり 約 1 ms しか縮まなかった。
- 効いたのは送信のまとめ: 送信単体の実測（PYNQ → PC、同じ TCP）で、1 回の send が 4 KB で 26.1 ms/MB、6.5 KB で 20.7、16 KB で 15.3、64 KB・256 KB で 16.7。読めるスロットを最大 8 つ（約 50 KB）まとめて `sendmsg` にして、送信が 約 21 → 約 17 ms/MB（リング満杯が 0 回になり、読みが待たされなくなった）。
- 読みのレジスタ: 1 回の `relay_ps_fill_bytes` で位置のレジスタを 1 回だけ読み、続けて写し、読み終えた位置・出す拍の数の書きも最後に 1 回（データを渡す前）。UDP の `relay_ps_step` の動きは同じ（`ps_fill` は 3 つを続けて呼ぶ）。
- 途中までしか送れない場合（送信バッファが埋まる）: ホストの受信スレッドを遅くして通した（EAGAIN 約 8,000 回・リング満杯 約 70 万回）。通し番号の検査で壊れは 0。
- 試験: 中継の C のテスト 65 件通過（`test_peek_many_...`・`test_fill_bytes_reads_the_positions_once_...` を追加。後者は変更前のコードで失敗を確認）。実機の試験 `test_pynq_ps_stream_hw.py --hil` は 4 回続けて 4 件通過。
- 使えなかった・やらない手: かたまりの拡大（ホストの `STREAM_SEG_MAX_BEATS` = 256 拍が上限）。ジャンボフレーム（PC の NIC = Realtek Gaming GbE はジャンボの設定項目を出さず、PYNQ は同じ LAN のスイッチ経由）。
- 壁は、2 コアとも 85 % ほど使う TCP の処理（CPU0 の softirq と CPU1 の送信）。次に動かすなら、パケット数・ACK の数を減らす手（PC の TCP ACK の頻度の設定など。PC のレジストリの変更が要る）。

### 10.13 NIC の割り込みを遅らせて、25 MS/s の 60 秒を持続させた（2026-10-31、実測。`main.c` の `nic_tune`、`relay.c` の `relay_sysfs_set`）
- 切り分け: 25 MS/s の 60 秒が溢れた回でも、中継の EAGAIN は 0・リング満杯は 0 回。PC の受信や TCP の詰まりではなく、読みの速さが必要な 20 ms/MB の前後にあった（通った回 19.0、溢れた回 20.8）。読みは CPU0 の NET_RX の softirq（毎秒 約 1 万回の ACK、1 回 約 30 µs）に CPU0 の約半分を取られる。
- 対策: Linux 6.6 の `/sys/class/net/eth0/napi_defer_hard_irqs` と `gro_flush_timeout` で NAPI の割り込みを遅らせ、ACK をまとめて処理する。**25 MS/s の 60 秒（3 GB）は、設定なしが 8 回中 3 回通過、設定ありが 16 回中 16 回通過**（napi_defer_hard_irqs 2/100 µs・8/500 µs・30/2 ms の 3 通りを手で入れて 9/9、中継に組み込んだ 8/500 µs で 7/7。ほかに 1 回は結果の行が出ず不明）。上限は 33 MS/s（66 MB/s）が 2.3 秒で溢れ、ピークで約 54 MB/s。
- 組み込み: 中継が、TCP のストリームがつながった時に 8・500000 ns を入れ、閉じたとき（終了時の atexit も）元の値に戻す。普段の通信の遅れに影響させないため。ストリームの最中に中継を再起動しても `0 0` に戻ることを確かめた。root でなければ変えられず、そう記録して続ける。`relay_sysfs_set` は、書く前の値を返し、入りきらなければ何も書かない（テスト 3 件）。
- 実機の試験 `test_pynq_ps_stream_hw.py --hil`（制御の往復の項目を含む）は、設定を入れて 3 回続けて 4 件通過。
- PC 側の妥当性: タスクマネージャの受信 421 Mbps は、中身 50.25 MB/s（402 Mbps）× 回線上の 1518 B ÷ 中身 1448 B ≈ 421 Mbps と一致。送信 2.5 Mbps は ACK。回線（1 Gbps）の約 4 割。

### 10.14 PC 側の受信が詰まる時間帯があった: 受信スレッドが少し眠って、まとめて取る（2026-10-31、実測。`eth_link.py` の `_tcp_rx_task`）
- 10.13 の「16 回中 16 回」は、PC が空いていた時間帯の結果だった。続けて測ると、同じ設定で 6 回中 3 回が溢れた（14〜57 秒）。そのときの中継のカウンタは、通った回も溢れた回も **EAGAIN 6.5〜9.6 万回・リング満杯 約 100 万回**（以前の通った回は 0 回）。PC が受信しきれず、TCP の詰まりが中継を止めていた。10.13 の「読みが 19〜21 ms/MB」は、そのときの要因で、これは別の要因。
- 受信の能力の測定（PYNQ の sendbench 16 KB 送り → ホストと同じ作りの受け側。1.5 GB）: そのときの PC で 約 56〜61 MB/s（以前は 63〜66 MB/s）、Python の CPU は 27 秒で 12〜15 秒。50 MB/s のストリームに対して余裕が 1〜2 割しかなかった。`recv` を `recv_into` に替えても差は出なかった。
- 対策: 1 回の `recv_into` が 64 KB に満たなければ、1 ms 眠ってから次を取る。1 回に取る量が約 8 KB → 約 50 KB になり、毎秒の recv が約 6000 → 約 1000 回。同じ 57 MB/s で Python の CPU が **12.5 s → 7.0 s（27 秒）**。受信バッファ 8 MB は 1 ms では埋まらない。ストリームの遅れは最大 1 ms。
- 結果: 25 MS/s（50 MB/s）の 60 秒（3 GB）が **11 回中 11 回** 欠けなし、中継の EAGAIN は 0 回。実際の流れの Python の CPU は 60 秒で 22.5 s → 約 15 s。実機の試験は 3 回続けて 4 件通過、ホスト全体は 3124 通過（失敗 22・エラー 78 は基準と同じ）。
- PC の設定（MTU・レジストリ・NIC の受信バッファ）は変えていない（ユーザの方針）。PC の NIC にはジャンボフレームの項目があり（値は無効）、先に「項目が無い」と書いたのは英語名でしか探さなかった誤り。使うには PC のメインの回線の MTU 変更とスイッチの対応が要るため、提案にとどめる。

### 10.15 `reboot` が止まる原因: 中継が SLCR をロックし直していた（2026-10-31、実機で確認、解決。`relay.c` の `relay_slcr_write`）
- 症状: Linux の `reboot` が `Reboot failed -- System halted`（CPU0 が `machine_restart` の `b .`）で止まる。JTAG からの PS のソフトリセットは効く。
- 止まった状態を JTAG で読んだ: **SLCR の `LOCKSTA`（0xF800000C）= 1（ロック）**。以前の記述「SLCR は解錠されている」は誤りだった（確かめずに書いた）。
- カーネルの再起動処理 `zynq_slcr_system_restart` の機械語を JTAG で読んだ（0x0011731c）: `REBOOT_STATUS`（0x258）を読んで書き、`PSS_RST_CTRL`（0x200）に 1 を書く。**鍵（`SLCR_UNLOCK`）を書かない**。カーネルは、起動時に解除した SLCR をそのまま使う前提。ロックされていると、この書き込みは無視され、リセットがかからずに戻って「Reboot failed」になる。JTAG の復旧が効くのは、先に 0xDF0D（解除）を書くため。
- 原因: 中継（`main.c`）が、レベルシフタを切り替えるたび（起動時の有効化・`--isolate`・`--enable`）に、解除 → 書く → **ロック（0x767B）** としていた。起動のたびに中継が SLCR をロックし直していた。試した全部の構成が止まったのは、どの構成でも中継が動いていたため（`--isolate` の試験も、同じくロックして終わる）。
- 修正: 書く前のロック状態を保つ。ロックされていれば解除して書いてロックし直す。解除されていれば解除のまま書く（`relay_slcr_write`、テスト 2 件）。修正した中継で起動すると `LOCKSTA` = 0（旧: 1）。`fprobe-pl before/after`（レベルシフタの切替）を通しても 0 のまま。
- 確認: 修正した中継で、Linux の `reboot` が JTAG なしで通った（約 95 秒で復帰）。再起動後の `LOCKSTA` も 0。
- 注意（自分の誤り）: 検証の最中に、中継を動かしたまま `fprobe-relay --isolate` を実行し、レベルシフタが切れた状態で動いている中継が PL のレジスタを読みに行って、ボードが固まった（JTAG のリセットで復旧）。`--isolate` は、`fprobe-pl before`（先に中継を止める）の中で使う。
- 再起動の後の悪化（2026-10-31、3 回目の再起動で毎 30 秒に観測）: 起動から約 3 分間、**PYNQ の 2 コアとも CPU がほぼ使い切り**になる（+122 秒: CPU0 user 62 %・idle 5 %、CPU1 user 60 %・idle 1 %。中継の送信は user 5 % なので別のプロセス。ロード 3.2）。この間、25 MS/s は溢れる（+122 秒 25.6 MB/s で 1.2 秒、+157 秒 36.8 MB/s で 3 秒）。+187 秒から 50.2 MB/s で安定。PL を書いた直後（再起動なし）は 14 回中 14 回通るので、原因は PL の書き込みでなく起動。
- **原因（再現して確定）**: 起動時の `jupyter.service`（42.7 秒）・`clear_pl_statefile.service`（34.3 秒）など Python の PYNQ 読み込みが、中継の 2 スレッド（読み取りと送信。25 MS/s で 2 コアとも約 85 %）と CPU を取り合う。ストリーム中に `systemctl restart jupyter` するだけで、`jupyter-notebook` が 80〜138 %（`node` も 63 %）を十数秒使い、25 MS/s は 約 5.7 秒（242 MB）で overrun（42.5 MB/s）。
- **対策**: 中継のサービスを `Nice=-20` にした（`fprobe-relay.service`、テスト 1 件）。jupyter・clear_pl_statefile の再起動と、2 コアを使い切る Python 2 本（20 秒）を同時にかけた中で、25 MS/s・40 秒が、`-20` で 3 回中 3 回（各 2 GB）欠けなし、`-10` では 2 回中 2 回が溢れた（15.8 秒・26.9 秒）。上げる前は、jupyter の再起動だけで溢れる。ボードでは systemd の unit を入れ替えて確認済み。**実際の再起動の後（4 回目の再起動、reboot は JTAG なしで通った）に、PL を書いて +131 秒から +464 秒まで毎 30 秒に 25 MS/s の 8 秒を流して 11 回中 11 回欠けなし**（+131 秒は CPU の idle 0 %・ロード 3.9 で、`Nice=-20` なしでは +122 秒に溢れた時点）。softirq（NIC）は nice の対象外なので、`-20` でも余裕は約 15 % しかない。
- 結果の行が出ない（以前の「6 回目」と、この負荷試験の 1 回）: `soak2.py` に例外処理は無く、行が出ないのは例外で終わった場合だけ（検索が例外の表示を隠していた）。負荷の中で、ストリームが 2 秒届かない（`TimeoutError`）などと見ているが、その 2 回の例外の種類は取っていなかった。PC に CPU 使い切りの負荷（10 本）をかけた実機の試験では、`TimeoutError`（ch 0 の応答が来ない／ストリームが 4442640/4800016 バイトで止まった）が出ている（過度な負荷）。例外を表示する版で、PC に同じ負荷をかけて 25 MS/s の 40 秒を 3 回流したが、3 回とも欠けなしで例外は出ず、再現しなかった。原因は未確認。

### 10.16 使うチャンネルだけ詰めて流す（la_pack、2026-10-31。実機で確認）
- 目的: 50 MB/s の壁（10.12〜10.14）の下で、速いサンプルレートを流す。**情報を捨てない**方針（ユーザの指示）で、無損失の手だけを採る。間引きは入れない。
- 仕組み: エンコーダ（`la_encoder`）の手前に詰め段 `la_pack` を置く。`pack` = 1・2・3 で、下位 8・4・2 ビット（ch 0〜7・0〜3・0〜1）だけを使い、連続する 2・4・8 サンプルを 1 つの 16 ビットの語にする（時間の古いサンプルが下位）。
  エンコーダ・DDR・リング・中継・PS の経路は変えない。語が揃うまで出さないので、データ量が 1/2・1/4・1/8。RLE とは併用しない（RLE は 16 ビットの値の繰り返し）。`pack = 0` は入力をそのまま通す（待ち 0 周期）。
- 指定: CSR `la_deep.control.pack`（ビット 4〜5、run の間は変えない）。ケイパビリティ `la_pack`（FEATURES ビット 12。外部メモリのある構成だけ。今は `fprobe_pynq_deep` だけ）。ホストは `DeepAnalyzer.stream(pack_channels=8|4|2)`（既定 None = 16 ch）。
  合わない値は `ValueError`、rle との併用は `ValueError`、ケイパビリティが無い構成は `RuntimeError`（黙って詰めない）。選んだチャンネルは 1 サンプルも欠けない。**選ばなかった上位のチャンネルは記録されない**（ユーザが明示して選ぶ）。
- ホストの解読: `StreamChunk` に `pack`。`samples()`・`length`・`transitions()` は、語ごとでなくサンプルごとに展開する。`LaStream` のサンプル数は語数 × 2^pack。
- 確認（シミュレーション）: `la_pack` 単体（4 件）、`la_deep_buffer` を通して 8・4・2 ビットのカウンタが、展開すると欠けも重複もなく 1 ずつ増える（受け手が止まる条件つき）。ホストは偽のデバイスで 11 件。ホスト全体 3138 通過（失敗 22・エラー 78 は基準と同じ）。
- 確認（実機、PYNQ-Z2、Vivado 2025.2、ビルド約 12 分、sys_clk Fmax 107.1 MHz・TNS 0。ID 458d03d98241f2be）: 欠けなし（overrun なし・lost_frames 0・サンプル数がレート × 時間と一致）。

  | 構成 | データ量 | 60 秒 |
  |---|---|---|
  | 16 ch・25 MS/s | 50 MB/s | 11 回中 11 回（10.13・10.14） |
  | 8 ch・50 MS/s | 50 MB/s | 2 回（各 3,015 MB、30 億サンプル） |
  | 4 ch・100 MS/s | 50 MB/s | 2 回（各 3,015 MB、60 億サンプル） |
  | 2 ch・100 MS/s | 25 MB/s | 20 秒 1 回 |
  | 8 ch・25 MS/s | 25 MB/s | 10 秒 1 回 |

  実機の試験 `test_packed_stream_keeps_every_sample_at_the_rate_the_unpacked_stream_cannot_reach`（8 ch・50 MS/s、4 ch・100 MS/s、2 ch・100 MS/s の各 10 秒）が通る。
- 時間無制限の持続は、理屈（速度が一定で受け取りの上限以下なら、バッファは溜まらない）と 60 秒の実測まで。**9 分間の実測はユーザの指示で行っていない**。DDR のリング 32 MB は 0.6 秒ぶんで、バッファで時間を稼ぐ形ではない。
- 限界: 実機の入力は何もつないでおらず（信号は一定）、中身の並びの確認はシミュレーションのみ。外部ピンの実信号での確認は、配線測定の待ち（docs/hardware-wiring-request.md）。余裕は 50 MB/s の構成が小さい（2 コアが約 85 %）。長時間・PC が忙しいときは、25 MB/s の構成（2 ch・100 MS/s、8 ch・25 MS/s）のほうが安全。
- 無損失の手のうち、まだ入れていないもの: 適応 RLE（変化の多い信号は RAW、少ない信号は RLE を拍ごとに選ぶ。信号次第で効果が読めず、実信号の測定が先）。

### 10.17 外部ピン入力の限界の測定: 試験用の方形波（la_testgen、2026-10-31、実機で測定）
- 目的: 内蔵ロジアナ（fprobe_pynq_cap、取り込み 300 MHz）が、外部ピンの実信号を、どの速さ・どの幅のパルスまで正しく取れるか。配線なしの selftest（内部信号）では、入力のバッファ・配線・ピンの限界は測れない。
- 部品: `la_testgen`（cap_clk の領域）。周期（cap_clk の周期の数、2〜4095）・high・edge（0 = 立ち上がりで変える、1 = 立ち下がりで変える = 半周期 1.67 ns 遅れる）。出力は RPi ヘッダ 32 番（GPIO12、ピン B20、DRIVE 8・**SLEW FAST**）。有効にしたとき以外は Hi-Z（OBUFT）。CSR `la_cap.testgen`・`testgen_period`・`testgen_high`、ホストは `LogicAnalyzer.testgen(period, high, edge)`・`testgen_off()`（範囲外は断る）。
  出力と取り込みは同じ MMCM のクロックなので、**位相が固定**される。そのため、edge 0・1 の 2 通りで測る。
- 作る途中の失敗: 最初の版は、16 ビットの比較・引き算を 1 周期で行い、cap_clk の setup が −3.4 ns で不合格だった。丸めと引き算を数段のレジスタに分け、出力のカウンタを「ゼロまで数える下りカウンタ」（1 の区間と 0 の区間で読み込み直す）にし、周期を 12 ビットにして解消。新しい設定が届くたびにカウンタをやり直す（古い設定の数え残しを持ち越さない）。ビルドは、`Default` の配置が −0.007 ns（既存の取り込み部の 1 本）で不合格、`Explore` が合格（WNS +0.006 ns、cap_clk Fmax 300.571 MHz、sys_clk Fmax 100.070 MHz）。ID b00491cd2f2483e1（ビルド C:/fw48c）。
- 結果（RPi ヘッダ 32 番 → PMOD JB の 1 番（ch 10 = in0）のジャンパ線 1 本。GND の 2 本目は未確認）:
  - 方形波（50 % 近く）: 周期 20 以上（15 MHz 以下）は、edge = 1 で、1 と 0 の連続の長さが**設定どおり**。edge = 0 は、1 サンプル（3.3 ns）ずれる（1 の区間 +1、0 の区間 −1。合計は周期と一致 = サンプルの欠けも重複もない）。周期 6〜12（25〜50 MHz）は、どちらの edge も同じく ±1 サンプルずれる。周期 5（high = 2）は一致、周期 2〜4 と 5（high = 3）は、波が**見えないものがある**。
  - 狭いパルス（周期 40）: 1 の幅 1 サンプル（3.3 ns）は**一度も見えない**（204 個中 0）。2 サンプル（6.7 ns）は見えるが長さが 1 か 2。3 サンプル（10 ns）は edge 0 で一致、edge 1 で 2 か 3。**4 サンプル（13.3 ns）以上は、edge = 1 で、すべて見えて幅が一致**（4・5・6・8 サンプルで確認）。0 のパルスは、どの幅も 1 サンプル短く見え、1〜2 サンプルは見えない。
- 読み取り（事実と解釈を分ける）: **このループバック全体（出力の駆動・ジャンパ線・入力のバッファ）の限界**が、約 13 ns のパルス幅（約 40 MHz の 50 % の方形波）で、10 ns 前後は幅が ±1 サンプル、7 ns 以下は不安定、3.3 ns は見えない。立ち上がりが早く、立ち下がりが遅く見える（1 の幅が長く、0 の幅が短く見える）一定の差がある。
  **取り込み回路だけの限界は、ここからは言えない**（出力の駆動・線の長さ・入力のバッファの影響を分けていない）。分けるには、より速くきれいな信号源（案 A: 信号発生器、案 B: 別の FPGA）か、GND の 2 本目・線を短くした再測定が要る。
- 実機の試験: `gateware/tests/hil/test_pynq_cap_testgen_hw.py`（9 件通過。ジャンパ線がつながっていなければ skip）。

### 10.18 律速の測定（B0、2026-11-01、実測。コードは変えていない。設計 `2026-11-01-bandwidth-observation-design.md` 1.4）
条件: PYNQ-Z2（PL は `fprobe_pynq_deep`、ID dd3c4fe482275cd9、中継は動かしたまま）、PC は Windows 11・12 論理 CPU、同じ LAN。PC の設定は変えていない。
PYNQ の設定は、`napi_defer_hard_irqs`・`gro_flush_timeout` を比べるために一時的に 8・500000 にし、測った後に 0・0（元の値）に戻したことを読み戻して確かめた。`ethtool -K` は使っていない。

- Windows では、タイムアウト付きのソケット（`settimeout`）に `MSG_WAITALL` を渡すと `WSAEOPNOTSUPP`（10045）。使うならブロッキングのソケットにする。

**導出**:
- **バイト数に比例する部分（送り手の CPU1 の複写）**: 同じ 1 回の大きさで `send` − `MSG_ZEROCOPY` = 16 KB 5.0・32 KB 5.2・64 KB 5.3・256 KB 4.3 ms/MB（約 190〜230 MB/s の複写）。**CPU1 の送信の時間の約 3 割**。残りの約 10 ms/MB（1 MB は 690 セグメント、1 つ約 14 µs）は複写以外。
- 中継のいまの道は、これに CPU0 の NEON の読み（約 9 ms/MB）が加わる。25 MS/s で CPU0 の idle が 0 % なので、**いまの壁は CPU0（読み + softirq）と CPU1（送信）の両方**。ゼロコピーは CPU0 の読みと CPU1 の複写の両方を消し、合成の試験の上限は 97〜100 MB/s（遅らせあり）。
- 1 回の大きさ: ゼロコピーでも 16 KB は 64 KB より 1 MB あたり 約 1.2 ms 重い。64 KB と 256 KB の差は 0.2 ms/MB。中継の 1 回の `sendmsg`（最大 8 スロット）は、ゼロコピーにするなら 64 KB 以上にまとめるのがよい。
- PC: 実際の NIC で、ホストと同じ作りの受信が 90 MB/s を 1 コアの約 4 割で受けた。10.14 の「PC の受信の能力 56〜61 MB/s」は、送り手の sendbench（16 KB の `send`）が、この測定で 49〜65 MB/s が上限だったので、**送り手が律速だった可能性が高い**（同じ時間帯の比較ではない）。

**推測（確かめていない）**:
- ゼロコピーで残る約 10 ms/MB には、セグメントごとの処理（GSO の分割・macb の送信・qdisc）のほか、DMA のためのキャッシュの書き戻し（L1・PL310 の行ごとの操作。中身の量に比例）と、送り手がソケットを持っている間に後回しにされた ACK の処理（送り手の CPU で動く）が含まれるはず。perf が無く、分けていない。
- 遅らせありの `send` の CPU0 の softirq（1 MB あたり約 8 ms）がゼロコピー（約 3 ms）より重い理由は分からない。ACK が約 4 倍多いことと、複写で作ったページの解放が CPU0 で起きることが候補。
- リングのページを TCP にゼロコピーで渡すには、`/dev/mem` の mmap（`VM_PFNMAP`）は使えない（上の EFAULT）。設計 1.3.1 の (a)・(b) のカーネルモジュールが要る。`/dev/mem` からの普通の `send`（複写 1 回で `tcp_ring` を通さない）は、カーネルの複写が書き込み結合の領域を読むので遅く（64 KB・遅らせなしで 18.1 ms/MB。普通のバッファからの `send` は 16.1）、CPU1 の律速を悪くする。
