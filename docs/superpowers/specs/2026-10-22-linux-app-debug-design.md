# 組み込み Linux のアプリのデバッグの統合（R26）

日付: 2026-10-22。利用者と決めた内容（ブレインストーミング）。技術の選び方で利用者が任せた所は「Claude の判断」と書く。

## 1. 目的と意図

- 組み込み Linux（Cortex-A 等）のユーザーアプリは、いまは printf デバッグしか手段が無い。体系的なデバッグの手段を fprobe に統合する（利用者）。
- uprobes・gdbserver など Linux の便利な仕組みをできる限り取り入れる（利用者）。
- fprobe に組み込むことで、従来のデバッガに無い最大の価値を生む（利用者）。
  - 価値の中心は「アプリの出来事と、ハード・FPGA の信号を、同じ時間軸で見る」こと（Claude の判断。利用者が概ね同意）。
  - 止めて調べる（gdbserver）と止めずに見る（uprobes 等）を 1 つの道具にまとめる。
- 対象は特定のアプリではなく何でも（利用者）。1 つの機器の中に複数の SoC と FPGA が同居する大きなシステムまで想定する（利用者）。

## 2. 目標・目標でないこと・失敗とみなすこと

目標:
- Linux のアプリの関数の出入り・引数・戻り値を、アプリを作り直さずに（printf を足さずに）時刻付きで記録する。
- その出来事を、fprobe の記録（ロジアナ・FPGA の観測・MCU の出来事）と同じ時間軸に並べる。
- gdbserver による止めて調べるデバッグを、画面・AI から使う。
- 準備（エージェントの導入・プローブの設定・シンボル）を AI が API で自律的に行える。

目標でないこと:
- 慣れていない人向けに設定を隠すこと（利用者）。画面は分かりやすく、ただし何をしているかは見え、変えられる。
- Linux のカーネルのデバッグ（カーネルを止める・カーネルのシンボルでのステップ）。カーネルの出来事を「見る」（ftrace）は入れる。

失敗とみなすこと:
- 推測で補った値を事実として出すこと（CLAUDE.md の原則）。ターゲットのカーネルに機能が無ければ、「無い」と使える代わりの手段を事実で返す。
- 時刻の換算の不確かさを出さないこと。
- 設定や操作が画面・アクティビティから見えないこと。

## 3. 決めたこと

### 3.1 2 つのデータの道（A と B）

| | A: ネットワーク | B: JTAG でメモリから吸い上げる |
|---|---|---|
| 位置づけ | 必須。操作（SSH）もこの道 | **必須の機能として完成度高く**（利用者: 「ターゲットには基本 JTAG はあるつもり。必ず B は完成度高く」） |
| 出来事の受け取り | エージェント → TCP → デーモン | エージェントが物理メモリのリングに書く → fprobe が JTAG の MEM-AP で CPU を止めずに読む |
| 強み | 配線不要。速い（Ethernet）。どの基板でも | ネットワーク・カーネルが止まっても最後の出来事まで読める。通信の負荷をかけない |

- どちらで受けても同じ記録の形（後述の出来事の形）にする。使う側（画面・AI）は道を意識しない。
- 両方を同時に使ってもよい（同じ出来事を重ねて受けたら、出来事の番号で 1 つにする）。
- B のリングは、キャッシュしない物理メモリに置く（Claude の判断）。置き場所は、カーネルの予約（reserved-memory または起動の mem=。PYNQ は既に mem=480M）を使い、番地は使う側が明示して渡す（推測で探さない）。
- B は CPU を止めずに読むので、ARMv8 の Pi 4 のように fprobe が JTAG で止められないコアでも、MEM-AP が使えれば使える。
- **B の速さ（利用者: JTAG の速さが性能を決めるなら、fprobe の JTAG も速くする。そのために回路を外すなら相談）**:
  - B の性能（取りこぼさずに読める出来事の量）は、JTAG での MEM-AP の読み出しの速さで決まる。
  - 今の事実: SWD 25 MHz で PC の pyOCD から読むと 0.87 MB/s（2026-10-16）。頭打ちは線の速さより PC との往復と見る（未確認）。
  - 段階 2 で、まず JTAG（と SWD）での読み出しの速さを実機で測る。
  - 測った事実（2026-10-22、Primer の JTAG → Pi 2B の APB-AP、1 語ずつ DRW を PC から読む）: 1 語 約 0.24 ms（16 kB/s）。
    5・10・15 MHz で変わらず（PC との往復で決まる。線の速さではない）。1 MHz は 0.34 ms。25 MHz では DAP が答えなかった
    （ジャンパ線の信号の質か Pi の JTAG の上限かは未切り分け）。よって、まとめて読む（CMSIS-DAP のブロック転送、または
    FPGA の回路が読み続けて流す）ことが道 B の速さの前提になる。
  - 足りなければ、FPGA の回路が自分でリングを読み続けて PC へ流す形にする（DAP サンプラの延長。PC との往復を無くす）。
    あわせて JTAG の線の速さの上限も上げる。目標は J-Link の RTT（公表で約 2 MB/s）を超えること。
  - そのために Primer の回路を外す必要が出たら、作る前に利用者に相談する。

### 3.2 時刻合わせ（両方を持つ。利用者）

- 出来事にはターゲットの時計（CLOCK_MONOTONIC_RAW の ns）を付ける。
- かんたんな方（ミリ秒）: ネットワークの往復で組を作る（デーモンが問い、エージェントがその時の時計を返す。不確かさ = 往復の半分）。
- 正確な方（マイクロ〜ナノ秒）: エージェントが GPIO を切り替え、その時の時計を記録する。fprobe のロジアナがその辺を見た時刻と組にする。
- 換算はモジュール化の合成（timesync.py・merge.py）をそのまま使う。どちらの方法で合わせたかと、不確かさ（量子化・組の残差・最も近い組までの距離）を事実として出来事に付ける。

### 3.3 部品

1. **エージェント（ターゲットの Linux の上）**: C で書く小さなプログラム（Claude の判断）。
   - プローブの設定・出来事の読み出し・リングへの書き込み・時刻合わせに答える。
   - 作り方: ターゲットに gcc があればその場で、無ければクロスで（どちらで作ったかは記録する）。
2. **関数の出入りを取る仕組み（カーネルにあるものを段で選ぶ。どれを使ったかは出来事に書く。Claude の判断）**:
   1. uprobes: tracefs の uprobe_events（CONFIG_UPROBE_EVENTS）。BPF（BTF のあるカーネル）があれば引数の読み出しの強い方として選べる。
   2. perf のハードのブレークポイント（PERF_TYPE_BREAKPOINT、CONFIG_HAVE_HW_BREAKPOINT・PERF_EVENTS）: カーネルの作り直し無しで、
      ユーザーのアプリの番地の実行を止めずに時刻付きで取る。同時に仕掛けられる数は CPU のブレークポイントの数まで（Cortex-A9 は 6）。
   3. ptrace（gdbserver と同じ）: 一瞬止めるので振る舞いが変わる。そのことを出来事に書く。
   - 事実（2026-10-22、PYNQ の標準のカーネル 6.6.10-xilinx）: FTRACE・KPROBES・UPROBES が無い。BPF_SYSCALL はある（JIT 無し）、
     PERF_EVENTS・HW_PERF_EVENTS・HAVE_HW_BREAKPOINT・DEVMEM・DEBUG_FS はある。gcc・gdb・strace はある、gdbserver・bpftrace・perf は無い。
     よって PYNQ では 2・3 を使う（uprobes を使うにはカーネルの作り直しが要る。利用者の判断）。
   - **事実（2026-10-22、PYNQ で試した）**: 2 で別のプロセスの関数（Thumb、番地 &~1・長さ 2）に実行のブレークポイントを付けると、
     そのプロセスが CPU を使い切って進まなくなった。kill -9 の後、SSH・シリアルとも応答しなくなった（ping だけ応答。電源の入れ直しが要った）。
     よって 2 は「そのカーネルで使えるかを確かめてから使う」もので、既定では使わない。使う側が明示して選んだときだけ使い、
     この事実を API の説明に書く。段階 1 の取り出しの道具は 1（uprobes）と 3（ptrace）にする。
3. **デーモンの API（`linux.*`。MCP にも同じ）**:
   - つなぐ・能力: `linux.connect`（ホスト・利用者・鍵）、`linux.capabilities`（カーネルの設定の事実: uprobes・BPF・BTF・perf・ftrace・gdbserver の有無、版）。
   - エージェント: `linux.agent.deploy` / `status` / `stop`。
   - プローブ: `linux.probe.add`（バイナリ・関数または番地・取り出す引数）/ `list` / `remove`。
   - 記録: `linux.trace.start` / `stop`（道 A・B を選ぶ。B はリングの番地を明示）。時刻合わせ: `linux.sync`（方法を選ぶ）。
   - 止めて調べる: `linux.gdb.*`（gdbserver をアプリにつける・起動する。デーモンが RSP を中継し、画面・AI・手元の gdb から使う）。
   - そのほか: `linux.perf.*`（サンプリング）、`linux.ftrace.*`（カーネルの出来事）、`linux.log`（journal・syslog）、`linux.core.collect`（core dump の回収）。
4. **シンボル**: アプリと共有ライブラリのバイナリをターゲットから取り寄せて、デーモンの手元に置く（sysroot の置き場所）。取り寄せたものと元の場所を記録に残す。
5. **記録**: Linux の出来事は、ターゲットごとの「子の記録」として fprobe の記録に合成する（stream は `<ターゲット名>.uprobe` 等）。
6. **画面**: Linux のパネル（つないだターゲット・能力の事実・プローブ・gdb）、時間軸の Linux の行。設定はすべて見えて変えられる。

### 3.4 段階

1. **段階 1（A の土台）**: つなぐ・能力の事実・エージェント・tracefs の uprobes・道 A・ネットワークの時刻合わせ・記録への合成・画面の最小限。
2. **段階 2（B を完成度高く）**: キャッシュしないリング・JTAG の MEM-AP での読み出し（止めずに）・読み出しの速さを測って上げる（FPGA の回路で読み続ける）・GPIO の時刻合わせ・ネットワークが落ちた／カーネルが固まった後も読めることの実機の確かめ。
3. **段階 3**: gdbserver の統合（RSP の中継、画面・AI から）。
4. **段階 4**: perf・ftrace・journal・core dump。
5. **段階 5**: 複数の SoC と FPGA の大きなシステム（モジュール化の合成で 1 本の時間軸）。

### 3.5 確かめに使う機材

- PYNQ-Z2 の PS（Cortex-A9、PYNQ の Linux。SSH で入れる。mem= の予約あり）: 段階 1 の主な確かめ。
  - B: fprobe の JTAG の口から PS の DAP には今は届かない。PL の EMIO PJTAG で PS の JTAG を fprobe の回路へつなぐ案を、段階 2 で確かめる（B は止めずに読むので、PS の中継は止まらない見込み。未確認）。
- Raspberry Pi 2B（Cortex-A7）・Pi Zero（ARM1176）・Pi 4（Cortex-A72）: 利用者の手元にある。JTAG は GPIO の代替機能で出す（配線は利用者）。**段階 2 の B の主な確かめは Pi 2B**（利用者、2026-10-22）。
  - **事実（2026-10-22、Pi 2B を Primer の J12（DVP）に JTAG でつないで読んだ）**: JTAG-DP（IDCODE 0x4BA00477）の AP は
    AP0 = APB-AP（IDR 0x24770002、BASE 0x80000000）だけで、AHB-AP / AXI-AP は無い。よって Pi 2B では止めずに読む道 B は
    できない（§3.6 の扱い:「止めずには読めない」と事実を返し、短く止めて読むのは使う側が選んだときだけ）。
    止めずに読む道 B を実機で確かめるには、システムのメモリにつながる MEM-AP を持つ SoC が要る（候補: PYNQ の Zynq の DAP。
    fprobe の JTAG から届かせる方法は未決。利用者と相談）。
  - Pi 2B の Raspberry Pi OS 13（カーネル 6.18.50+rpt-rpi-v7）: UPROBES・UPROBE_EVENTS が無い。FTRACE・KPROBES はある。
    gcc あり、gdbserver 無し。gcc の既定は ARMv6 で、Thumb の題材は -march=armv7-a+fp -mthumb で作る。

### 3.5.1 Zynq（PYNQ）で止めずに読む道 B の候補（2026-10-23 の調べ。未確認のものはそう書く。利用者と相談して決める）

1. **fprobe（Primer）の JTAG → Zynq の PS の DAP（AHB-AP）**: Zynq-7000 の DAP にはシステムのメモリにつながる AHB-AP があるとされる
   （UG585 の debug の章。実機では未確認）。PYNQ-Z2 の基板の JTAG は FT2232 の 1 本だけで、外付けの JTAG の口は無い見込み。
   - Zynq の「独立 JTAG」（PS の DAP を PJTAG = MIO 10〜13 か EMIO に出す。起動時のストラップ MIO2 で選ぶ）にすれば、EMIO で PS の
     JTAG を PL の端子（PMOD 等）に出し、Primer からつなげる。PYNQ-Z1 は JP2 のジャンパで独立 JTAG になると資料にある。
     PYNQ-Z2 に同じジャンパがあるかは未確認（フォーラムで「下の 4 ピンのヘッダ」の問いがあり、答えは UG585 の 153〜154 ページ）。
   - ジャンパの付け替えは利用者の手作業。独立 JTAG にすると、基板の USB の JTAG からは PS が見えなくなる（PL の書き込みはできる）。
2. **PYNQ の PL（fprobe の回路）が AXI で DDR のリングを読む**: PL から PS の HP ポートで DDR を読める（深いバッファで使っている道）。
   CPU を止めず、速い。ただし PC への道は PYNQ の Linux の上の中継なので、カーネルが固まると PC に届かない
   （ネットワーク・カーネルが止まっても読む、という道 B の目的は満たさない。カーネルが生きている間の高速の道としては使える）。
3. 追加購入（STM32MP1 等、AXI-AP があるはず。未確認）は、今の方針（追加購入なし）では選ばない。

### 3.6 作り手の確認（builder check）で決めたこと（Claude の判断）

- **SSH**: Windows 標準の OpenSSH（ssh）を子のプロセスで使う。利用者の ~/.ssh と ssh-agent をそのまま使い、鍵はリポジトリに置かない。新しい依存（paramiko 等）は足さない。
- **道 A の向き**: デーモンが SSH でエージェントを起動し、その SSH の中（標準入出力、または ssh のポート転送）で出来事を受ける。PC 側にポートを開かない（PC のネットワーク・ファイアウォールの設定を変えない、§4）。§3.1 の「エージェント → TCP → デーモン」はこの意味で読む。
- **uprobes の時計**: tracefs の trace_clock を mono_raw にする。無ければ「無い」と事実で返し、使った時計の名前を出来事に書く。
- **引数の取り出し**: tracefs の fetch-arg（`%r0`・`+0(%sp):u32` 等）を明示して受け取る。呼び出し規約から「第 1 引数 = r0」と決めつけない。DWARF から作る場合は、DWARF の location が言える分だけにする。作った uprobe_events の行は、そのまま API と画面に出す。
- **ネットワークの時刻合わせ**: 往復の半分（ターゲット ↔ PC）と、PC ↔ fprobe の時計の対応（ClockMap）の不確かさを、別々に出す（一つにまとめない）。
- **GPIO の時刻合わせ**: 辺と記録の対応は、番号を符号化したパルスの並びで取る（辺の数え方を推測しない）。数が合わなければその事実を返す。ロジアナのチャンネルと GPIO の番号は、使う側が明示して渡す。
- **エージェントの作り方**: 段階 1 は PYNQ の上の gcc で作る。Linux 用のクロスコンパイラは段階 2（Pi）で足す。無ければ事実で返す。どちらで作ったかは記録する。
- **時刻の換算**: timesync.fit_parent の遅れの定数（FPGA の同期の線の RX/TX）を、引数で渡せるようにする（Linux の組では値が違う）。
- **B の読み出し**: 止めて読む今の Cortex-A の道（arm_debug.read_memory）は使わない。システムのメモリにつながる MEM-AP（AHB-AP / AXI-AP）を AP_IDR で探し、止めずに読む新しい道として作る（raw_dap の MEM-AP の読み出しが土台）。
  - システムのメモリにつながる MEM-AP が無い SoC（ラズパイは APB-AP だけという情報がある。未確認。Pi 2B をつないだら最初に AP の一覧を読んで確かめる）: 「止めずには読めない」と事実を返す。CPU を短く止めて読み再開する方法は、使う側が明示して選んだときだけ使い、止めた回数と時間を記録に残す。
- **カーネルが固まったときの B の範囲**（利用者が (a) を了承、2026-10-22）: アプリが FPGA のレジスタ等を触ってシステムごと固まると、道 A は最後の出来事を失う。B はリングに書き終わった分を最後まで読み、書きかけで欠けたかもしれない範囲（書き位置の前後）をそのまま事実として出す。カーネルの中の状態の解析はしない。
- **記録中の表示**: Linux の出来事は、記録中にも画面の時間軸に出す（その時点の換算で入れ、元のターゲットの時刻も残す）。記録の後の合成（merge）も使える。

## 4. 制約

- CLAUDE.md の原則: 本体にヒューリスティックを入れない。特定のターゲットのための機能を足さず、汎用の機能（MEM-AP の読み出し・GPIO の時刻合わせ・tracefs）で作る。ボード固有の手順はプラグインにする。
- 操作はデーモンの調停と記録を通る（人と AI の操作がアクティビティに見える）。
- SSH の鍵はリポジトリに置かない。PC のネットワークの設定は変えない。

## 5. 作り手に任せること

- エージェントの内部の作り（スレッド・バッファの大きさ）、線上の形式の細部、リングのヘッダの細部（版・magic・書き位置・時計の情報を含むこと）。
- 画面の配置の細部。
