# U45 RTOS の対応の拡大: RTX5（CMSIS-RTOS2）

ギャップ分析（`docs/reports/2026-10-18-gap-analysis.md`）の U45 は「ThreadX・RTX5・µC/OS-III・NuttX と Zephyr の完全化」。
このうち、この版で足すのは **RTX5**。

## 1. どれから足すか

| RTOS | 試せる本物 | 判断 |
|---|---|---|
| RTX5 | この PC の Zephyr のワークスペースに CMSIS の RTX5 の本物のヘッダ（`rtx_os.h`、V5.5.0）とライブラリがある | **足す**。Keil MDK・CMSIS-Pack の標準の RTOS（KEIL・OOCD・SEG-65 の項目）。本物のヘッダで DWARF の配置を作れる |
| ThreadX | ソースが手元に無い（取ってくれば MIT。今回は追加の取得をしない） | 残す。次に足す候補（CUBE-08・VSC-09・TRX-01/03・TZ-14 が求める） |
| µC/OS-III・NuttX | 手元に無い | 残す |
| Zephyr の完全化 | 既にスレッド・オブジェクト（U08）・ヒープの要約がある。実ビルドの ELF は手元に無い | 今回は触らない |

## 2. 口（既存の層に合わせる）

`fprobe.rtos.base.KernelAwareness` を継承した `fprobe.rtos.rtx5.RTX5` を `fprobe.rtos.open_rtos` の表に足す
（`detect` は `"rtx5"`）。API・MCP の `rtos.*` は RTOS に依らないので、そのまま RTX5 で動く（summary の種類の列を更新）。

- 検出: 大域変数 `osRtxInfo` と型 `osRtxThread_t`、`osRtxInfo_t.thread.run.curr`。
- スレッドの集め方（RTX5 は全体の一覧を持たない）: 実行中 `run.curr`、準備完了 `ready.thread_list`（`thread_next`）、
  時間待ち `delay_list`・時間切れの無い待ち `wait_list`（`delay_next`）、終わり `terminate_list`、アイドル・タイマのスレッド。
  id が 0xF1 でないものは警告して外す。巡回・数の超過は警告して止める。
- 状態: 下位 4 ビット（Ready・Running・Blocked・Terminated）。Blocked で待ちの種類が無い = `osThreadSuspend`（SUSPENDED）。
  待ちの種類（上位 4 ビット）は共通の言葉に: delay / join / notification（スレッドフラグ）/ event（イベントフラグ）/
  receive（ミューテックス・セマフォ・メモリプール・メッセージの受け取り）/ send（メッセージの送り）。
- 待っているもの: `thread_prev` を辿り、id がスレッドでない構造体（オブジェクトの `thread_list` はスレッドの `thread_next`
  と同じ位置にあり、先頭の待ち手の `thread_prev` はオブジェクトを指す）。名前はオブジェクトの `name` → シンボル → 番地。
  ミューテックスなら持ち主。残りのティックは `delay_list` の差分の和。
- 優先度: 大きい方が高い（`priority_order = 1`）。元の優先度は `priority_base`。
- スタック: `stack_mem`・`stack_size`。底の語が `osRtxStackMagicWord`（0xE25A2EA5）でなければあふれ（notes に書く）。
  その上の 0xCC の塗り（`osRtxConfigStackWatermark`）から最大の使用量。
- 保存された文脈: PendSV（irq_armv7m.S）の積み方 = `thread.sp` から [s16〜s31]、r4〜r11、ハードのフレーム。EXC_RETURN は
  `thread.stack_frame | 0xFFFFFF00`（`fprobe.rtos.cortexm.read_fp_first_context`。FreeRTOS の積み方とは FP の位置が逆）。
  巻き戻しは `osThreadExit`（新しいスレッドの LR）で止める。
- オブジェクト（`fprobe.rtos.rtx5_objects`）: mutex（持ち主・継承・再帰・ロックの数）・semaphore（count・max）・event_flags・
  memory_pool（ブロックの数）・message_queue（数・最大・空き）・timer（動いているか・周期・残り・呼ぶ関数と引数）。
  集め方は 変数（静的な制御ブロック）・動いているタイマの列・スレッドが持つミューテックスの列・スレッドの待ち。
  共通のメモリから確保され、どこからも辿れないもの（止まったタイマ・待ち手の無いセマフォ等）は見えない（RTX5 に一覧が無い）。
- サンプラ（時間軸・逆転の推移）: いまのスレッドの語 `run.curr`、保存された SP `thread.sp`、ミューテックスの
  `owner_thread`・`thread_list`（差 0、空は 0）。
- ヒープ（`osRtxInfo.mem.common` の可変長のプール）は構造体が rtx_memory.c の中だけで DWARF に無いので、今回は出さない。

## 3. 試験

`host/firmware/rtx5_shape/`: 本物のヘッダ（`CMSIS-RTX/`、出典は SOURCE.md）の構造体で、止めたときの様子を .data に置いた
ELF（arm-zephyr-eabi-gcc で作る。RTX5 のカーネルそのものではない）。`host/tests/test_rtos_rtx5.py` が、9 つのスレッド
（実行中・準備完了 2・時間待ち 2・ミューテックス待ち・停止・タイマのスレッド・終わり）、待ち・残りのティック、スタックの
塗りと壊れた底の印、保存された文脈からの巻き戻し、オブジェクトと優先度の逆転を確かめる。

## 4. 付記: C4・C5 の判断（競合調査から）

- C4（静的なスタック使用量の解析、IAR-28）は U26 の `debug.stack.static`（`fprobe/stackusage.py`・`probe_stack.py`、
  MCP `debug_stack_static`）が既に満たす: .su か逆アセンブルの枠、最悪の深さと経路、再帰（cycles）・関数ポインタ・
  可変長の確保・ELF に無い呼び先は bounded=false と理由、根（リセット・例外・呼ばれない関数）と MSP の見積もり。
  新しく足すものは無い。
- C5（実行時の検査、IAR C-RUN、IAR-29・30）はギャップ分析で「対象外（コンパイラによる計装の機能）」。デバッガの汎用の
  機能ではなく、コンパイラ（gcc / clang の -fsanitize=undefined の最小の実行時 等）の領分。足さない。
  検査の結果を観測したいときは、既存の汎用の口（UBSan の最小の実行時が呼ぶ関数へのログのブレークポイント、
  `testpoint`、RTT / semihosting の出力）で足りる。
