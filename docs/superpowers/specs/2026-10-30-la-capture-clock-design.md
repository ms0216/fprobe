# ロジアナの取り込みを、速い別のクロックの領域に分ける（設計）

2026-10-30。状態: 案（実装は段階ごとに、試験が通ったものだけコミットする）。上位の検討: `2026-10-29-performance-limits-study.md` §2.2・§2.3。
対象: 全機能の基準の PYNQ-Z2。Primer と小さい FPGA は、同じ回路が比 1（今と同じ）で動く。

## 1. 目的と、なぜ

- ロジアナのサンプリングの細かさと時刻の分解能は、デバッグ対象の挙動を時系列で捉える力そのもの（優先度の最上位）。
- 今は、端子の取り込みからトリガ・記録まで全部が sys クロック（PYNQ 100 MHz）1 本。最高 100 MS/s、時刻の分解能 10 ns。
- sys 全体を速くする試み（コア全体の Fmax の改善）は、約 157 MHz で頭打ち（`2026-10-29-performance-limits-study.md` §3）。コアは大きく、配線が長い。
- ロジアナの取り込みは小さな回路（同期化・トリガの比較・エンコード）なので、コアとは別の速いクロックの領域に置けば、コア全体を速くせずに、
  取り込みだけ速くできる。部品の上限（DS187、速度グレード -1）: グローバルクロック 464 MHz、Block RAM 388 MHz。

## 2. 範囲

やる（段階 1〜3。§7）:
- 取り込み側のクロック `cap_clk`（sys の整数倍。同じ MMCM から作る）を足し、`la_filter`・`la_pulse`・`la_front`・（内蔵の）`la_capture` を cap 領域に移す。
- 設定（CSR）と結果（状態・トリガの時刻）の受け渡し。
- ケイパビリティの `la_sample_hz` を cap のクロックにし、PC 側が使う。

やらない:
- タイムベース（`time_count`）を速くすること。多くのモジュール（イベントの記録・割り込み書き込み・観測の口・クロストリガ・ボード間の同期）が sys の周期で
  数えた値を前提にしている。ロジアナの時刻の細かさは、トリガの時刻に「sys の周期の中の位置（位相）」を足して補う（§5）。
- 1 サイクルに複数サンプル（ISERDES）。取り込みを 1 サイクル 1 サンプルのまま速くする（段階 4 の候補。cap_clk の上限を超える細かさは、そこで扱う）。
- 深いバッファ（DDR へ書く経路）の cap 領域への移行（段階 3 の後。内蔵のロジアナで確かめてから）。

## 3. クロック

- PYNQ-Z2: MMCM 1 個から sys_clk と cap_clk を作る（同じ VCO から割るので、周波数が整数比で、位相がそろう関連クロックになる）。
  整数比 R と、作れる組（入力 125 MHz、DIVCLK = 5 で比較周波数 25 MHz、MMCM の VCO は 600〜1200 MHz、出力の分周は整数）:

  | R | VCO | sys（÷） | cap（÷） | 備考 |
  |---|---|---|---|---|
  | 2 | 1000 MHz（M = 8、DIVCLK = 1） | 100 MHz（÷10） | 200 MHz（÷5） | |
  | **3（既定）** | 900 MHz（M = 36） | 100 MHz（÷9） | **300 MHz**（÷3） | Block RAM（388 MHz）に収まる。内蔵のロジアナの BRAM も cap で動かせる |
  | 4 | 1200 MHz（M = 48） | 100 MHz（÷12） | 400 MHz（÷3） | VCO が上限（1200）ちょうど。Block RAM（388）を超える。試験の候補 |

  既定は R = 3（300 MHz）。cap 領域の回路は小さいので、R = 4 の配線の余裕は段階 3 の配線の結果で判断する。
- sys が 100 MHz 以外の構成（Primer の 100.2857 MHz 等）は、R = 1（cap_clk = clk）で、今と同じ回路・振る舞い。
- ボードの記述（`fprobe_gw/boards/pynq_z2.py`）の `sync_pll` に、cap 用の出力を足す（MMCM の解は `MmcmSolution`）。VHDL の定数
  （`pynq_z2_pkg.vhd`）との一致は、今ある試験 `test_vhdl_package_matches_board_definition` に cap の分を足して確かめる。

## 4. 領域の分け方

| cap 領域に移すもの | sys に残すもの |
|---|---|
| `la_filter`（ピンのグリッチフィルタ）、`la_pulse`（パルス幅のトリガ）、`la_front`（同期化・間隔・トリガの判定）、内蔵の `la_capture`（BRAM への記録） | CSR・CONTROL・DAP・タイムベース・イベント・クロストリガ・深いバッファ（段階 3 まで） |

つなぎ目（関連クロックなので、データは 1 段のレジスタで渡し、制約は関連クロックとして解析させる。非同期の FIFO や 2 段の同期は、本当に別の
クロックのもの（mem_clk）にだけ使う）:
- sys → cap（設定）: `run`・`arm`・`rate`・トリガの条件・フィルタ・パルスの設定。いずれも「止めてから変える」設定（既に約束）。`run` の 0→1 は、
  cap 側で同期してから取り込む（設定は run の前に cap 側のレジスタに入る順番で受け渡す: 設定を先に写し、最後に run）。
- sys → cap（信号）: `ext_trigger`（sys の 1 周期のパルス = cap の R 周期。cap 側で 1 周期のパルスにして取りこぼさない）、プローブのうち sys 領域の内部信号
  （`swdio_oe`・`dap_busy`）、ピン。
- cap → sys（結果）: `capturing`・`triggered`・`done`・`trigger_index`・`start_index`・`overrun`。`done` を立てる前に値を確定させ、sys 側は `done` の後に読む
  （値の確定 → 旗の順。旗は 2 段で受ける）。
- BRAM の読み出し（CSR の窓、`rd_addr` / `rd_data`）: BRAM は cap 領域。読みは sys から出す番地を cap 側で受け、`done` の後（記録が止まっている間）だけ読む約束にする。
  読みの経路は、番地を cap のレジスタに取り、データを sys のレジスタに戻す（関連クロック。2 周期以上かけてよい）。

## 5. 時刻

- `time_count` は sys のまま。他のモジュールの時刻の意味は変わらない。
- ロジアナのトリガの時刻 = **sys のタイムベースの値 + 位相**。位相は、トリガのサンプルが sys の周期のどの cap 周期にあたるか（0〜R − 1）。
  cap 領域で、sys の周期の頭を示す印（sys で 1 周期ごとに反転するビットを cap で受けたもの）から数える。
- ホストは、トリガの時刻（タイムベースの刻み）に位相 / R を足し、サンプル i の時刻 = トリガの時刻 + (i − トリガの番号) / `la_sample_hz`。
- 不確かさ: 印の受け取りの遅れは固定（段数）。値は試験と配線後の実測で決め、ケイパビリティの遅れの項目（`LA_*_DELAY`、`LA_PHASE_SPAN_TICKS`）として申告する
  （決め打ちの定数にしない。測った値を返す）。

## 6. 受け渡しの約束（インターフェース）

- `fprobe_core`: ポート `cap_clk`・`cap_rst` と generic `CAP_RATIO`（既定 1）を足す。`CAP_RATIO = 1` のとき、トップは `cap_clk => clk` をつなぎ、回路の振る舞いは今と
  ビット単位で同じ（既存の試験が変更なしで通ることで確かめる）。
- ケイパビリティ: `la_sample_hz` = cap のクロック（`sys_clock_hz` と別の値になる）。PC 側は `la_sample_hz` を使う（`la.py` の `la_sample_hz` の使用は既にある）。
  ただしグリッチフィルタの周期の換算（`la.py` の `clock = caps.sys_clock_hz`）は、フィルタが cap 領域に移るので `la_sample_hz` にする。
- `rate`（サンプル間隔 − 1）の単位は cap の周期。範囲（16 ビット）は変えない。最高のサンプリング = `la_sample_hz`（rate = 0）。

## 7. 段階

1. **配管（R = 1）**: `cap_clk`・`cap_rst`・`CAP_RATIO` と、cap 領域への受け渡しの部品を入れる。`CAP_RATIO = 1` で既存の試験がすべて通る。
2. **内蔵のロジアナを cap 領域に（R = 3）**: 受け渡しを 2 クロックの cocotb 試験で確かめる（R = 2・3・4）。PYNQ をビルドして、cap の Fmax と余裕を測る。
3. **ケイパビリティ・PC 側・ボードの記述**: `la_sample_hz`、フィルタの換算、トリガの時刻の位相。PYNQ のビルドの結果を記録する。
4. （候補）深いバッファの cap 領域への移行、1 サイクルに複数サンプル（ISERDES）。

## 8. 試験

- cocotb（2 クロック: sys と cap = R × sys、位相をそろえて始める）: `la_front` / `la_capture` を cap で動かし、トリガ・プリトリガ・取りこぼしなし（連続した値の列が欠けない）・
  `rate` の間隔・`run` の開始と中止・結果の受け渡し（`done` の後に値が確定）・位相（トリガの時刻が sys の周期の中の位置と一致）。
- `CAP_RATIO = 1` の回帰: 既存の試験がそのまま通る。
- 配線: PYNQ をビルドし、cap の領域の Fmax と、sys ↔ cap の経路の余裕。
- 実機（配線の待ち）: PYNQ の PMOD に既知の周期の信号を入れ、取り込んだ列の間隔から、サンプリングの周波数を実測する。

## 9. 未確認・リスク

- 関連クロックの受け渡しを、Vivado が「同じ MMCM の整数比のクロック」として正しく解析するか（`set_clock_groups` を入れず、自動の関連で解析させる）。配線の報告で確かめる。
- MMCM の VCO を 900 MHz にすること自体の問題（ジッタ・ロック）は、実機でロックを確かめる（PYNQ の LED でロックを見ている）。
- BRAM を 300 MHz で動かしたときの配線の余裕（上限 388 MHz）。
- ピンの入力の制約（IOB の FF、入力遅延）はまだ無い。チャネル間のずれは未測定（検討書 §5）。

## 10. 実装の記録（2026-10-30。段階 1〜3 のソフトの部分）

設計からの違いと、確かめた事実。

- **リセット**: `cap_rst` は作らず、sys のリセットを cap で 1 段受けて使う（`la_cap_domain` の `rst_c`）。リセットは「止めてから変える」運用の外なので問題ない。
- **時刻**: ピンが変わった取り込みの周期の番号 n = `trigger_time × R + trigger_phase − latency`（取り込みの周期の数）。`latency` は固定の遅れで、
  `la_cap` ブロックの `info.latency` から読む（CSR 0x0C80。値 = 5 − R。R は 2〜5。`tests/tb/la_cap_domain_tb.py` が R = 2・3・4 で測り、申告の値と一致を確かめている）。
  ホストの `Capture.trigger_cap_cycles` が n、`Capture.trigger_time`（タイムベースの刻み）は n を R で割って切り捨てたもの。
- **ケイパビリティ**: `cap_ratio` は TLV に出さず、ホストは `la_sample_hz / sys_clock_hz`（割り切れるとき、内蔵バッファの構成のみ）で知る。
  `la_cap` ブロックの `info.ratio` と突き合わせ、合わなければ読み出しを止める（`LogicAnalyzer.read`）。
  フィルタとパルス幅の換算は `la_sample_hz`（`Front.of`）。
- **取り込みのクロックの置き場**: `la_cap_domain` が、グリッチフィルタ・パルス幅・前段・BRAM 記録を cap 領域に持つ。`CAP_RATIO = 1` の構成は従来の回路のまま
  （`fprobe_core` の `internal_la`）。比 ≥ 2 は `LA_INTERNAL` のときだけ。
- **試験（シミュレーション）**: `la_cap_domain` 単体（R = 2・3・4）: 取り込みの周期ごとに 1 サンプル（欠けなし）、`rate` の間隔、トリガの時刻と位相が R × 2 通りのずらしで一定の差、
  run の再開・中止、フィルタ。コア全体（`CAP_RATIO = 3`、20 試験）: 内蔵ロジアナの捕捉・クロストリガ・FPGA の条件での停止・サンプラ一致が、取り込み領域に移しても通る
  （フィルタとパルス幅の長さは取り込みの周期で数えるので、試験側で比倍にした）。
- **ボード（PYNQ-Z2）**: MMCM を VCO 900 MHz（125 / 5 × 36）にし、sys ÷ 9 = 100 MHz（従来と同じ）、`CLKOUT1` ÷ 3 = 300 MHz（`cap_clk`）。
  `MmcmSolution.cap_div`（sys の分周を割り切ること、1〜128 を検査）、`Board.cap_clock()`、構成 `fprobe_pynq_cap`（`cap_ratio = 3`、`la_sample_hz` = 300 MHz）。
  GHDL の MMCM の模型は `CLKOUT1` を、`CLKOUT0` の立ち上がりごとに頭がそろう整数比のクロックとして出す（`xilinx_mmcm_tb.py` が確かめる）。
  他の PYNQ 構成も MMCM は新しい設定（VCO 900 MHz）になる。sys は 100 MHz のままで、`CLKOUT1` は使わない。

### 10.1 cap_clk 300 MHz のタイミングの詰め（PYNQ-Z2 `fprobe_pynq_cap`。Vivado 2025.2、xc7z020-1）

最初の回路は cap_clk 300 MHz に届かなかった。次の変更を重ねた（いずれもシミュレーションの試験は通したうえでビルドした）。

- **sys → cap の受け渡しを 1 段置く**: 時刻・トグル・設定は、sys 側の `_s` レジスタを通してから cap が受ける（cap の R 周期ぶん古くなる。`latency = 5 − R` はこの段を含む）。
  `rd_addr`・`ext_trigger`・`sys_bit_a`・`sys_bit_b` は段を置かない（ピンとの時間関係をずらさないため）。
- **la_capture**: 汎用 `FAST`・`RD_REG`。`FAST` はトリガの記録を 1 周期遅らせる（`ev` の段）。`RD_REG` は BRAM の出力にレジスタを足す。
  PRE・POST の数えは、残りの数 `left` と「`left = 1`」の旗 `left1`（更新と同時に決める）で行い、広い比較を毎周期の経路に置かない。
- **la_front**: 汎用 `FAST`。値一致とエッジを s1 から 1 周期早く評価（`match_r`・`edge_r`）、設定はレジスタで受け、サンプル間隔は降順のカウンタ。
  `FAST = false` は元の回路と周期まで同じ。
- **la_pulse**: 比較の旗（`min_f`・`max_f`）を自走させ、「設定 − 1」の計算を 2 段にした。

| 版 | cap_clk の Fmax | cap の遅れの不足の合計（TNS） | 未達の端点 | sys_clk の Fmax |
|---|---|---|---|---|
| 第 1 回 | 222.6 MHz | −66.8 ns | 238 | 102 MHz（合格） |
| 第 2 回 | 257.1 MHz | −1.206 ns | 10 | 109.2 MHz（合格） |
| 第 3 回 | 265.7 MHz | −1.365 ns | 10 | 105.3 MHz（合格） |
| 第 4 回 | 277.3 MHz | −0.273 ns | 3 | 104.6 MHz（合格） |
| 第 5 回 | **305.8 MHz** | **0（合格）** | 0 | 103.4 MHz（合格） |

第 5 回の変更: `la_front` で「prev の次の値が s2 になる周期」の判定（`sel_r`）を 1 周期早く決めて持ち、エッジの選択の経路を短くした
（run が変わる周期だけ実際の now と違うが、その周期のエッジは使われない）。ビットストリームも出来た（`fprobe_pynq_cap`、Default と Explore を並列にビルドして良いほうを採る）。

測ったのは Vivado の静的タイミング（setup・hold とも合格）で、**実機のサンプリングは測っていない**。

### 10.2 配線なしの実機確認（selftest）

`la_cap.control.selftest = 1` のとき、ch `LA_PIN_COUNT + 1`（PYNQ では 9）に、`dap_busy` の代わりに sys の周期ごとに反転する内部信号が入る（段は置かない。
`dap_busy` と同じ時間関係）。取り込みの周期が sys の 1 / R なら、同じ値が R 個ずつ続く。`tests/tb/fprobe_core_tb.py` の
`the_cap_selftest_signal_toggles_every_sys_cycle`（`CAP_RATIO = 3`）が確かめる（期待値をわざと R + 1 にすると失敗し、実際の連続は 3 だった）。
実機は `tests/hil/test_pynq_cap_hw.py`。Vivado（`fprobe_pynq_cap`、selftest 入り）は cap_clk 302.1 MHz で合格。

**実機の結果（2026-10-30 16:01、PYNQ-Z2、最終版 設計 ID b182d3294446f4fb、配線なし）**: `tests/hil/test_pynq_cap_hw.py --hil` の 3 件すべて合格。
- 比（la_cap の info）= 3、`la_sample_hz` = 3 × `sys_clock_hz`（レジスタ読み出し。実測）。
- selftest: 8192 サンプルすべてが連続 3（先頭の途中から始まる 1 つを除く）。取り込みの周期が sys の 1/3 であることの実測。
- sys = 100.0092 MHz（ホストの時計との比較。ホストの時計の揺れを含む）。取り込み = 3 × sys = 300.027 MHz は計算値で、直接は測っていない。
- 書き込みは Linux の fpga_manager 経由（`fprobe-pl before` / `after`）。MMCM はロックし、PS からの AXI も止まらなかった。
- 未測定: 外部ピンからの入力の限界（配線が要る）。

### 10.3 取り込みの速さの上限（整理）

- 内蔵バッファの取り込みの上限: BRAM 388 MHz（部品の上限）。BUFG は 464 MHz。今の cap_clk の Fmax は 302 MHz 付近（ビルドごとに数 MHz 動く）。
- 比は sys の整数倍。sys = 100 MHz のままでは 300 の次は 400 MHz で、BRAM の上限を超える。388 MHz 級にするには sys を下げる必要があり、他の構成に影響する。
- 深いバッファ（DDR）の符号器は sys の 1 サンプル/周期で動くので、cap 領域の 300 MS/s は流せない。ホストへの垂れ流しは、PYNQ の中継のストリームだけで約 8 MB/s（制御と混ぜると約 1〜2 MB/s で制御が遅れた。2026-10-21 の記録）。
  原因の切り分け（2026-10-30、中継を通さない素の UDP の測定）: PYNQ の上の C の UDP エコーで 512 バイトが約 11,400 個/秒（5.8 MB/s）、1400 バイトが 15.2 MB/s（PC は Python。値は下限）。
  中継を通したストリームだけの上限は約 8 MB/s（RAW 4 MS/s で overrun なし、6 MS/s 以上で DDR に溜めきれず overrun。リンクは 1 Gbps なので律速ではない）。
  DDR（深いバッファ）への記録は、sys の最大 100 MS/s（200 MB/s）まで overrun なしで書けた（8 MB を 0.041 s。実測）。
  以前の記録の約 2 MB/s は、制御と同じ中継に混ぜたときの値。8 MB/s で頭打ちになる原因（中継のソフト・PC の受信・PYNQ の CPU）は切り分けていない。

**中継の垂れ流しの改善（2026-10-30 夜、PYNQ 実機）**: 律速は UDP の送信ではなく PL の窓の読みだった（中継の中で計った: 1 フレーム 約 510 バイトで、
窓の読み 約 34 µs（1 語 約 270 ns）、`sendto` 約 27〜29 µs、次のフレームが窓に出るまでの待ち 約 5〜6 µs）。変更（host/、ゲートウェアは不変）:
読み取りスレッド + リング、PC が頼んだときだけの byte チャンネルのまとめ送り（`CH_BUNDLE` = 0x40、既定 1400 バイト。CONTROL・DAP はまとめない）、
まとめ送り中の次フレームの短い待ち。結果: 取りこぼしなしで続く速さは 8 → 約 10.4 MB/s（RAW 16 ch で約 4 → 約 5.2 MS/s、約 +30%）、
入れた版で 9 回とも欠け 0・overrun なし（6 MS/s 10.6〜10.8 MB/s、8 MS/s 10.4〜10.6 MB/s、各 5 秒）。
まとめを使わずスレッド化だけだと、小さいパケットの高頻度の送信で PC に届く前に欠ける回があった（6 回中 2〜6 回。落ちた場所は未確定）。
今の律速は PL の窓の読み（毎秒約 22,000 フレーム）。これ以上はゲートウェア（TX バッファを 32 ビット幅に）か、PS が DDR を直接読む方式が要る（未着手）。

### 10.4 独立したレビューの結果（2026-10-30）

回路（`la_capture`・`la_front`・`la_cap_domain`・`la_pulse`）を、別のエージェントが読んで試験で確かめた。

- **直した（再現できた）**: `FAST` で `pretrigger` と `run` を同じ周期に変えると、`pre_zero` が 1 周期古く、開始が S_PRE ではなく S_WAIT になり、前の捕捉の内容が pre の領域に残った。
  CSR からは別の書き込みなので実害は無かったが、`la_capture` を直接使う試験（設定と `run` を同時に変える書き方）では出た。
  直し方: `FAST` のとき `run` を 1 周期遅らせて使う（`run_i`）。試験 `test_la_capture[fast]`（`la_capture_tb` を `FAST = true` でも走らせる）は直す前に 2 件失敗し、直した後に通る。
- **制約として書く（直さない）**:
  - `FAST` で `run` が 1 周期だけ 0 になって戻る使い方は、`sel_r` の説明（run が変わる周期のエッジは使われない）が当てはまらず、`rise`/`fall` 指定のときに最初のサンプルのエッジ判定が誤りうる。
    `la_cap_domain` 経由では `run_c` の 0 は最低 R 周期続くので到達しない。
  - `FAST` の最初のサンプルの `prev` は 1 周期古い（`FAST = false` でも `run` の周りの 2 周期は同様）。
  - `pretrigger` ≥ DEPTH は元の回路と違う動きになる（約束は `pretrigger ≤ DEPTH − 1`。ホストの `LogicAnalyzer.start` が 0〜depth − 1 に限る）。
  - 完了直後の 1 sys 周期、`done` と `start_index`・`trigger_time` が揃わないことがある（`FAST` の `ev` 段）。CSR の読み出しは別の転送なので実害は無い。
    `done` の立ち上がりで内部ロジックが取る設計を足すときは注意。
- **確かめて問題が無かった**: PRE・POST の数え（`left`・`left1`・`first`）、`cnt`/`cnt_zero`、`la_pulse` の自走する比較旗、`sys`→`cap` の受け渡し（全ビットが同じ周期）、
  `latency = 5 − R`（R = 2〜5 の試験で一致）、`FAST = false` が元の回路と同じこと。
