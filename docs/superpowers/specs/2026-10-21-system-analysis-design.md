# システム解析（MCU と FPGA を並べて「なぜ壊れたか」を探す）

2026-10-21。Shrike-Lite（RP2040 + ForgeFPGA）の連携デモ（target_ip/fprobe_obs/examples/shrike_lite）で作り、
確かめた。機能はどの対象にも使える汎用のもの（デモ固有の処理は入れない）。

## 1. 目的

MCU と FPGA が連携するシステムの不具合は、片側だけ見ても分からない（MCU からは「たまに答えが違う」、FPGA からは
「計算は回っている」）。両側を同じ時間軸に並べ、**結果（例: MCU の誤りの数が増えた）の直前に何が起きていたか**を
数で示し、時間軸の該当箇所へ飛べるようにする。人も AI も同じ道具を使う。

## 2. 今あるもの（画面 SystemPanel・API system.status）

- MCU: コアの状態と、止めずに読む番地（名前つき。毎秒の増え方）。
- FPGA: 観測の型・状態・各組の最新の値（信号の名前で）、FPGA の条件（`restart changed and state=BUSY`）の毎秒。
- 記録: 「記録を始める」で MCU のメモリ（DAP サンプラ、名前つき）・ピン（ロジアナを流し続け）・FPGA の観測・DAP が
  1 本の時間軸に入る。「時間軸で並べて見る」で MCU のメモリ → FPGA → 変化のあるピンの順に並べる。
- 観測が答えなくなったら（対象の FPGA を書き直した等）同じ設定で開き直す。

## 3. 結果の直前に多い出来事（recording.correlate）

方針（利用者、2026-10-21）: 道具は「原因はこれ」と判断しない。判断のための情報を確実にそろえ、欠けを示す。この解析が
出すのは「結果の直前にこの出来事が多い」という事実と、記録のうち候補の後の時間窓に当たる時間の割合（coverage）まで。
名前・文言も断定しない（旧名「原因の候補」）。さらに 2026-10-21 夜に、本体にヒューリスティック（経験則の閾値・仮定に頼る
推定・それらによる順位づけ）を入れないと決めた（CLAUDE.md）。以前の lift（ランダムな時刻の仮定による見込みとの比）・
「先行率 0.5 以上を先に」の並べ方・窓あたり 3 回超の自動の除外・「中央値の 5 倍」の欠けの判定・「窓が読みの間隔の 2 倍より
短い」の警告は取り除いた。

### 3.1 変数と条件

記録の中の「変数」を名前で指す:

| 種類 | 名前 | 値 |
|---|---|---|
| MCU のメモリ | 記録の情報 `sample.names` の名前（watch.set の names）、または番地 `0x20040808` | 32 ビットの語 |
| FPGA の信号 | 記録の情報 `fpga.signals` の信号の名前 | 信号の値（列挙は名前でも比べられる） |
| ピン | 記録の情報 `pins`（記録を始めたときの既定の名前。`in0` 等）・`channel_names` の名前、または `ch10` | 0 / 1 |

同じ名前が複数の種類にあれば `mcu.` / `fpga.` / `pin.` を前に付けて区別する（付けなければ誤り）。
空白・`=`・`"` を含む名前は `"…"` で囲む（`"Error count" changed`）。画面は同じ名前の番地を 2 つ置かせない。

条件 = 項を `and` でつないだもの。項:
- `<変数> changed`（値が変わった）・`<変数> rose`（0 → 0 以外）・`<変数> fell`（0 以外 → 0）: 瞬間の項
- `<変数>=<値>`（その時の値。値は数・16 進・列挙の名前）: 状態の項

条件は瞬間の項を 1 つ以上含む（そのどれかが起きた時刻を、ほかの項で確かめる。瞬間の項どうしは同じ時刻に起きたとき
だけ成り立つ）。画面の FPGA の条件（`restart changed and state=BUSY`）と同じ書き方で、MCU とピンにも広げたもの。

### 3.2 何を返すか

`recording.correlate(effect, causes, window_s, t0, t1, examples)`:
- effect: 結果の条件（例 `errors changed`）。causes: 候補の条件の並び。
- 結果ごとに、窓 window_s の中で直前に起きた候補の時刻を探す。候補ごとに:
  - `preceded`: 直前（窓の中）に候補が起きていた結果の割合
  - `coverage`: 記録のうち（候補の変数の欠けを除いて）、ある候補の後 window_s 以内に当たる時間の割合（測った値。仮定なし。
    preceded とどう比べるかは使う側が決める。どちらも 1 に近い候補は、いつも起きているだけかもしれない）
  - `followed`: 候補のうち、窓の中で後に結果が来た割合（候補 → 結果の起こりやすさ）
  - 遅れ（結果 − 直前の候補）の最小・中央値・90 % 点・最大
  - `examples`: 結果と直前の候補の時刻の組（最初の数件。時間軸で飛ぶ）
- 結果・候補の数、調べた範囲。
- `judged`: preceded の分母。窓が候補の変数の欠けにかかる結果は、候補が先に来たか分からないので除く。
- `reads`: MCU のメモリの読みの事実（回数・読めなかった回数・間隔の分位・いちばん長い空白の時刻）。

窓は既定 10 ms。MCU のメモリは DAP サンプラの周期（既定 1 ms）より細かくは決まらない（遅れの分解能。返す）。
FPGA の標本型は標本の間の変化が見えない（`hidden` の数を返す）。

- 並べ方: preceded の大きい順、同じなら条件の文字の順（事実だけで）。結果と同じ時刻の候補は前後が分からないので
  数えない（同じ読みの中で変わった MCU のメモリ同士等）。結果の時刻は読みの間隔だけ遅れて見える（reads・sampling）。

### 3.2.0 データの欠け（gaps）

黙って数え落とさないため、使った変数の欠けを返す（`gaps`。時刻・reason）。reason: `reads_missing`（MCU のメモリの
読みが、使う側が明示した gap_s より長く空いた所。範囲の端から最初・最後の読みまでも。gap_s が無ければ欠けにしない）・`read_failed`（読めなかった語）・
`pins_missing`（ピンの波形が無い区間）・`fpga_lost`（FPGA の観測の欠落）・`events_error`（取り込みの失敗）・
`recording_dropped`（長期の記録の間引き・削除）。warnings に件数と合計（重なりは 1 回）。画面は一覧と「表示」。
recording.transactions・durations も、欠けにかかる区間・回を数えず `excluded` と `gaps` を返す。
実機: watch を 1.5 秒止めた記録で reads_missing 1509.8 ms、ピンを途中の 2 秒だけ流した記録で in0 rose の先行率が
41 %（欠けを分母に入れた値）→ 89/219 回で判定して 100 %。

### 3.2.1 候補を自動で作る

causes を省くと、記録の変数から候補を作って調べ、先行率の大きい順に上位（既定 20）を返す: 各信号の変化
（1 ビットとピンは rose / fell）、列挙の信号の各値に入った瞬間、「変化 かつ 列挙の信号 = 値」の組、ほかの MCU の
メモリの変化。結果の変数と、範囲の中で変化しない変数は使わない。頻度による除外はしない（使う側が max_coverage を明示すれば、
coverage がそれを超える候補を除く）。実機（Shrike・4 秒の記録）: 約 1.5 秒で「restart changed and state=BUSY」が一番上（手で書いた
候補と同じ結論）。

### 3.2.2 区間ごとの集計（recording.transactions）

この解析は「結果の直前に何が多いか」を出すが、「どの入力の要求が誤るか」は出せない。記録を区間（リクエスト等の
1 回の取引）に切り、区間ごとに数える:

- 区間 = start（瞬間の項のある条件）が成り立ってから次に成り立つまで（最後は範囲の終わりまで）。
- 区間ごとに by（変数）の開始時の値（開始より前に値が無ければ null）・counts の各条件が区間の中で成り立った回数・
  effect が区間の中で起きたか。
- groups = by の値ごとの区間の数・effect の割合・counts の平均（by の値の順）。rows = 最初の rows 区間の中身。
- 2026-10-21 の実機（10 秒、1361 区間、0.35 秒）: start `state changed and state=BUSY`・by `left_hi`・counts
  `restart changed and state=BUSY`・effect `errors changed` → left_hi 0〜8 は再試行も誤りも 0、10〜14 はほぼ全件が
  再試行され誤る。AI の試験（手引きと API だけ）で、AI が記録を全件読んで手で出した集計と同じ。
- `by_effect`（effect があるとき）: 結果が起きた区間（with）と起きなかった区間（without）の数・counts の平均。
  失敗した回と普段の回の違いを事実として並べる（実機: with 217 区間で演算中のリトライ 1.00 回、without 531 区間で 0.08 回）。

### 3.3 画面

システム解析のパネルに「結果の直前に多い出来事」: 結果の条件（既定: MCU のメモリの表の 1 つの `changed`）と、候補（FPGA の条件の
表 + 入力）を、開いている記録で調べる。表: 候補・preceded・coverage・followed・遅れの中央値。行を押すとその例の時刻の前後へ
時間軸を合わせる（ui.state の view）。

## 4. 条件で印を付ける・止める（recording.trigger）

めったに起きない不具合を、前後つきで記録に残す。記録中に `recording.trigger_set(condition, action, post_s)`:
- 条件は §3.1 と同じ書き方（MCU のメモリ・FPGA の信号・ピンをまたげる）。
- デーモンが 0.5 秒ごとに、前に調べた所から「今 − 遅れ（既定 2 秒。ロジアナの流れ・イベントの取り込みが記録に
  届くまで）」までの記録で条件の時刻を探す。前の範囲の最後の値を持ち越す（範囲の境の変化を落とさない）。
- 成り立つたびに記録に印（stream annotation、kind trigger、本文に条件）。action = stop なら最初に成り立った時刻から
  post_s 秒（記録の時刻で）が記録に入ったら記録を止める（ロジアナの流れも）。
- `recording.trigger_status`: 条件・回数・最初と最後の時刻・状態（armed / fired / stopped / error）。
  `recording.trigger_clear` でやめる。記録を止めればやめる。
- ハードのクロストリガ（数 µs）とは別物: 判定は PC で、数秒遅れる。代わりに MCU と FPGA とピンをまたいだ条件が書ける。

## 4.1 FPGA の条件でハードのクロストリガ（obs_match。FPGA 観測の仕様の O3「線なしのクロストリガ」）

PC の判定（§4、数秒遅れ）では、成り立った瞬間の MCU の中は見られない。fprobe の観測のエンジン（obs_jtag_engine）が、
観測した値（標本型の値・記録型の値の記録）ごとに比べ、成り立ったら 1 周期のパルスを出し、クロストリガの源 bit4
（obs_match）にする。既存の経路（ロジアナのトリガ・割り込み書き込み = MCU の停止・出力の端子）にそのままつながる。
- 比べ方（CSR obs.match・match_change）: 前の値から change のビットのどれかが変わり、かつ
  (値 xor match.value) and match.mask = 0。change = 0 なら「一致に入った瞬間」（前は不一致、今は一致）。最初の値は
  前が無いので成り立たない。成り立った回数は obs.match_count。
- 書き方はシステム解析の条件と同じ（`restart changed and state=BUSY`・`state=BUSY`（入った瞬間）・`flag rose`）。
  ホストが信号の定義からマスクに直す。瞬間の項は 1 つまで（ハードは「変化のマスクのどれか」を見るため）。
- 遅れ: 観測のスキャン 1 回分（スナップショット型・TCK 2.5 MHz で約 15 µs）+ 割り込み書き込み（DHCSR への SWD の書き込み。
  約 190 SWCLK）。2026-10-21 の実機（RP2040、FPGA の値の時刻 → DAP の書き込みの時刻）: SWD 1 MHz で 205.6 µs、4 MHz で 63.5 µs。
- 判定の一致: 2026-10-21 の実機で、同じ 1 秒の区間のハードの成立回数（obs.match_count）と、PC が観測の値の並びで
  数えた回数（画面の回/秒と同じ規則）が 3 回とも一致した（`restart changed and state=BUSY` で 60 / 42 / 52）。
- ケイパビリティ FEATURES bit8（OBS_MATCH）: 観測の口とクロストリガの両方がある構成。
- デーモンの再起動: 条件は FPGA に残る。仕掛けた条件の文字・halt・la・レジスタの値を FPROBE_HOME/obs_trigger.json に
  残し、再起動後にレジスタと一致すれば条件の文字で返す（restored）。一致しなければ持ち主の無い条件（orphan。マスク等）
  として返し、画面は警告と「解除」を出す。
- 記録型は組を区別せずに続く値を比べる（組を切り替えて使うときは組ごとに設定し直す）。

## 5. やらないこと

- 因果の断定（測った割合を出すだけ。決めるのは人・AI）。
- 特定の対象のための規則（デモの「演算中のリトライ」などは利用者が条件として書く）。
