# Shrike-Lite の C のデモ（MCU と FPGA の連携の不具合の題材）の仕様

状態: 確定（2026-10-21）。前提: [システム解析の仕様](2026-10-21-system-analysis-design.md)、
今のデモ（MicroPython）: `target_ip/fprobe_obs/examples/shrike_lite/`。

## 1. 目的

Shrike-Lite（RP2040 + ForgeFPGA SLG47910）を、**MCU と FPGA の連携の不具合を fprobe で調べる実地の題材**にする。
fprobe の価値（解析力 → 日常のデバッガ → AI の道具）を最大にすることを優先する（利用者、2026-10-21）。

- **連携の不具合の題材**: 原因が MCU と FPGA の間にある不具合を複数の型で用意する（§4）。
  MCU が原因で FPGA が壊れる型・FPGA のまれな異常が MCU の誤りに出る型・タイミングで出たり出なかったりする型・1 回きりの型。
- **連動（クロストリガ）**: FPGA の条件で MCU を止め、止めた瞬間の MCU の変数とソース行を見る。MCU のブレークポイント・
  変数の変化をきっかけに FPGA の信号とピンの前後を残す。両方向の止まるまでの遅れを実測する。
- **同じ時間軸**: MCU の変数（名前つき）・ログ（RTT）・スレッド、FPGA の信号、ピンを 1 本の時間軸に、誤差つきで並べる。
- **単体でも見られる**（利用者、2026-10-21）: MCU だけ（書き込み・ブレークポイント・変数・ソース行・RTOS のスレッド・RTT）、
  FPGA だけ（信号・条件・波形）でも、それぞれ普通のデバッガ・ロジアナとして使える。連携の解析はその上に重ねる。
- **AI の道具の試験**: 変数名のある実在のファームウェアと FPGA の信号の両方を相手に、AI 役（手引きと API だけ）が
  連携の不具合を突き止められるか試せる。

今の MicroPython のデモの限界（ELF が無い・番地で指す・長く止めると固まる・題材が 1 種類で毎秒数十回起きる）を解く。

## 2. やらないこと

- fprobe 本体（FPGA・デーモン）に、このデモのための機能を足さない（CLAUDE.md の原則）。足りない汎用の機能が見つかれば、
  別に仕様にする。題材の切り替えは、fprobe の汎用の操作（メモリの書き込み）でする。
- RP2040 のコア 1・USB（CDC）は使わない（USB はつながず、電源だけでもよい形にする）。
- MicroPython のデモは保守しない（フラッシュから消える。元のファイルはリポジトリに残る。戻し方は README に書く）。

## 3. 構成

### 3.1 ファームウェア（MCU 側）

- **Zephyr 4.1 のアプリ**（基板 `rpi_pico` + Shrike の差分の overlay）。この PC の既存の環境を使う: Zephyr の本体と
  モジュールは `~/zmk/ws`（hhkb-split の作業場所。**書き換えない**。ビルドの出力はこのリポジトリの build の下）、
  GCC は Zephyr SDK 0.17.0（`~/zmk/sdk`）、west は `~/zmk/zmkenv`。場所は環境変数で差し替えられるようにする
  （ほかの PC・CI）。2026-10-21 に hello_world を `rpi_pico` 向けに作れることを確かめた（FLASH 15 KB）。
- 置き場所: `target_ip/fprobe_obs/examples/shrike_lite/firmware_c/`。ビルドは Python の `build.py`（今の FPGA の
  ビルドと同じ入口）から: FPGA の回路を作り、その出力をファームウェアに埋め込み、ファームウェアを作る。
- **書き込みは fprobe の SWD**（`flash.*`。pyOCD の rp2040 の書き込みアルゴリズム）。日常のデバッガとしての書き込みの
  実地の試験を兼ねる（速さ・検証・失敗時の戻り方を記録する）。UF2 も出す（fprobe が使えないときの戻し用）。
- **スレッド**（Zephyr のスレッド。fprobe の RTOS の表示が Zephyr に対応済み）:
  - 要求のスレッド: A・B を書いて演算を要求し、完了を待ち、結果を検証する（今の main.py の流れ）。
  - 割り込み: タイマ割り込み（§4 の S3 の題材に使う）。
  - ログのスレッド（または要求のスレッドから）: RTT に 1 行のログ（要求の番号・A・B・結果・判定）。頻度は設定で絞れる。
- **名前つきの大域変数**（ELF から引ける。fprobe の MCU のメモリの表・解析の変数に名前で入る）: `g_requests`・`g_errors`・
  `g_retries`・`g_last_a`・`g_last_b`・`g_last_result`・`g_scenario`（題材の選択。§4）・`g_poll_limit` 等。
  今のメールボックス（0x20040800）は使わない。
- マーカー: GPIO26 = 要求中 1（ロジアナ。今と同じ）。GPIO27 = 題材の印（§5）。

### 3.2 FPGA の回路

- 今の演算器（`rtl/demo_accel.vhd`）と観測の回路（スナップショット型）をもとにする。
- 起動時に MCU が SPI で回路を送る（Shrike の公式の手順: GPIO12 = 電源・GPIO13 = 有効を下げて 100 ms → 上げて 100 ms →
  500 ms 待つ → CS（GPIO1）を 2 ms 上げて下げる → SPI モード 0・MSB 先頭で回路のデータをそのまま送る → CS を上げる。
  出典: vicharak-in/shrike_flash の `ShrikeFlash.cpp`）。送った後に演算器の ID レジスタを読み、合わなければ RTT と
  変数に誤りを残して止まる。
- **題材の切り替えは実行中に**（フラッシュを書き直さない。利用者の「フラッシュの書き込みを節約する」）: 演算器に
  MODE レジスタを足し、各題材の FPGA 側の仕込みを MODE のビットで入れたり外したりする。MCU は `g_scenario` の変化を見て
  MODE を書く。
- 観測する信号に、題材の判定に要るもの（MODE・題材ごとの内部の状態）を足す。ForgeFPGA の資源（今 45 %）に収まる範囲で。

## 4. 題材（不具合の型）

`g_scenario` で 1 つ選ぶ（0 = 不具合なし）。各題材について、仕込み・MCU だけ / FPGA だけで見えること・両方を並べると
分かること・fprobe のどの機能で捕まえるか、を README に書き、実機で確かめる。

| # | 型 | 仕込み（案） | 起きる頻度 | 捕まえ方（想定） |
|---|---|---|---|---|
| S1 | MCU → FPGA | 今の題材: 演算中のリトライで和がクリアされない（FPGA）+ 待ち回数が短い（MCU） | 毎秒数十回 | 結果の直前に多い出来事・区間ごとの集計 |
| S2 | FPGA → MCU | FPGA がまれに、特定の条件（例: 書き込みが演算の終わりの 1 クロックと重なる）で B の書き込みを取りこぼす。MCU には「たまに結果が違う」としか見えない | 数秒〜数十秒に 1 回 | FPGA の条件で MCU を止める（クロストリガ）・前後の波形 |
| S3 | タイミング | タイマ割り込みが GPIO の出力を古い写しで丸ごと書き戻す（排他の無い読み・変え・書き。CS も含む）。要求のスレッドの SPI の転送の途中に割り込みが入った回だけ CS が上がり、FPGA に壊れたコマンドが届く（2026-10-21 に「ISR が SPI を直接たたく」から変更: SPI のドライバの受け取りを奪って固まりになるため） | 割り込みの周期と要求の周期の兼ね合いで変わる | 時間軸で割り込み（スレッド・RTT）と SPI（ピン・FPGA の信号）を並べる・条件で記録を止める |
| S4 | 1 回きり | まれな組み合わせ（例: A = 0xFF かつ割り込みが重なる）でだけ FPGA の状態機械が BUSY から抜けなくなり、以後の要求が全部タイムアウトする | 数分に 1 回、起きたら戻らない | 条件で記録を止める（前後つき）・FPGA の条件で MCU を止める・止まった瞬間の変数とスレッド |

仕込みの細部（どの条件で起こすか・頻度の調整）は実装で決めてよい。ただし各題材は次を満たす:
- MCU だけ・FPGA だけを見ても原因が分からず、両方を並べると分かる。
- 頻度を変数（`g_*`）で調整できる（まれな題材を試験のたびに何十分も待たない）。
- 不具合なし（`g_scenario = 0`）では、長く回しても `g_errors` が 0。

## 5. 配線

今のデモと同じ（README の表: 観測の JTAG 4 本・SWD・GND・GPIO26 のマーカー）に、**題材の印 GPIO27 → PMOD JB 7 番
（ロジアナ ch 14。JB 1 番の真下の穴）を 1 本足す**（利用者が 2026-10-21 に配線）。GPIO27 には「割り込みの中」「FPGA の異常を MCU が
検知した瞬間」等の印を出す。ファームウェアは最初から出しておき、線が無い間は RTT とスレッドの表示で代わりに見る。
配線の手順に、電源の順・電圧の範囲・逆流を書く（両方 3.3 V。Shrike と PYNQ の電源を入れてから信号の線）。
Shrike の USB は電源としてつなぐ（CDC は使わない）。

## 6. 確かめること（受け入れ）

実機（PYNQ-Z2 の fprobe・Shrike-Lite）で:

1. **書き込み**: fprobe の SWD でファームウェアを書き、検証し、単独で起動する。書き込みの時間を記録する。
2. **単体（MCU）**: 接続（attach）・停止・ブレークポイント（ソース行）・変数を名前で読む・スレッドの一覧・RTT のログ。
   長く止めても（10 分）再開して動き続ける。
3. **単体（FPGA）**: 観測の回路に接続し、信号の定義・条件の回数・波形の捕捉が今と同じに動く。
4. **題材ごと**: §4 の表の「捕まえ方」で、各題材の原因に行き着ける（実機の数値を README に残す）。
5. **連動**: FPGA の条件 → MCU の停止の遅れ、MCU のブレークポイント → FPGA の前後の捕捉、を実測する。
6. **AI の試験**: AI 役（手引きと API だけ）に、題材を伏せて S2〜S4 のどれかを調べさせ、原因に行き着くかと、つまずきを記録する。
7. **不具合なし**: `g_scenario = 0` で 30 分回して `g_errors` = 0。

## 6.1 作者の判断（実装者の確認で出た点。2026-10-21）

- 観測の回路: 1 クロックの出来事（S2・S3）を取り逃がさないよう、**記録型（変化をすべて記録）を先に試す**。ForgeFPGA の
  資源に収まらなければ標本型のまま、演算器に「起きた回数」のカウンタを足す（製品の FPGA にもよくある作りで、題材として
  不自然でない）。どちらにしたかと、標本型の見えない変化（fpga_hidden）を README に書く。
- S3 の割り込み: ISR の中で GPIO の出力のレジスタを、割り込みを仕掛けたときの古い写しで丸ごと書き戻す（排他の無い
  読み・変え・書きの競合。転送中なら CS が上がる）。「割り込みが排他なしで同じ資源に触る」現実の不具合の形。当初の
  「ISR が SPI のレジスタを直接たたく」は、Zephyr の SPI ドライバの受け取りを奪いドライバが待ち続けて固まったのでやめた
  （2026-10-21、台帳の Task 6 の Ruling）。
- MCU のブレークポイント → FPGA の前後: ロジアナのピン（マーカー・SPI）と、止めた時点の FPGA の観測の値で見る。
- fprobe の SWD で RP2040 のフラッシュに書けなかったときは、**直すことをこの計画に含める**（日常のデバッガの中心の機能。
  価値を優先）。UF2 は戻し用にだけ使う。
- 実装者が決めてよいこと: 題材の頻度の変数（`g_s2_rate` 等）、RTT のログの間引き（`g_log_every`）、S4 から戻す操作
  （`g_reset` を書くと FPGA を送り直す）、Zephyr の版と RTT のモジュールの確認と記録。Zephyr のスレッドの表示に要る
  CONFIG（THREAD_MONITOR・THREAD_NAME・THREAD_STACK_INFO・INIT_STACKS）は host/fprobe/rtos/zephyr.py に従う。

## 7. 決めていないこと・危険

- fprobe（PYNQ の中継経由）での RP2040 のフラッシュの書き込みは、まだ試していない（pyOCD の rp2040 の対応はある）。
  動かなければ、それ自体が fprobe の課題（日常のデバッガ）として別に直す。
- Zephyr の RTT（SEGGER の RTT のモジュール）が、fprobe の RTT の読みでそのまま読めるか。
- ForgeFPGA の資源: 題材の仕込みと観測の信号の追加が 140 ブロックに収まるか。収まらなければ題材の仕込みを簡単にする。
- `~/zmk/ws` を使う都合: 利用者が ZMK の作業場所を更新すると Zephyr の版が変わりうる。ビルドの手順に、使った版を記録する。
