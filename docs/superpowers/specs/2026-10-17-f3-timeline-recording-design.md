# F3: 共通の時間軸の記録（解析の土台）設計

全体計画: [2026-10-17-feature-expansion-roadmap.md](2026-10-17-feature-expansion-roadmap.md)。

## 1. ゴール

fprobe が観測するすべての出来事を、**1 つの時刻の上の 1 つの記録**にまとめ、保存・検索・統計・書き出しを API で提供する。
TRACE32（PowerIntegrator との共通時刻）と DT+（テストポイント・アナログ・映像の同期、最長 30 日）の領域を、デバッガと
一体で上回る。後の F4（変数のライブ観測）・F5（性能解析）・F6（RTOS）・F7（テストポイント・通信の解読）・画面の
タイムラインは、すべてこの記録に書き込み、ここから読む。

| 完了条件 | 検証 |
|---|---|
| 波形（ロジアナ）・DAP の転送・UART・SWO・補助の電圧・ホストの操作（AI と人）・停止とブレーク・注釈（解読・印・メモ）を、同じ時刻の 1 つの記録に入れられる | 単体 + HIL |
| 記録は日単位で続けられ、ディスクに逐次書き、途中で落ちても書いた分は残る | 単体（大量の偽データ）+ HIL（数十分） |
| 時刻の範囲・種類・条件で読み出し、検索（条件 → 一覧）、統計（件数・間隔・最小/最大/平均・分布）ができる | 単体 |
| 拡大率に応じた要約（1 画素ごとの件数・波形の 0/1/x）を速く返す（画面の縮図・タイムライン用） | 単体（100 万件で 0.5 秒以内） |
| 書き出し: VCD（波形）・CSV/JSON（イベント・ログ）。読み込み: 保存した記録を開き直す | 単体 |
| API（デーモン・MCP）から記録を始める・止める・読む・検索する | 単体 + HIL |

## 2. 時刻のモデル

- **基準はデバイスのタイムベース**（FPGA の 64 ビットのカウンタ、`timebase_hz`）。デバイスが付ける時刻（イベント・
  ロジアナのトリガ時刻・補助の計測値）はこの値をそのまま使う。秒は `ticks / timebase_hz`。
- ロジアナのサンプル番号は、捕捉のトリガ時刻（タイムベース）と `sample_period_s` でタイムベースに写す。
- **ホストで起きた出来事**（API の操作・RTT や SWO をホストで受けた時刻・AI の行動）は、ホストの単調時計で時刻を取り、
  **時計の対応付け**でタイムベースに写す。対応付けは、記録中に定期的に（既定 1 秒ごと）`device.time()` を読み、
  読みの前後のホスト時刻の中点と組にして、直線（ずれと傾き）で当てはめる。読みの往復時間の半分を**不確かさ**として
  記録に持ち、画面と解析は「この出来事の時刻は ±x µs」として扱う（デバイスの時刻を持つ出来事と区別する）。
- 記録の時刻はすべて整数のタイムベースの値（ホストの出来事は写した値と不確かさ）。

## 3. 記録の形（ホスト）

- 1 回の記録 = 1 つのディレクトリ（`~/.fprobe/recordings/<日時>-<名前>/`、`FPROBE_HOME` に従う）。中身:
  - `recording.sqlite`: 索引と小さな出来事（SQLite。標準ライブラリ、トランザクションで途中で落ちても壊れない、時刻の
    索引で範囲の読みが速い）。
  - `waveform/<連番>.bin`: ロジアナの変化点のかたまり（数十万変化点ごと。タイムベースの開始・終了と、チャンネルの数を
    索引に持つ）。大きなデータを SQLite の外に置き、追記だけで書く。
  - `meta.json`: 記録の情報（デバイス・ケイパビリティ・ELF・ターゲット・開始時刻・時計の対応付けの最新値・版）。
- **ストリーム**（出来事の種類のまとまり）: `waveform`（変化点）、`dap`（転送）、`uart`、`swo`、`rtt`（チャンネルごと）、
  `aux`（電圧）、`host`（API の操作・AI と人）、`target`（停止・再開・ブレーク・リセット）、`annotation`（解読・印・メモ）、
  `sample`（変数の値。F4）、`clock`（時計の対応付けの点）。
- 1 件の出来事 = 時刻（開始、必要なら終了）・ストリーム・種類・小さな値（整数 2 つ）・本体（JSON。小さなもの）・
  不確かさ（ホストの出来事だけ）。SQLite の表 1 つに入れ、（ストリーム, 時刻）の索引。
- 書き込みはまとめて（例: 0.2 秒か 1 万件ごと）トランザクションで。

## 4. 取り込み（記録器 `Recorder`）

- `Recorder(device, directory)`: 記録の開始・停止、ストリームへの書き込み口（`add(stream, kind, t, ...)`、
  `add_waveform(transitions)`）、時計の対応付けの定期実行。スレッド安全。
- **取り込みの元**（F3a）:
  - ロジアナの捕捉（内蔵・深いバッファ）: 捕捉が終わったら `Transitions` をトリガ時刻で写して入れる。
  - ロジアナの流し続ける捕捉（`LaStream`）: チャンクごとに入れる（日単位の連続記録の主な道）。
  - イベント記録（DAP・UART・SWO・補助）: `EventLog.read` の差分を定期的に取り込む（深いバッファの捕捉中は読めないので、
    捕捉していない間に読む。F3b で解消）。
  - ホストの出来事: デーモンの操作の記録（activity）・停止の見張り（target.state）を `host`・`target` に。
  - RTT・SWO（F1 の担当 D の部品ができたら）、変数（F4）、解読（F7、担当 C の部品）: それぞれの元が `Recorder` に書く。
- **F3b（ゲートウェア）**: 深いバッファの流し続ける読み出しに、イベントのリングも混ぜて 1 本の流れにする（種類付きの
  かたまり）。これで「波形とイベントを同時に日単位で記録し続ける」をデバイスの時刻のまま実現する。F3a の後、別の
  計画で行う。→ 2026-10-19 に R1 として実装（構成 fprobe_la。docs/superpowers/specs/2026-10-19-r1-unified-stream-design.md）。

## 5. 読み出し・検索・統計（`Recording`）

- `Recording.open(directory)`: 記録を開く（記録中でも読める）。
- `events(t0, t1, streams=None, kinds=None, limit=None)`: 範囲の出来事を時刻順に。
- `waveform_view(t0, t1, width)`: 範囲の波形を画素ごとに 0/1/x（`fprobe.la.Waveform` と同じ考え。かたまりをまたぐ）。
- `density(t0, t1, width, streams)`: 画素ごとの出来事の件数（縮図・タイムラインの要約）。
- `find(query)`: 条件 → 一致した出来事の一覧と件数。条件は構造化した JSON（ストリーム・種類・値の比較・本体の文字列の
  正規表現・波形のエッジ（チャンネル・向き））。後で画面の検索と、同じ条件をハードのトリガにする変換（F3 の後）に使う。
- `intervals(start_query, end_query)`: 2 つの条件の間の時間の一覧と統計（最小・最大・平均・標準偏差・分布の箱）。
  2 点間の時間・ばらつき（DT+・SystemView）の土台。
- `export_vcd(path, t0, t1, channels)`、`export_csv(path, ...)`、`export_json(...)`。

## 6. API（デーモン・MCP）

| メソッド | 種類 | 内容 |
|---|---|---|
| `recording.start` | control | 名前・取り込む元（waveform の連続捕捉の設定、events、rtt 等）を指定して始める |
| `recording.stop` | control | |
| `recording.status` | read | 記録中か、時間、件数、大きさ、時計の不確かさ |
| `recording.list` / `recording.open` | read | 保存した記録の一覧・開く（以後の読みの対象） |
| `recording.events` / `recording.find` / `recording.intervals` / `recording.density` / `recording.waveform` | read（`record: false`） | 読み出し・検索・統計・要約 |
| `recording.mark` | control | 印・メモ（人と AI の調査の経緯を残す）を `annotation` に |
| `recording.export` | read | VCD・CSV・JSON |

デーモンは記録中、操作の記録（activity）を `host` に、見張りの状態の変化を `target` に、自動で書く。

## 7. 判断

| 判断 | 理由 | 誤っていた場合のコスト |
|---|---|---|
| 索引と小さな出来事は SQLite、波形は別のかたまりのファイル | 標準ライブラリだけで、落ちても壊れず、範囲の読みが速い。波形は量が桁違いなので追記だけのファイル | 低（索引だけ別の仕組みに替えられる） |
| 基準の時刻はデバイスのタイムベース、ホストの出来事は対応付けで写し不確かさを持つ | デバイスの時刻を持つ出来事（波形・DAP）の精度を落とさない。ホストの出来事の不正確さを隠さない | 低 |
| F3a（ホスト）と F3b（ゲートウェアの 1 本の流れ）を分ける | F3a だけで、記録・検索・統計の API と、捕捉ごとの記録はすぐ使える | 低 |

## 8. 試験

- 単体: 時計の対応付け（ずれ・傾き・不確かさ）、書き込みと範囲の読み（ストリームの混在、かたまりをまたぐ波形）、
  検索・間隔の統計、縮図、書き出し（VCD を既存の読み手で読み直す）、記録中の読み、途中で落ちた記録を開く、
  100 万件の性能。
- HIL: 実機でロジアナの連続捕捉とイベントと AI の操作を同じ記録に入れ、時刻の順序（AI の操作 → DAP の転送 → 波形の
  変化）が正しく並ぶことを確かめる。
