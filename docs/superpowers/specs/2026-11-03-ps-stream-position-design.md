# PS が DDR を直接読む流れの「位置の約束」（窓の版 4）

2026-11-03。対象: `la_deep_buffer`・`la_ps_port`（新規）・`zynq_frame_link`・`cdc_value`・中継 `fprobe-relay`・`eth_link`。
前の設計: [2026-10-30-la-stream-ps-direct-design.md](2026-10-30-la-stream-ps-direct-design.md) §3.2〜3.4（ここで置き換える）。
番地とビットの正: `gateware/fprobe_gw/ps_window.py`（表は [docs/ps-window.md](../../ps-window.md)）。

## 1. なぜ（点検 2026-11-03 の穴）

- C1: 世代 `ps_gen` を sys 側で付けていた。中継が新しい流れに気づく前に書いた古い位置は、窓の 0 戻しの後に届くと新しい世代の値として
  使われ、書き位置が追い越した時点で読み位置が飛んだ。`EV_CONSUMED`・`STREAM_BEATS` には守りが無かった。
- C2: 32 ビットの総数を折り返しなしで比べていた（`w_total >= 応答待ち`・`consumed <= w_total`）。中継はリングの位置を
  `総数 mod リング` で求めていたが、リングの拍数（15/16 × 2^n）は 2 の冪でないので 2^32 拍（68.7 GB、66.7 MB/s で 17 分）の後に狂う。
- C3: 流れの途中で `events.enable` を始め直すと、書き込み器がイベントのリングを先頭に戻し、読み位置との差がでたらめになった。
- C4: 窓の `STREAM_STATUS` が番号・書き位置と別の受け渡しだった。C10: 中継は複数のレジスタを別々の時点に読んでいた。
- C5: `cdc_value` は「読み込みの間隔が受け側の数周期より長い」約束を守らせていなかった（受け側が取り込む間に値が変わりうる）。
- D8: 握手の代わりに待ち時間（`drain` 31 周期、`T_SETTLE`・`T_IDLE2`）を使っていた。P7: PYNQ は mem_clk = sys なのに 16 周期ごとの受け渡し。

## 2. 約束

1. **流れの番号** `epoch`（16 ビット）は sys で run の 0→1 ごとに 1 進む（PS が読む流れに限らない）。開始の設定（stream・ps_read・gaps・
   post_beats）は同じ辺で写す。
2. **書く側が番号を添える。** 窓の位置（`LA_CONSUMED`・`EV_CONSUMED`・`STREAM_BEATS`）は `la_ps_port` が持ち、番号が変わった次の周期に
   0 に戻す。位置の書きは、PS が `POS_TAG` に書いた番号が今の番号のときだけ受け、違えば捨てて `STALE_WRITES` に数える。窓は書きを
   1 つずつ順に処理するので、`POS_TAG` → 位置の書きは割り込まれない。位置はその値の番号（`ret_epoch`）と一緒に la_deep_buffer へ
   返し、mem は今の流れの番号の値だけを使う。
3. **公開は 1 つの時点の組。** mem は（流れの番号・書き込み中・トリガ・完了・溢れ・PS の流れの生死・応答の来た書きまでの総数と
   ロジアナのリングの書き位置・イベントの位置・busy・入れた拍の数・受けた読み出しの番号）を同じ周期の値でレジスタに写し、1 つの
   受け渡しで sys に渡す。流れの番号は書き込み器の総数の 0 戻しと同じ辺で変わる。窓の `STREAM_EPOCH` の読みは組を写し、以後の
   `LA_WRITTEN`・`LA_WPTR`・`EV_WPOS`・`EV_START` の読みは写しを返す。`CURRENT` = 公開された番号が窓の位置の番号と同じ。
4. **総数は折り返す。** 比べは `util_pkg` の `mod_diff`・`mod_le`（差が 2^(n-1) 未満なら以前）。リングの位置は総数から求めない:
   PL は `LA_WPTR` を公開し、中継は付き始めに `LA_WPTR − 未読` から読み位置を決め、以後は読んだ分だけ進める。
5. **受け渡しは握手。** `cdc_value` は送った値を受け側の返事が戻るまで変えず、その間の読み込みは最新の 1 つを控えて後で送る（最後の
   値は必ず届き、届く値はどれも送った値そのもの。シミュレーションで assert）。sys → mem の開始の設定は状態（番号・run・設定）として
   流し続け、mem は番号が変われば始め（run = 0 なら始めて止める）、同じ番号で run = 0 になれば止める。`SAME_CLOCK`（PYNQ）は 1 周期で渡す。
6. **拍は流れの番号を持って届く。** 拍の FIFO に番号の下位 4 ビットを付け、書き込み器がその流れを始めるまで待たせる（前の流れの
   拍は捨てる）。開始の受け渡しと拍の遅れの競争にしない。
7. **完了は信号で。** 読み出し中 = 要求の番号を mem が受けていない・mem が busy・mem が入れた拍の数を sys が取り出していない・分解し
   終えていない・PS への読み出しの要求に返事が無い。流れの読み出し器の始めは `T_WAIT`（busy を見る）で待つ。
8. **イベントのリング**は、それを読む流れの間は `events.enable` の 0→1 でも先頭に戻さない（位置と written を続ける）。
9. **流れの終わりの境界**（2026-11-03 のレビューの B1 で決めた）: 流れは**止めの命令が効いた時点**（mem で書き込みが止まった周期。
   `ev_lim` が書き位置を追うのをやめた時点）で終わる。流れに入るイベントはその時点の書き位置まで。それより後に書かれたイベント
   （`events.enable = 1` の間は止めた後も書かれる）は流れに入れず、イベントのリングに残し、`events.read`（窓経由）で読む。
   このため、PS が読む流れで書き込みが止まった後は、公開する `EV_WPOS` を `ev_lim` で頭打ちにする（読み位置からの距離で比べる）。
   中継は公開された `EV_WPOS` まで読むので、`ev_lim` を越えて `EV_CONSUMED` を返さない。前は頭打ちにせず、中継が `ev_lim` を
   越えて読むと未読（`ev_lim − 読み位置`、mod 2^EV_BITS）が 0 にならず、`reading`・`ACTIVE` が 1 のまま残って流れが終わらなかった。
10. **リセット**: rst と mem_rst は同時にかける。リセットの後は番号 0、受け渡しも 0 を持つ。片方だけのリセットの後の reading は
   次の両方のリセットまで定まらない（非同期 FIFO と同じ）。

## 3. 中継（fprobe-relay）

- 位置の書きは全部 `ps_put`（番号が違えば先に `POS_TAG`）。複写の道・ゼロコピーの道の解放・つながりの終わり。
- 1 周: `STREAM_EPOCH`（写す）→ `LA_WRITTEN` → `EV_WPOS`（付いた後は 3 回。前は 6 回）。`ACTIVE` = 0 なら離れる、`CURRENT` = 0 なら
  何もしない（休まず見る）。付き始め: `POS_TAG` → 位置 3 つ → `STREAM_EPOCH` を読み直し、同じ番号・`CURRENT` なら付く。
- ありえない位置（未読がリングより多い等）は読まずに数える（`ps_bad_*`。状態の問い合わせで返す）。
- ゼロコピーの道を閉じるときは `SO_LINGER 0` で打ち切ってから、取ったかたまりを PL に返す（捨てた数を `zc_abandoned_*`）。
- NIC の設定は変える前の値を `/run/fprobe/nic-saved` に控え、atexit・落ちる信号・次の起動で戻す。
- 状態の問い合わせ（版 2）は、問い合わせの番号を返事に写す。ホストは自分の番号の返事だけを受ける。
- PS 直読みは窓の版 4 だけで使う（1〜3 はフレームの受け渡しだけ）。

## 4. 試験

- `gateware/tests/tb/la_deep_buffer_ps_tb.py`（別クロック・`SAME_CLOCK`・`TOTAL_START_BELOW_4G` で 2^32 の手前から）: 古い番号の位置を
  使わない、開始と止めが受け渡しより近くても最後の状態に着く、番号と組が揃う、events.enable の始め直し、読み出しの完了。
- `gateware/tests/tb/review_psstream_evstop_tb.py`（`SAME_CLOCK`）: 止めた時点で未読が残り、止めた後もイベントが来続けても流れが
  終わる。流れのイベントは止めた時点まで（送った順の先頭）で、それより後のイベントはリングに残る（§2.9）。
- `gateware/tests/tb/ps_window_tb.py`（窓 + la_ps_port）: 番号での 0 戻し、古い番号の書きを捨てて数える、番号が変わる周期の書き、写し。
- `gateware/tests/tb/cdc_value_tb.py`: 不規則に速く送っても混ざらない・順番・最後の値・同じクロック。
- `host/tests/test_pynq_relay_ps.py`・`test_pynq_relay_zc.py`（窓の模型 `tests/pynq_window.py`。読みの n 回目に PL を変える注入の口）:
  読みの途中で次の流れ、`CURRENT` = 0、写しの時点、2^32 の折り返し、ありえない位置、閉じたときの数え。

## 5. 実機で確かめること

`fprobe_pynq_deep`（と `fprobe_pynq_deep_fast`）を作り直して書き、中継を据え付け直す（`window_regs.h` を足した）。
長い流し（25 MS/s・RAW 16 ch を 20 分以上: 総数が 2^32 を越える）で欠けなし、`relay_status` の `pl_stale_writes`・`ps_bad_*` が 0、
流しの開始・止めの繰り返し（間を空けずに）で前の流れの拍が混ざらないこと。

### 5.1 実機の結果（2026-11-03、C:\fw85 = fprobe_pynq_deep・C:\fw86 = fprobe_pynq_deep_fast、中継は窓の版 4）

- ビルドの前に、同期化と cdc_value の制約が generate の中の FF（`cross_g.stage_reg[0]`・`cross_g.held_reg`・`cross_g.value_r_reg`）に
  当たらず効いていなかったのを直した（3d1a57b9。C:\fw84 の cap_clk が -0.072 / -0.157 ns、C:\fw83 はたまたま満たしていた）。
  直した後は 2 つとも最初の戦略で満たした（deep: sys 101.7 MHz、deep_fast: cap_clk 418.6 MHz・sys 104.5 MHz）。
- 長い流し（fw85、RAW 16 ch・25 MS/s = 50 MB/s を 1600 秒）: 80.0 GB = 5.0 × 10^9 拍（1 拍 16 バイト。2^32 拍 = 68.7 GB を越えた）、
  溢れなし・欠け 0、`ps_bad_la_positions`・`ps_bad_ev_positions`・`pl_stale_writes` は前後とも 0、リングの未読の最大 20998 拍。
  - 1 回目（並行で gateware の全体試験が PC で走っていた）は 1000 秒・48 GB で制御の READ の応答が 2 秒の時間切れを越えて止まった。
    中継の記録はゼロコピーの送りの完了まで最大 1.52 秒（PC が TCP を受け取らなかった時間）で、中継の主のループは送りが詰まっても
    1 ms ごとに制御を受けに戻る作り。PC が空いた状態の 2 回目では起きなかった。制御の UDP に再送は入れていない（点検の A11 は別に扱う）。
- 開始と止めの繰り返し（fw85、間を空けず 200 回、流す長さ 0.05〜0.23 秒を回ごとに変える）: 溢れ・欠け・受け取り 0 の回は 0、
  中継の数えは 0。
- deep_fast の HIL（fw86）: RLE 周期 300・150、RAW 1 ch 400 MS/s・800 MS/s（上限を明示）の 4 件が通った。PS 直読みの試験
  （`test_pynq_ps_stream_hw.py`、fw85）は 7 件すべて通った（PS 直読み 32.6 MB/s、窓経由 9.5 MB/s、TCP 10 MS/s・8/4/2 ch）。
