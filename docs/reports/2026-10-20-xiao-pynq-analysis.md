## 2. キーの走査（ロジアナ、5 µs ごと）

fprobe のクロストリガの出力で U の行を「列（ch1）が High の間 High」にして押し、行の立ち上がりで取り込んだ。

- 待っている間: 列は High のまま（キーの割り込みで待つ方式。走査していない）。
- 行が上がってから走査が始まるまで **0.20 ms**。
- 走査の周期 **約 1.0 ms**（0.90〜1.08 ms のばらつき。ワークキューで回しているため）。列が選ばれるのは 1 回 **約 40 µs**。
- fprobe の出力は列に約 40 ns で追従するので、本物のスイッチと同じ形で読まれる（J・U 各 10 回で取りこぼし 0）。

## 3. 押す・離すから状態が変わるまで（PC から position_state を読み続けて）

`position_state`（0x20005C0B、右手から左手へ送る押されている位置）を、fprobe の操作の直後から PC が読み続けた（1 回
約 0.4 ms の粗さ。10 回）。

| | 中央値 | 範囲 |
|---|---|---|
| 押す → position_state が変わる | 4.4 ms | 4.1〜4.6 ms |
| 離す → 戻る | 7.6 ms | 7.1〜8.0 ms |

所見: ビルドの設定（`build/right-mon/zephyr/.config`）は `CONFIG_ZMK_KSCAN_DEBOUNCE_PRESS_MS=3`・
`CONFIG_ZMK_KSCAN_DEBOUNCE_RELEASE_MS=5`、走査は `diode-direction = "col2row"`（列が出力、行が入力）。測った値は
「設定の待ち + 走査の粒度（約 1 ms）+ PC の操作と読みの往復（約 0.5 ms）」で説明がつき、設定どおりに動いている。
離すほうが約 3 ms 遅いのは設定（5 ms）による。行が入力（押すと High）なので、基板の引き上げのある穴に行をつなぐと
押されっぱなしになる（2026-10-20 の配線の不具合の裏付け）。

### 3b. 共通の時刻での測定（イベント記録を BRAM に持たせた後。docs/superpowers/specs/2026-10-20-bram-event-ring-design.md）

ロジアナで U の行の立ち上がり（押した時刻）と最後の High（離した時刻）を取り、同じ時刻の物差しで、サンプラ（5 kHz、
`position_state` の U の位置を含む語 0x20005C0C）の値が変わった時刻と比べた（10 回、サンプラの誤り 0）。

| | 範囲 | 粗い測定（PC から読む）との差 |
|---|---|---|
| 押す → position_state が変わる | **3.07〜3.85 ms** | PC の往復の分（約 1 ms）が消えた |
| 離す → 戻る | **6.89〜7.06 ms** | 同上。ばらつきは 0.17 ms |

所見（ZMK の `module/lib/zmk_debounce/debounce.c` と照合）: チャタリング除けは積算方式で、走査（1 ms）ごとに食い違い
なら 1 ms 足し、**しきい値に達したのを見た次の走査で**切り替える（押す・離すとも走査 1 回分が上乗せ）。
- 押す: 待っている間は割り込みで待ち、行が上がると 0.2 ms で走査が始まる → 0.2 + 3（設定）≒ 3.2 ms。測った 3.07〜3.85 ms
  と合う（残りはサンプラの 0.2 ms の刻みと、position_state を更新するまでの処理）。
- 離す: 押している間、行は列が選ばれる 40 µs だけ High なので、測りの起点（最後の High）は「最後に押していた走査」。
  そこから次の走査で離しを見つけ、1 + 5（設定）回目で切り替わる ≒ 6 ms、後段の処理を足して約 7 ms。
- **ZMK の動きは設定どおりで、異常は無い。** 離すほうが長いのは設定（release 5 ms > press 3 ms）による。

## 3c. 左手との BLE の接続（止めずに Zephyr の `acl_conns[0]` を DWARF で読んだ）

| 項目 | 値 |
|---|---|
| 状態・役割 | BT_CONN_CONNECTED・peripheral（左手が central） |
| 接続の間隔 | 6 × 1.25 ms = **7.5 ms** |
| peripheral latency | 30（送るものが無ければ最大 30 回休める。あれば次の回で送る） |
| 切断までの待ち | 400 × 10 ms = 4 s |
| PHY | LE 2M |

所見: 右手で状態が変わってから左手に届くまで、BLE の 0〜7.5 ms（平均 3.75 ms）が加わる。押してから左手まで
約 3.2 + 0〜7.5 ms。打鍵の遅れを詰めるなら、接続の間隔（ZMK の split の BLE の設定）が一番効く。

## 3d. 電池・起動からの時間・リセットの原因（止めずに読んだ）

- 電池（利用者の部品 `hhkb,battery-alkaline`、`alk_data_0`）: ADC の生の値 967 → **1.70 V**。設定は空 2.40 V・満 3.30 V
  なので残量 0%（`last_state_of_charge = 0`）として左手に送っている。今は USB で給電しているので動作には影響しない。
  乾電池が入っているなら交換時期（2 本で 1.70 V = 1 本あたり約 0.85 V）、入っていないなら表示が 0% になる理由。
- 起動からの時間: `curr_tick` 1,364,183,743 / 32768 Hz ≒ **11.6 時間**（不意の再起動は無い）。最後の打鍵は約 37 分前
  （`activity_last_uptime`。fprobe のキーの試験）。
- リセットの原因（nRF の RESETREAS 0x40000400）: 0（電源の投入。起動のときにブートローダが消している可能性もある）。

## 4. ほかに確かめたこと

- BLE（左手との接続 `is_connected`）は、止めずに読む間も、モニタ方式でブレークポイントで止めている間も真のまま。
- モニタ方式: `zmk_physical_layouts_kscan_process_msgq` のブレークポイントに、fprobe で押した 0.07 s 後に止まり、
  呼び出しの履歴（work_queue_main → z_thread_entry）・ステップ・再開ができた。
