# FPGA 観測の端から端までの差分試験: 台帳（検出専用。修正はしていない）

日付: 2026-10-25。土台: `integ/round1`（2952479c）。製品コード（RTL・host）は変更していない。

## 作ったもの

- `gateware/tests/tb/obs_e2e_tb.py`・`gateware/tests/test_obs_e2e.py`: obs_harness（obs_jtag_engine ↔ JTAG ↔ obs_soft_core / obs_snap_core）に、
  ランダムな間隔・値で対象の probes を変え、エンジンのイベント（ev_valid / ev_sync / ev_data / ev_time）を集め、本物の復号器
  `fprobe.obs_decoder.samples`（ObsDecoder）に通し、復号した (fprobe の時刻, 値) を、シミュレーションが知っている正解
  （値を替えた対象の clk の立ち上がりの瞬間の fprobe の時刻）と突き合わせる。
- 正解の時刻の物差し: time_count を clk の立ち下がりで読み、f(T) = tc + (T − (Tf − 半周期)) / 周期 で連続化（count n は立ち上がり n から次まで）。
  対象の clk は立ち上がりの直後に probes を替える（登録の出力。obs_core の SAMPLE_DELAY = 1 の前提）。
- 観測の回路の申告（REG_SYNC_DELAY / REG_SAMPLE_DELAY / REG_CLOCK_HZ）はレジスタの読みで取り（host の FpgaObs.register_read と同じ待ち方）、
  復号器の sync_delay（半周期の単位 ÷ 2）・sample_delay に渡した。nominal_ratio = 対象の clk の周期 / fprobe の周期。
- 時刻の許容の閾値は置いていない（測った数字を下に示す）。試験が確かめるのは: 値の列が欠けなく順序どおり・時刻が全部付く・時刻が単調。
- 実行: `pytest gateware/tests/test_obs_e2e.py`（全体で約 15 分。並列は run_cocotb(parallel=True) だが 1 設定 1 テストなので実質直列）。
  E2E_LOG に統計を JSON 行で追記できる。

## 測った事実

### (1) 値の列

溢れない条件（短い間隔 1〜8 周期の連続は 6 回まで、その後は吸い出せるだけ空ける）で、全設定とも 150 変化 + 初期値の列が
**欠けなく・順序どおり・重複なし**で復号された（値は 16 ビットのランダム）。溢れの切れ目（gap）は 0。

### (2) 時刻の誤差（復号した time_fprobe − 正解、単位 = fprobe の刻み 10 ns。申告の遅れで直した後）

SYNC_DELAY 申告: 2 クロック版 3.5 周期、1 クロック版 6.5 周期（対象の clk）。SAMPLE_DELAY 申告 1 周期。対象の clk 50 MHz = 2 刻み/周期。

| 2 クロック half=3 sync=1 words=8 | 150 | -0.546 | -0.234 | -0.490 |
| 2 クロック half=5 sync=4 words=4 | 150 | 0.000 | 0.000 | 0.000 |

読み方（事実のみ）:
- 絶対値の最大は 1.399 刻み（= 0.70 対象の clk 周期、対象の clk 31.7 ns の設定）。他は 1.0 刻み（0.5 周期）以内。
- 2 クロックと 1 クロックの両方で、整数比の clk では誤差が定数（0 か −1.0 か −0.49）になる。対象の clk が fprobe の clk と位相固定で、
  印の遅れ（申告は平均 ±0.5 周期の幅）が決まった値になるため。整数比でない clk では誤差が分布する（標準偏差 0.07〜0.41 刻み）。
- 印が 1 組だけの間の値（basis = nominal_ratio）は、nominal_ratio を正しく渡したときは同じ精度（長い静かな区間の最初の値で
  −1.0 〜 +0.28 刻み）。**nominal_ratio に申告の CLOCK_HZ と違う値を渡した場合は未測定**（host は申告の CLOCK_HZ から作る）。
- 鎖（ir_before / dr_before 等）・1 クロック版・TCK の速さ（half 3/5/10/20）・sync_period（1〜8）・words（2〜8）・印の番号の一周を
  変えても、値の列は欠けず、時刻に None は出なかった。時刻は単調。

### (5) 溢れ

密に変える（1〜300 周期）400 変化・words=2 で溢れさせた（2 クロック・1 クロック）。復号した値は正解の部分列で、隣り合う復号した値の
正解での番号の差 = その間の gap の lost の合計と**全箇所で一致**した（2 クロック: 20 切れ目・失った 305・値 116 件、1 クロック: 8 切れ目・
失った 324・値 85 件）。切れ目なしの飛び（静かな欠け）は 0。

### 標本型（obs_snap_core）

60 変化を 1〜3000 周期でランダムに替え、各標本の値は「その fprobe の時刻の正解の値」と一致（食い違い 0）。見えた標本 28 + hidden の lost 32 = 60 変化で一致。

### (4) 開き直し・リセット

- 止めて開き直すのを 4 回繰り返し（各回 12 変化）: 各回の復号は、その回に替えた値だけで一致。
- 密に替えて対象の FIFO を溢れさせたまま止め、開き直す: 前の観測の読み残しが新しい観測の値に**混ざらなかった**（stale = 0。2 クロック・1 クロック）。
- 対象の clk 側のリセット（tgt_rst）: 記録は止まったままにならず、リセットが明けると TCK 側の CONTROL を写し直して**自動で再開**する
  （target_running は 1 のまま）。→ BUG-E2E-001、E2E-S1。

## 不具合（A = 静かに誤った結果 / B = 失敗が見える / C = 端の条件・まれ / D = 品質）

件数: A 1（まれな条件なので C 相当でもある）・B 0・C 0・D 0（疑い 3 は下）

### BUG-E2E-001（A、まれ）【修正済み: リセット明けの再開を溢れの経路に乗せた。下の「修正」】 対象の clk 側のリセットの間の変化が、失ったと分からないまま続けて見える

- 再現試験: `tests/test_obs_e2e.py::test_changes_during_a_target_reset_are_reported_as_lost`（xfail strict。tb:
  `changes_made_during_a_target_reset_are_reported_as_lost`）。
- 事実: 値 0x0AAA が安定した後、tgt_rst の間に probes を 0x1111 → 0x2222 → 0x3333 と替えると、復号は 0x0AAA → 0x3333 と**切れ目なし**で続く
  （`[value 0xa0, value 0xaaa, value 0x3333]`、gap・hidden なし）。0x1111・0x2222 の 2 変化は何の印も無く消える。
- 原因の推定: リセットが明けると `reload` で TCK 側の t_control（開始）を写し直して自動で再開し、S_RESYNC → S_GROUP → S_VALUE で「組 → 今の値」を
  新しい鎖（delta 0）として書く。溢れ（dropping）の経路でないので溢れの記録（lost）を書かず、復号器は新しい鎖の始めを溢れとして扱わない。
  リセットの間の変化は数えられていない（`dropping` は RESYNC の溢れの時だけ lost を数える）。
- 直し方の案（適用しない）: リセットからの再開を「溢れ」の経路に乗せる（dropping := 1、lost には「不明」を意味する値）か、再開の鎖の前に
  「リセットがあった」ことを示す記録（制御の記録の新しい種類）を書く。もしくは再開せず、ホストが開始し直すまで止める（`target_running = 0` で見える）。
- 影響: 対象の設計がリセットされる試験（リセット直後のレジスタ・状態遷移の観測。まさに解析で見たい瞬間）で、リセットの間の変化を見逃したと気づけない。
- 確信度: 高（シミュレーションで再現）。ただし「リセット中の probes は意味が無い」という立場なら仕様どおり。その場合も下の E2E-S1 は残る。

- **修正**: `obs_core.vhd` の reload（rst の明け）で CONTROL=1 を写し直すとき、`dropping`・`overflowed` を 1 にして再開（開始の `reg_sync`
  のトグルでは従来どおり 0）。S_RESYNC → S_GROUP → S_OVERFLOW → S_VALUE で「組 → 溢れ → 値」と書き、復号器は既存の溢れの記録として
  gap を報告する。記録の形式・復号器のコードは不変（後方互換）。lost はリセット明けに数えられた分だけ（0 もある）で、
  リセットの間の変化の数は事実として不明 = 「0 でも欠けがある」と文書に明記。理由: fprobe は事実だけを返す。数えられないものを
  数えたふうにせず、連続性が切れたことを既存の gap で示す。target_running は 1 のまま（再開は実際に起きている）。
- **E2E-S1 の判断**: 復号器は鎖の始め（delta 0）の値を直前と同じでも value で返す（コードは変えない）。これは出発点で変化ではない。
  文書（ObsSample・README）の「値が変わった」を、鎖の始めは出発点（直前の gap・group が目印）と正した。リセット明けは gap が付くので区別できる。

## 疑い・気づき（再現試験なし、または仕様の判断が要る）

- **E2E-S1（D）** 対象の clk のリセットの後、直前と同じ値の「value」サンプルが出る（`0x55c3, 0x55c3`）。復号器は kind "value" を「値が変わった」と
  定義するが、再開の最初の値は変化ではなく、`group` のサンプルも出ない（組が同じなので `_shown_group` が変わらない）。変化の数を数える利用者が 1 つ多く数える。
  開き直し（reopen）でも同じ形が出るはず（鎖の始めの値は必ず出る）。BUG-E2E-001 と同じ直し方（再開の印）で解消する。
- **E2E-S2（D）** 標本型の最初の標本は、変化の回数 n が付いていても復号器は捨てる（前の標本が無いので hidden にできない）。
  最初の標本までに見えなかった変化の数は報告されない（開始前の変化なので許容かもしれないが、n > 1 は事実として持っている）。
- **E2E-S3（試験の範囲）** 申告の遅れは平均値（SYNC_DELAY は ±0.5 周期の幅）なので、位相固定の clk では誤差が定数に張り付き、整数比でない clk では
  最大 0.7 周期ほどまで分布する。これは申告どおりの性質で不具合ではない。
